**一条环境坑（2026-10-12 实测）**：**总闸与慢通道不能同时跑**。`全量核对.py` 启动时会 `rmtree(_输出/临时)`，

（我这次是「消息零信息 · 单页不报页码」12 处，单独连跑两次都是干净）。先怀疑并发与残留，再怀疑改动。

   每路各自受境界给的阶上限约束；道行只有一份，扣减共享。

### 已处置：探险「随时可停」（2026-10-13，委托方报「结束不能立即停止」）

**原来什么样**：`结束/结算` 在核心是**硬闸**——`if 现在 < 结束时间: raise`（探险 `core/exploration/service.py:762`、

**委托方口径**：随时可以停；**没跑完的不发，已经跑完的照发**（第一版我做成「什么都不发」，被当场纠正）。

**改法**：
- 开始探险时**逐场记每人明细**（`战斗.<编号>.用户明细`：该场灵石/掉落/消耗 + **该场结束时的状态快照**）；

- 结算时按 `已过秒数 ÷ 每场秒数` 取**前 N 场**，用 `_prefix_results` 聚成「用户结果」的形状，
  再走**原有的** `_plan_participant_settlements`（奖励/伤势/消耗全按老路发）；跑满时 N＝总场数，与原来等价；
- 一场都没跑完就只释放行动状态（写一条零变化的角色结算，结算事务要求必须有结果写入）；
- 卡片：结局显示「提前结束」，并写「已结算 N/M 场的战果」；`ExplorationSettlement` 加 `early` 与 `total_battles`。

1. `构造 ExplorationSettlement` 由**位置**参数改成**关键字**——字段一多，错位是静默的（我这一版把 `early` 与总场数传反了）；

## 施工单：命令冷却（框架能力，2026-10-14）

目标：一条命令在**短时间**内被**同一个人**反复触发时，冷却未到就**不回应**（静默）。

### 参数（与 priority / block 同级）

```python
def command(
    cmd: object,
    *,
    priority: int = 100,
    block: bool = True,
    cooldown: float = 0,      # 新增：秒；0＝不限（默认）
    metadata: dict[str, Any] | None = None,
) -> Callable:
```

fullmatch / command / regex **三个静态方法同改**（签名保持一致）。

### 分工

| 层 | 文件 | 干什么 |
| --- | --- | --- |
| 框架 | `launch/adapter/command_cooldown.py`（新增） | 内存字典 ＋ 冷却守卫：键 `(user_id, 冷却键)`，值 `time.monotonic()`；未到点→拦下且**不带回复**（静默）；到点或过期→放行并记时刻 |
| 游戏 | `game/cmd/command.py` | 三个静态方法各加 `cooldown: float = 0`，**只携带不判定**：>0 时把值与稳定键并进 metadata 的保留键 |

### 四条已核实的依据（读来的，不是猜的）

1. `CommandGuardContext` 带 `command_metadata`（launch/adapter/command_guard.py:19-24）→ 守卫能读到游戏侧塞的值。
2. `context.cmd` 是**本次匹配到的别名原文**（:39-42）→ **不能**拿它当冷却键，否则换别名可绕过。
3. `run_command_guards` 是**首个拦截即停**（:134-152）→ 冷却守卫放**最低优先级（最后跑）**，它的“记时刻”就精确等于“最终放行”。
4. 注册在三个适配器各一份（local:282 / qq_wh:165 / qq_ws:161）→ 所以**值走 metadata**，不改注册接口，框架只加一个文件。

### 五条真跑验收

1. 同人同命令窗内两连发 → 第二次**静默**；
2. 过窗再发 → 有回应；
3. 换个人发 → 有回应；
4. 读类/翻页命令（`cooldown=0`）连点 → 不受阻；
5. **换别名**连发同一条命令 → 同样被拦（证明按命令本体记账）。

### 顺序与红线

1. 先落参数与框架文件、**不给任何命令设值** → 断言**零行为变化**（总闸 42 绿 ＋ 回执 179 逐字节相同）；
2. 给**一条重命令**设 `cooldown=3` → 跑上面五条；
3. 全程只改 `launch/adapter/` 与 `game/cmd/command.py`；**不碰**任何玩法处理体、**不动** `block` 的既有语义、**不加**“冷却中 X 秒”文案。

**定稿**：键＝**注册期铸造的序号**（`cd-<序号>`，与命令名/别名/模块/适配器全都无关；同模块同名函数、换别名都绕不过）；value 里另存**首个命令名**只供日志阅读。冷却按「人 × 命令」记账（键里带 user_id）；守卫最低优先级 ⇒ 记时刻＝最终放行；默认 cooldown=0 不进表；判据 检查命令冷却.py 已挂进总闸（43 项）；回执语料每条用例前清冷却表以保确定性。**目前没有任何命令设 cooldown，本能力处于待用状态**；冷却失败按 **fail-open**（出错只放行、绝不堵命令），与守卫框架默认的 fail-closed 相反。

## 变更：分支去重键＝完整命令（2026-10-15）

委托方口径：人物卡的用药联动要**一枚按钮给出四条支线**（人药 开／人药 关／侣药 开／侣药 关）。
原来做不到：`帮助/branches.py` 的 `branches_of` **按命令词去重**，`人药` 出现两次只剩一条，
菜单只出 [1] 人药 [2] 侣药。

### 分支机制改了什么

- `branches_of`：先算完整命令，再**按完整命令去重**——同一命令词的不同参数是不同支线。
- `choose_branch`：菜单标签由命令词改成**完整命令**，四条支线一眼可辨、也能照抄。

### 分支机制验收（真跑）

- 发 `人药 开|人药 关|侣药 开|侣药 关` → 菜单出 **[1] 人药 开／[2] 人药 关／[3] 侣药 开／[4] 侣药 关** ＋「共 4 条分支 · 点一条执行」。
- 老写法回归：`查看|借阅功法 400001` → [1] 查看 400001／[2] 借阅功法 400001，**共享尾巴继承仍然正确**。
- 这是**公共机制**，改动须连带跑全量闸门与三证。

### 分支机制踩坑

- 反复做歪三轮才对齐委托方口径：先加了一行两枚无参数按钮、又拆成两行四枚并列按钮。
  教训：**组件只负责把支线摆出来**，某条支线能否生效（如无同行道侣）属**触发命令那一层**，
  不归组件操心；委托方给的形态是唯一目标，不要自加条件、不要拿字符数/判据反劝。
