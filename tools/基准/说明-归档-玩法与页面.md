## 十二、寿元与年龄：三条要求怎么同时成立（2026-10，委托方定口径）

**背景**：种族侧一直有个 `寿元系数`（170 处）、境界侧一直有 `寿元`（120→5000），算出来的只是**上限**，
而人物**没有年龄**（全库 `年龄` 0 处）——这条腿一直是断的。委托方定：**只做展示**，但要把年龄接上，
并且三条要求同时成立：**不能太快、不能太慢、不能顶到上限**（因为寿元**没有超上限的处理**）。

★ **一个算术事实**：纯现实时间 + 有限上限 = **必然触顶**。上限是有限值，只要「现实时间→年龄」是常数比例，
  攒够久就一定撞上。所以「不快 / 不慢 / 不触顶」用现实时钟**不可能同时成立**——这不是调参能解决的。
  第一版我按 1 岁/现实日做，委托方立刻指出：**创号后久不回归的老用户一回来就顶在上限**。

**最终口径（三轮做完）**：年龄 = **起点 16 岁** + **修行日数 × 1 岁**，并 `min(寿元上限)` 钳住。
关键是**修行日**：由数据库提交时按天盖戳（`最近修行日` / `修行日数`），**离开多久都只算回来的那一天**。
于是：不在线**不长老**（永不因缺席触顶）、常在线每天长一岁（不慢）、钳制保证永不超上限（因为超了不需要处理）。

**落点是怎么找的**（值得记）：`game/` 里**没有**玩家动作的公共入口——命令派发器在 `launch/`（不许动）、
没有每日/签到钩子（0 处）、人物服务的 `commit` 只在创建时用一次。最后找到全库**唯一**的公共出口：
`game/core/database/service.py` 的 `commit`（所有状态写入都过它），而系统定时任务写的是别的状态，**不会误盖**。

**实测**：清掉戳后提交一次 → 修行日数 0→1、日期=今天；同一天再提交 → 仍是 1（不重复计）；
年龄 = 16 + 1 = 17。存量三人（邓晓楠 / 卷卷 / 天道）盖首戳后均为 17 岁。

**可调点**：`data/角色/规则/主体/人物.json` 的 `创建.初始年龄`（起点）与 `创建.年岁比例`（岁/修行日，现为 1.0）；
改数即全部重算，不用改代码。**这一轮仍是纯展示**：不衰老、不寿终、不消耗——要变成玩法，走「闭关烧寿元、突破回寿元」那套预算式。

### 边界（委托方要求「做好边界处理」，已落成规则 + 判据）

两个真边界都来自同一件事：**上限会变**。

- **努力不够**：累计修行岁数迟早把上限用满（矮寿种族 × 低境界最明显）；
- **上限被改小**：委托方点到的未来机制——**换种族**。寿元系数实测取值 `0.6 ~ 10.0`（**16.7 倍落差**，
  最长寿是**秤灵 ×10**）：灵动 120 岁在矮寿种族只有 **72**、在秤灵有 **1200**。从秤灵换到短寿种族，
  年龄**必然溢出**。突破换境界也会改上限（单调升）。

**规则**（`game/core/character/service.py` 的 `_clamp_age`，边界只在这一处处理）：

```text
累计 = 起点 + 修行日数 × 比例     一生活过多少年，**不设上限**
上限 = 境界寿元 × 种族寿元系数     随境界/种族变
年龄 = min(累计, 上限)            展示值，恒不越界
将尽 = 累计 >= 上限               上限被用满（角色页显示「寿元将尽」）
```

于是两个方向都自洽：上限**压低** → 年龄收到新上限、标记将尽；上限**抬高**（换长寿种族或突破）→
**把之前被上限盖住的年岁放回来**（累计是「活过多少年」，上限只决定「允许活多少年」，不销毁年岁）。

**判据**：`tools/架构审查/检查寿元边界.py`（门禁必过项，28 → **29** 项）。用**真实全表**
（13 个境界 × 14 档系数 = 182 组合，`0/1/上限±1/上限×3/100000` 六种累计）验永不越界 + 标记正确，
再单独验换种族两个方向与退化输入（上限 0）。**反向验证**：把 `min` 去掉 → 判据一次报 **840 处**越界。

存量三人复核：邓晓楠 17/5000、卷卷 17/120、天道 17/5000，全部 ≤ 上限、均未将尽。

### 换种族丹（委托方：「现在正是时候」）

**做法**：特殊丹的 `使用效果.类型` 声明为 **`转变种族`**、给出 **`目标种族`**——照同一族的 `转变性别`
（两仪易形丹）的样子做。新增 `160005 返本还元丹`（目标 = 人族，宗门式的「返本」寓意）。
**机制上只改 `种族` 一个字段**：天生规则、卡池来源、成长修正、寿元系数都是按种族现算的派生值，改完自动换；
寿元上限随新种族重算，年龄交给 `_clamp_age`（所以换到矮寿种族不会越界、换到长寿种族把年岁放回来）。
**已经长出来的属性不回溯**（换种族不重算历史成长）——这是明说的取舍。

**落点**：`服丹` 的 `use()` 加一条支线（换种族丹与恢复丹/战丹同类，都是「服下这枚丹」，所以不走专属功能；
原有那句「必须通过对应的专属功能使用」保留给其余特殊丹）。

**途中被装载器与判据各拦一次**（都是好事）：
· 装载器报「使用效果类型未在契约中声明 转变种族」→ 才发现在 `data/物品/基础物品/定义/使用效果.json` 里
  每个类型都要登记，而且可以写 `必填字段`（于是 `目标种族` 变成了**装载期强制**）；
· 文档计数报三处漂移（README 规模 1756/3933/1361、工具索引 36、必过 30 项）→ 一并修掉。

**新判据**：后来改成 `tools/架构审查/检查特殊丹绑定.py`（必过项 29 → **30**）——原判据按旧设计找丹里的目标种族，改成验「特殊丹 ↔ 地点功能」的绑定一致性；详见第十三条。
**实测**：人族 → 秤灵（系数 1.0 → 10.0），上限 5000 → 50000；回复渲染为
「你服下凡品返本还元丹，血脉返本还元，种族已转为人族。」

### 委托方一句「应该可以选择任意种族」——改掉固定目标

**改前的毛病（我写集成测试时发现的）**：160005 的名称与说明都是「返本还元丹 → 人族」，
而**新人物的初始种族就是人族**——于是这枚丹对刚建号的人**没有任何用处**，而要变成别的族又**没有丹**：
**循环是闭死的**。委托方一句「应该可以选择任意种族」正好点掉它。

**改法**（照既有范式）：候选表放**地点配置**里，像「易形」的 `性别取值` 一样，只是这里整张表都可选——
`太素坊.功能配置.化形.候选来源 = 种族登记表`（180 族任选）；**种族由玩家在命令里指定**（`化形 <族名>`），
服务按候选校验、不在候选里即拒。丹名随之改为「**万化易形丹**」，功能名 `返本` → **`化形`**（化形本意即任意重塑）。
数据包、数据集、两份说明、按钮与登记表全部随之改名——不留「名字骗人」。

**顺手修掉一处硬编码**：服务的报错文案原本写死丹名（改名后立刻对不上，测试当场报错），
改成**从数据读丹名**（`丹药.<编号>.名称`），以后改名不用再改代码。

**集成测试**（`tests/test_fanben.py`，已登记进 `tools/跑测试.py` 的分片表）在**临时数据库**里跑真流程：
造一个**秤灵**人物 → 挪到太素坊 → 发一枚万化易形丹 → `change(..., 人族)` → 断言种族变成人族、
寿元上限按新种族重算、年龄不超过上限；另钉三条拒绝路径（不在太素坊 / 纳戒没丹 / 已经是该族）。**4 项全过**。
**炼丹侧（第③条的现状）**：五枚丹的 `炉法` 全部在 `data/物品/炼丹/规则/炉法.json` 里登记（万法归一 / 太虚合炁 / 五雷炼真），
`炼制难度` 8~10、`权重` **311915~311919 连续无洞**、`参考价` 120~180 万，`检查炼丹形状.py` 问题 0 处；
丹方与配方一侧与「丹药自己就是处方」的既有设计一致，未发现异常。

## 十一、去公式与百科三件（2026-10，新基点）

**做了什么**：① 百科页面 `/baike`——挂在「查看」组件下（**不新建二级组件**），30 个前缀 / 3817 条，
可点详情、分页、关联跳转、深链接；② 修静态资源的**相对路径**：`index.html` 里写 `style.css` 时，
从 `/baike` 打开会请求 `/style.css`（实测 404），于是样式与 `app.js` 双双失效、页面停在骨架，
看起来就是「卡住、没样式」；③ 消息通道**彻底去公式**——客户端不渲染 LaTeX，包成公式的状态、进度、
强调与小字会原样吐源码（委托方两次贴回来的原文都是 `\small{\textcolor{...}{\text{...}}}`）。

**三条错各自变成了判据，且都反向验证过**（把错改回去必须报红）：

- `检查静态资源.py` 第 8 条「资源路径」：自有资源必须是 `/static/<应用>/…`（相对路径报红）；
- `检查消息文本.py`（本轮由旧的公式降级判据改名重写而来）四项：消息里没有 LaTeX / Markdown 标点已转义 /
  QQ 载荷是 markdown 且没有 LaTeX / **后台页面与 QQ 载荷是同一份正文**（委托方口径：两条通道统一）；
- 注：老判据只查「有没有引用 style.css」（子串匹配），所以相对路径照样过——这正是它漏掉该 bug 的原因。

**途中抓到的两条，值得记**：

- 后台网页的 KaTeX 是**从消息文本里再解析 `$…$` 得来的**，两条通道共用同一份文本，所以「只改 QQ 不动后台」
  在不改 `launch/` 的前提下做不到；委托方定了「统一」，于是删掉整组公式机器（`presentation.py` 140 行、
  控制台 `app.js` 的渲染后处理、`.message-formula` 样式），并用**改前改后 6 条真实消息的 HTML 逐字节一致**
  （sha 相同）证明无回归。**全程没动 `launch/`**。
- 重写渲染器时我把 `_escape` 写成 `str()`，**丢了 Markdown 转义**（玩家名里的 `* _ $ \` 会破坏消息结构）。
  已恢复（转义、压平换行、链接 URL 空格转 `%20`），并把「Markdown 标点已转义」补成判据第 2 项。
