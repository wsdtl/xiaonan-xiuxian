# 架构审查

把 `系统架构.md` 与 `微服务边界规范.md` 里**已经声明的禁令**变成可执行检查。
属于维护审查：不进入游戏启动流程，不被 `game` 依赖。全部**非零退出即失败**。

```powershell
.venv/Scripts/python.exe -X utf8 tools/架构审查/<脚本>.py
```

## 六支脚本各管什么

| 脚本 | 回答什么 |
| --- | --- |
| `检查边界.py` | 目录必备文件、依赖方向、动态导入、第二套 JSON 读取、后台例外 |
| `校验启动契约.py` | 组合根（`game/app.py`）的启动契约：命令唯一性、状态唯一归属、命令守卫引用 |
| `校验命令目录.py` | 命令目录与 `scope` 一致性 |
| `检查数据驱动.py` | JSON 驱动完整性：有没有把正式规则写进代码 |
| `检查构筑形状.py` | 功法/真意/气机/器律四类内容是否合 `构筑契约.json` |
| `检查词条作用域.py` | 一个词条名被谁定义、被谁读取；卡内作用域是否闭合 |

## 规则与检查的落差

**这张表是本文档的重点。** 「审查全绿」只说明**已实现的那部分**成立；规范里
写了却没有对应检查的条款，破坏它不会有人报警。写这张表的直接起因：渲染器工作
里 `game/cmd` 直接导入了 `game.core.combat.card_text`，违反了「命令层不得导入核心
服务」，而 `check_core_internal_imports` 只扫 `game/core` 与 `game/features`
——**`game/cmd` 不在范围内**，所以长期无人发现。

### 已有检查

| 条款 | 出处 | 检查 |
| --- | --- | --- |
| 微服务必备 `__init__.py`/`service.py`/`说明.md` | 规范 §2 | `check_service_doc_coverage` |
| 只从微服务包顶层导入，不得碰 `engine`/`models`/`runtime`/… | 规范 §2 | `check_core_internal_imports` |
| `cmd` 不得直接导入核心服务 | 规范 §3 | `check_cmd_core_dependency` |
| 动态导入只允许 `game/cmd/__init__.py` 与 `launch/load_router.py` | 规范 §8 | `check_dynamic_imports` |
| `launch`/`message` 不得静态引用 `game` 或 `tools` | 架构 §4 | `check_framework_dependency` |
| 不得出现第二套 JSON Reader（`json.load(s)` 直读文件） | 架构 §4 | `check_single_json_reader` |
| 不得硬编码 `data` 目录布局 | 规范 §4 | `check_data_layout_hardcoding` |
| 后台命令只能由后台 scope 注册、不得读取游戏 | 规范 §3 | `check_console_boundary` + `校验命令目录.py` |
| 命令唯一性、状态唯一归属、命令守卫引用 | 架构 §2、§3 | `校验启动契约.py` |
| 四类构筑形状 | 架构 §2 | `检查构筑形状.py` |
| 正式规则不得写进代码 | 架构 §1.1 | `检查数据驱动.py` |
| 词条作用域闭合 | 规范 §4 | `检查词条作用域.py` |

### 尚无检查（待逐条补）

按「能机械判 / 值得先做」排：

| # | 条款 | 出处 | 为什么该补 |
| --- | --- | --- | --- |
| G1 | 核心服务不得引用 `features` 或 `cmd` | 规范 §3 | 依赖方向一旦反向就是架构错误，且很容易在补功能时发生 |
| G2 | `game/core/__init__.py` 不转发具体服务 | 规范 §3、架构 §4 | 它是「不许有第二套门面」的守卫，转发会让导入路径悄悄多一条 |
| G3 | `game` 不得导入 `tools` | 架构 §4 | 反向依赖会把维护期代码拖进运行期 |
| G4 | 禁止空的/无人消费的 `contracts.py` | 规范 §2 | 死代码会改掉命令层原有的异常语义 |
| G5 | 公共结果不得返回 `Fighter`/`BattleContext`/`StatusState` 等可变运行对象 | 规范 §5 | 运行对象逃逸出去后，调用方能原地改动战斗事实 |
| G6 | 随机服务必须返回或接受种子 | 规范 §5 | 没有种子就无法复现，平衡测量与语料对照都失去意义 |
| G7 | 评分、平衡模拟不得进入运行时 | 架构 §1.4、§4 | 「评分进了运行时」被明确列为架构错误 |
| G8 | 不得出现第二套战斗入口 | 架构 §4 | 同上，明确列为架构错误 |
| G9 | `cmd` 的 `reply.py`/`input.py` 不得取得组合根服务 | 规范 §3 | 适配模块拿到服务就会开始推断业务事实 |
| G10 | 不得在自身代码中遍历或拆解数据目录 | 规范 §4 | 目前只查了「硬编码路径」，遍历/拆解还没查 |

G1、G2、G3、G4 是**纯导入/结构检查**，与前八项同类，成本最低，建议先做。
G5、G6 需要类型或调用约定，G7、G8 需要先定义「什么是第二套入口 / 评分」，
G9、G10 需要判定「什么算取得服务 / 拆解目录」。

## 约定

- 新增检查写进 `检查边界.py` 的 `CHECKS` 元组，或另立脚本；两种情况都**必须**在
  本表登记，否则又会出现「规则写了、没人查」。
- 检查只报事实（文件、行号、越界了什么），不给修复建议式措辞。
- 本目录的脚本属于维护审查；**跨模块且运行前必须成立的契约**不放这里，
  放 `game/startup`（见 `系统架构.md` 第二节「启动契约」）。
