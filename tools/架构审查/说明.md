# 架构审查

把 `系统架构.md` 与 `微服务边界规范.md` 里**已经声明的禁令**变成可执行检查。
属于维护审查：不进入游戏启动流程，不被 `game` 依赖。全部**非零退出即失败**。

```powershell
.venv/Scripts/python.exe -X utf8 tools/架构审查/<脚本>.py
```

## 六支脚本各管什么

| 脚本 | 回答什么 |
| --- | --- |
| `检查边界.py` | 目录必备文件、依赖方向、动态导入、数据目录、随机种子、战斗入口唯一、评分归属、后台例外、无人引用的模块（当前 19 项） |
| `校验启动契约.py` | 组合根（`game/app.py`）的启动契约：命令唯一性、状态唯一归属、命令守卫引用 |
| `校验命令目录.py` | 命令目录与 `scope` 一致性 |
| `检查数据驱动.py` | JSON 驱动完整性：有没有把正式规则写进代码 |
| `检查构筑形状.py` | 功法/真意/气机/器律四类内容是否合 `构筑契约.json` |
| `检查词条作用域.py` | 一个词条名被谁定义、被谁读取；卡内作用域是否闭合 |

## 规则与检查的落差

**这张表是本文档的重点。** 「审查全绿」只说明**已实现的那部分**成立；规范里
写了却没有对应检查的条款，破坏它不会有人报警。写这张表的直接起因：渲染器工作
里 `game/cmd` 直接导入了 `game.core.combat.card_text`，违反了「命令层不得导入核心
服务」，而 `check_core_internal_imports` 只扫 `game/core` 与 `game/features`
——**`game/cmd` 不在范围内**，所以长期无人发现。

### 尚无检查（待逐条补）

**编号固定不变，补上一条就把它移进上面的表**，不要重排——否则历史提交里的
「G3」会指向另一条规则。

**G1–G10 已全部补完，落差清零。** 这张表现在的作用是：以后再从规范里发现新条款，
按同样格式加 G11 起的新编号；而「审查全绿」也终于等于「规范里可机械判的部分都成立」。

### 各条判据（问过的口径，记下来免得再猜）

- **G6 随机**：禁止 `random` 模块的便捷函数（`random.choice()` / `random.random()` /
  `from random import choice`）。它们走全局无种子 RNG，同一次运行里先后顺序会互相影响。
  只允许 `random.Random(种子)` 实例。现状 0 处裸用、30 处带种子实例。
- **G7 评分**：**按名字判，不扫正文**。`generating` 里含 "rating"、五行相生的
  `root_score` 是战斗规则计算（读 `五行.json` 的基准值）——扫正文会把它们全误报。
  只查目录名、模块名与顶层函数名。
- **G8 战斗入口**：硬条件，不给例外。`BattleEngine` 只允许在 `game/core/combat/` 内被
  提到；`simulate_teams` 只允许出现在 `engine.py`（定义）与 `service.py`（唯一入口）。
  第二条尤其重要——它能抓出**战斗包内另起的第二个入口**，那是包外检查抓不到的。
- **G5 可变运行对象**：名单**从代码自动取**——各包运行期模块（`models`/`engine`/
  `runtime`/… 见 `INTERNAL_MODULES`）里**非 `frozen`** 的 dataclass。规范举的三个例子
  `Fighter` / `BattleContext` / `StatusState`，正是 `game/core/combat/models.py` 里
  非 frozen 的那批（共 9 个），所以口径完全对得上。只查 `contracts.py` 与包顶层
  `__init__.py` 的 `__all__`；`service.py` 内部构造 prepared 快照是正常的，不该拦。

  **必须全库取名单，不能按包取**：`features/chakan_wupin` 里一个运行期模块都没有，
  而它要防的 `Fighter` 住在 `game/core/combat`——按包取会把它整个跳过，检查看着
  通过、其实什么都没查。这个坑是反向验证抓出来的。

### 覆写既有允许清单时的要求

允许清单（如 `DIRECTORY_TRAVERSAL_ALLOWLIST`）每加一项都要写清**为什么它不算越界**，
并在本说明里留一句。当前两处目录遍历例外：`game/core/data/files.py`（唯一的正式
JSON 遍历者）、`game/cmd/后台/天道后台/media.py`（清的是控制台自己的
`/game-console/media/`，不是游戏数据）。

### 补检查时的要求

新增检查**必须做反向验证**：在干净数据上通过只说明它没误报，还要**临时造一处违规、
确认它报出文件与行号并非零退出**，再还原。否则可能写出一条永远通过的检查——
那和没有检查一样，却更让人放心。

已按这个要求验过的：`check_core_upward_dependency`（往 `game/core/pool/__init__.py`
末尾加一行导入 features，报出该行、退出 1）、`check_core_namespace`（往
`game/core/__init__.py` 加一行 `from .pool import PoolService`）、
`check_game_tools_dependency`（新建 `game/core/_探针.py` 写 `import tools`）、
`check_contracts_file_purpose`（新建一个只再导出核心契约的 `contracts.py`）、
`check_command_adapter_purity`（新建 `game/cmd/通用/_探针/reply.py`，写
`from game.app import current_game_services`，报出导入与调用两处）、
`check_data_directory_traversal`（新建 `game/core/_探针.py`，写
`Path('data').glob('**/*.json')`）、`check_random_seeding`（同文件写
`random.choice([1, 2])`）、`check_scoring_outside_tools`（新建 `game/core/_评分探针.py`）、
`check_combat_single_entry`（两处：包外 `BattleEngine(None)`，以及**战斗包内**非入口
模块调 `engine.simulate_teams(...)`）、`check_unreferenced_modules`（新建一个全私有、
无人导入的模块，报出该文件；再接上一个真实导入方，报出立刻消失）。十次都是**造出来
能报、还原后回到 19 项通过**，且 `game/` 的 `git diff` 为空。

一个实测教训：**字符串注解抓不到**。第一次验 G8 时我写的是
`engine: 'BattleEngine'`，AST 里它是常量而不是名字，检查没触发——那不是漏报，
但造违规时必须用真实写法（`from … import BattleEngine` 再实例化）。

反向验证时踩到一个坑，记在这里：用 `Set-Content -Encoding UTF8` 造违规文件会写入
**BOM**，`ast.parse` 直接 `SyntaxError`，**整支审查当场死掉、后面所有检查不再执行**——
于是「退出码 1」看着像查出了违规，其实是崩了。现在 `main()` 会把这个异常转成一条
`无法解析` 的 finding，`ast.parse` 也都带上文件名，报出来的是真实路径而不是 `<unknown>`。

另一条教训来自这条新检查本身：**它用自己的 docstring 把自己要抓的模块「引用」掉了**。
第一版把字符串字面量一律当引用，而它的 docstring 正好举 `game/cmd/通用/查看/combat.py`
当例子，于是探针不报、真身也照样漏。现在 docstring 节点单独排除。**造出违规却不报时，
先怀疑判定太松，不要先怀疑探针**——我第一反应是重写探针，那会把它改成一个能通过的
假探针，然后拿着「检查有效」的结论走开。

### 已知的检查器局限

- 检查**只做静态导入分析**，不看运行期反射或 `getattr` 拼出来的引用。
  `check_unreferenced_modules` 是唯一的例外：它另外认字符串字面量里的模块全名或
  文件名（动态装载与配置表走这条路），所以只会漏报、不会误伤活模块。
- `_imports` 不解析相对导入（`from .pool import X` 只给 `"pool"`），
  所以涉及相对导入的规则要自己走 AST（`check_core_namespace` 就是这么写的）。
  `check_unreferenced_modules` 用 `_resolve_from` 把相对导入解析成全名再比对，
  否则每个模块都会看着像孤儿。

## 约定

- 新增检查写进 `检查边界.py` 的 `CHECKS` 元组，或另立脚本；两种情况都**必须**在
  本表登记，否则又会出现「规则写了、没人查」。
- 检查只报事实（文件、行号、越界了什么），不给修复建议式措辞。
- 本目录的脚本属于维护审查；**跨模块且运行前必须成立的契约**不放这里，
  放 `game/startup`（见 `系统架构.md` 第二节「启动契约」）。
