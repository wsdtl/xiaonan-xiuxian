# 架构审查

把 `系统架构.md` 与 `微服务边界规范.md` 里**已经声明的禁令**变成可执行检查。
属于维护审查：不进入游戏启动流程，不被 `game` 依赖。全部**非零退出即失败**。

```powershell
.venv/Scripts/python.exe -X utf8 tools/架构审查/<脚本>.py
```

## 各支脚本各管什么

| 脚本 | 回答什么 |
| --- | --- |
| `检查边界.py` | 目录必备文件、依赖方向、动态导入、数据目录、随机种子、战斗入口唯一、评分归属、后台例外、无人引用的模块、字段校验重写、中文标识符、文件编码（BOM）、重复定义、写死机器路径、被忽略却仍在索引里的文件（当前 25 项） |
| `校验启动契约.py` | 组合根（`game/app.py`）的启动契约：命令唯一性、状态唯一归属、命令守卫引用 |
| `校验命令目录.py` | 命令目录与 `scope` 一致性 |
| `检查数据驱动.py` | JSON 驱动完整性：正式规则有没有写进代码、字段契约住没住对目录（`定义/` 或 `规则/`）、大类布局对不对得上（`check_category_layout`）、组件说明写没写中文逻辑且不夹带代码（`check_component_function_docs`）、说明的 Markdown 排版与坏链（`check_component_markdown`）、**代码读的规则键说明里有没有写到**（`check_rule_keys_described`）、**说明里还有没有代码**（`check_data_docs_no_code`）、规则键与展示文案有没有消费者（`check_unread_rule_keys`）、数据集有没有消费者 |
| `检查卡形.py` | 卡形判据总入口：并发跑完全部 14 支卡形检查（构筑形状、三件套边界、词条作用域、构筑模板、原子能力、重复动作、悬空引用、被动形状、能力命名、描述一致、炼丹形状、功法冷却、监听位置、结构唯一性） |
| `检查构筑形状.py` | 功法/真意/气机/器律四类内容是否合 `构筑契约.json` |
| `检查构筑模板.py` | 构筑模板库的形状：模板编号 = `43` + 正文摘要、索引映射、参数绑定、引用还原，**以及每个面的目录真的存在、真的有卡** |
| `检查原子能力.py` | 原子能力双向核对：数据只许用登记过的，登记过的必须有人实现 |
| `检查词条作用域.py` | 一个词条名被谁定义、被谁读取；卡内作用域是否闭合 |
| `检查悬空引用.py` | 读了却没人建立的状态层数 / 构筑计量 / 战斗记录 |
| `检查三件套边界.py` | 功法只主动 / 真意只被动 / 气机只属性，以及主动形状、长文本、计数配额 |
| `检查功法冷却.py` | 每卡主动 ≤3、同卡冷却不重复、全局冷却七档分布 |
| `检查监听位置.py` | 主动技能的效果数组里不该出现 `监听事件`（监听属于被动） |
| `检查被动形状.py` | 一个被动只挂一条监听；同一张卡里被动不重名 |
| `检查能力命名.py` | 主动/被动的短名与全名在全库唯一，卡内能力名唯一，**卡名**也全库唯一 |
| `检查重复动作.py` | 「同一时点不得出现重复动作」这条硬规矩，外加渲染底线 |
| `检查描述一致.py` | 渲染器不许解释层兜底（`未支持` / `兜底` / `None` 泄漏） |
| `检查炼丹形状.py` | 丹药自带处方（`炼制难度` / `炉法`），不再有第二份丹方实体与旧号段 |
| `检查基准文件.py` | `tools/基准` 下不许出现「野文件」 |
| `检查静态资源.py` | `static/` 的形状：不许再有手工 `?v=`、页面要有中文 lang 与非空标题、跨源资源必须带 `integrity`+`crossorigin`、不许内联脚本与内联样式、没有孤儿 js/css、没有死样式、下发页面的 `site.py` 必须有 CSP（当前 7 项） |
| `检查战报展示.py` | 跑一场真实战斗，核对展示层与战报自洽：阵营分组、对阵与标题、简要行不是内部阶段名、明细里没有内部记账字段与内部编号、展示事件只带协议声明的字段且角色键查得到、演员表与调色板跟战报一致、快照只带会变的那一半且花名册覆盖每个人（当前 7 项） |
| `检查文档计数.py` | README 与 `tools/说明.md` 里写死的数目与现状一致：微服务数、命令组件数、JSON 规模、脚本数与分类表、必过项数（当前 5 项） |
| `检查历史遗留.py` | 已清掉的东西不许回来：归档目录与禁用命名、文档里悬空的脚本引用、没有执行者的脚本、`game/` 里的自映射别名表、弃用的标准库 API |
| `检查规则层.py` | 效果之外的规则（`定义/规则层.json`）站不站得住：登记表自洽（含条件按原子能力契约校验、参数不许有死项、**条件不许为空**、行级载体必须真有技能行读它）、拦截点与实现双向不脱钩、每条规则都落进标准探针场景、**三种写法（`规则文本` / 被动技能行 / 状态定义）都渲染得出来**（第四种载体「参战者固有规则」
不挂卡、没有卡面，不参与渲染检查，由 `tests/test_inherent_rules.py` 负责）、内容只在引擎真会读的位置用规则、**卡面口径**（整段排在主动技能之前、一条一个 `•` 开头的行、非根载体的那份带尾注）、**种族登记表**（种族的天生锁定技：登记过、载体对、**有负面必配强正面**、基准族人族为空且六档全出现、两个种族不许长成同一副样子、**每个种族都要在敌方档次里出得来**）、**名额**（两本账：`名额` 是卡的发行量、`种族名额` 是种族的发行量，**卡与种族不共用闸门**，两笔用量每轮都打出来，超一个就红）（当前 7 项） |

## 规则与检查的落差

**这张表是本文档的重点。** 「审查全绿」只说明**已实现的那部分**成立；规范里
写了却没有对应检查的条款，破坏它不会有人报警。写这张表的直接起因：渲染器工作
里 `game/cmd` 直接导入了 `game.core.combat.card_text`，违反了「命令层不得导入核心
服务」，而 `check_core_internal_imports` 只扫 `game/core` 与 `game/features`
——**`game/cmd` 不在范围内**，所以长期无人发现。

### 各条判据（问过的口径，记下来免得再猜）

- **G6 随机**：禁止 `random` 模块的便捷函数（`random.choice()` / `random.random()` /
  `from random import choice`）。它们走全局无种子 RNG，同一次运行里先后顺序会互相影响。
  只允许 `random.Random(种子)` 实例。现状 0 处裸用、30 处带种子实例。
- **G7 评分**：**按名字判，不扫正文**。`generating` 里含 "rating"、五行相生的
  `root_score` 是战斗规则计算（读 `五行.json` 的基准值）——扫正文会把它们全误报。
  只查目录名、模块名与顶层函数名。
- **G8 战斗入口**：硬条件，不给例外。`BattleEngine` 只允许在 `game/core/combat/` 内被
  提到；`simulate_teams` 只允许出现在 `engine.py`（定义）与 `service.py`（唯一入口）。
  第二条尤其重要——它能抓出**战斗包内另起的第二个入口**，那是包外检查抓不到的。
- **G5 可变运行对象**：名单**从代码自动取**——各包运行期模块（`models`/`engine`/
  `runtime`/… 见 `INTERNAL_MODULES`）里**非 `frozen`** 的 dataclass。规范举的三个例子
  `Fighter` / `BattleContext` / `StatusState`，正是 `game/core/combat/models.py` 里
  非 frozen 的那批（共 9 个），所以口径完全对得上。只查 `contracts.py` 与包顶层
  `__init__.py` 的 `__all__`；`service.py` 内部构造 prepared 快照是正常的，不该拦。

  **必须全库取名单，不能按包取**：`features/chakan_wupin` 里一个运行期模块都没有，
  而它要防的 `Fighter` 住在 `game/core/combat`——按包取会把它整个跳过，检查看着
  通过、其实什么都没查。这个坑是反向验证抓出来的。

### 覆写既有允许清单时的要求

允许清单（如 `DIRECTORY_TRAVERSAL_ALLOWLIST`）每加一项都要写清**为什么它不算越界**，
并在本说明里留一句。当前两处目录遍历例外：`game/core/data/files.py`（唯一的正式
JSON 遍历者）、`game/cmd/后台/天道后台/media.py`（清的是控制台自己的
`/game-console/media/`，不是游戏数据）。

### 补检查时的要求

新增检查**必须做反向验证**：在干净数据上通过只说明它没误报，还要**临时造一处违规、
确认它报出文件与行号并非零退出**，再还原。否则可能写出一条永远通过的检查——
那和没有检查一样，却更让人放心。

已按这个要求验过的：`check_core_upward_dependency`（往 `game/core/pool/__init__.py`
末尾加一行导入 features，报出该行、退出 1）、`check_core_namespace`（往
- 检查**只做静态导入分析**，不看运行期反射或 `getattr` 拼出来的引用。
  `check_unreferenced_modules` 是唯一的例外：它另外认字符串字面量里的模块全名或
  文件名（动态装载与配置表走这条路），所以只会漏报、不会误伤活模块。
- `_imports` 不解析相对导入（`from .pool import X` 只给 `"pool"`），
  所以涉及相对导入的规则要自己走 AST（`check_core_namespace` 就是这么写的）。
  `check_unreferenced_modules` 用 `_resolve_from` 把相对导入解析成全名再比对，
  否则每个模块都会看着像孤儿。
