# 构筑模板化：设计说明与迁移方案

本文件记录「让功法 JSON 瘦下来、设计简单起来」这件事的**实测依据、已验证结论、
未决问题**。所有数字都是在本仓库 `data/` 上跑出来的，不是估计。

> **落地结果**（后续实现，与本文件的分析同期）：模板化已从功法扩到**六个面**——
> 构筑三段（功法 / 真意 / 器律）加上**战场环境 / 伤势 / 战丹**，共用一份联合模板库
> （见 `tools/构筑模板.py` 的 `SEGMENTS`：每个面配「目录 + 文件名模式 + 哪些位置算
> 匹配单位」）。
>
> 实测六个面 502,084 行 → **128,668 行**（省 373,416 行，74.4%）；
> 1,471 份模板覆盖 7,398 条效果，实际替换 7,398 条。
>
> | 面 | 基线行 | 现况行 | 省行 |
> | --- | --- | --- | --- |
> | 功法 | 349,275 | 80,464 | 268,811 |
> | 真意 | 98,361 | 23,250 | 75,111 |
> | 器律 | 10,426 | 2,623 | 7,803 |
> | 战场环境 | 14,172 | 7,388 | 6,784 |
> | 伤势 | 13,308 | 9,871 | 3,437 |
> | 战丹 | 16,542 | 5,072 | 11,470 |
>
> 匹配单位是**结构簇**而不是「一个动作序列一个模板」：同一动作序列下的实例字段集合
> 往往不同，按序列分组会让它们互相拖累、整组被放弃；按「**面** + 动作序列 + 标量叶子
> 位置表」分簇后各自成模板（`TEMPLATE_CLUSTERS`）。
>
> 排名**按面归一**（本簇收益 ÷ 该面平均簇节点数）：新面的效果是片段级，按绝对收益排名
> 会让靠前的名额被大量小片段占走，三段里本来成簇的大效果反而凑不成模板（实测三段覆盖
> 从 6,405 掉到 3,605）。归一之后三段一条都没退化（4,976 / 1,290 / 141）。
>
> 剩下 438 条的成因已经查清：合并基座对不齐的那些实例（`_stabilize` 会收敛到「同一
> 基座下都成立」的子集，不再有整簇被弃）。
>
> 落盘引用都能在装载期**逐字节还原**成原文（含键序，见 `templates.restore_reference`
> 与引用里的 `顺序` 键）。装载期展开的段名是**实体类别**：`战丹` 面对应的类别是
> `丹药`（`战场环境`/`伤势` 同名），漏一个段名那个面的监听就会全部报
> 「不是监听事件节点」（实测 148 条）。工作流与顺序见 `tools/构筑模板迁移.py`。

配套工具：`tools/构筑模板.py`（模板机制原型与回环验证，只读 `data/`）。

## 一、问题有多大（实测）

| 指标 | 实测值 |
| --- | --- |
| 功法 30 个文件的总行数 | **349,275 行** |
| 功法实体 | 600 门，编号 400001–400600 连续无空号 |
| 效果节点 | 244,224 个 |
| 顶层效果 | 5,188 个 |
| 效果的**动作序列原型** | **627 个** |
| 前 1 个原型 | 392 个实例，占 12.7% 节点 |
| 前 20 个原型 | 占 **47.2%** 节点 |
| 前 50 个原型 | 占 **65.2%** 节点 |

### 三个具体的「病」

**1. 一个语义量、多处声明。** 原型 1（「叠层 → 满层 → 引爆」）里，
状态名在一条效果内被写了 **5 遍**，每次都包一层
`{能力: 选择状态, 目标: {...}, 名称: ...}`。改一处漏一处就会变成「消耗 A、读 B」。

**2. `目标` 子对象重复 18,647 次**，其中 `{"能力":"选择目标","范围":"自身"}` 一种
占 **16,270 次（84%）**。

**3. 条件被建模成容器**，导致路径上出现 `效果 → 成立效果 → 尝试效果 → 效果` 这种
同名多层的结构。注意：实测容器节点只占 **5.5%**、连续嵌套最深 **2 层**，
所以**扁平化容器不是主要矛盾**，收益太小、动引擎核心，不建议做。

## 二、未采纳的两个方案（以及为什么）

### 「卡里省略目标 = 自身」——**已实测否决**

看起来最省：省略的默认值从「当前目标」改成「自身」，直接砍掉 16,270 个目标对象。

**但它会改变行为。** `_select_targets` 的调用点语义不同：多数传入的是出效果者自身，
但 `来源目标`/`接收目标`/`归属目标` 以及遍历选出的目标传的是别人的参战者。
实测把默认值改成「自身」后跑 1967 场语料对照：**1948 一致 / 19 差异**。

那 19 张卡是真实行为变化，不是等价重构。所以**缺省语义必须与原实现一致**，
「自身」只在显式写出时生效。

> 那 18% 的收益要用另一条路拿：把依赖旧默认值的节点**显式化**之后再改默认值。
> 这属于迁移阶段的事，需要先设计「哪些卡要改、改多少」。

### 「容器扁平化」——收益不足

见上，只占 5.5%，要改引擎条件分派，不划算。

### 已拿到手的 20%

`目标` 支持**字符串简写**（`"目标": "当前目标"` 等价于原来的对象写法）与
**省略**（语义保持原样）。这部分是纯新增能力，已实现并通过全量验证。

## 三、已实现并验证的东西

### 1. 引擎：目标双格式（`game/core/combat/mechanics.py`）

`_select_targets` 现在接受三种写法：

```jsonc
// 省略 —— 与原实现语义一致（当前目标）
{ "能力": "添加状态", "状态": {...} }

// 字符串简写 —— 纯新增
{ "能力": "修改技能", "目标": "当前目标" }

// 原对象写法 —— 不变
{ "能力": "添加状态", "目标": {"能力": "选择目标", "范围": "自身"}, ... }
```

配套常量：`TARGET_SCOPES`（14 个范围名）、`DEFAULT_TARGET_SCOPE`、`TARGET_SELECTOR_ABILITY`。

**验证结果：**

| 对照 | 结果 |
| --- | --- |
| 语料对照 1967 场 | **一致 1967 · 差异 0 · 失败 0** |
| 渲染正文对照 2442 条 | **一致 2442 · 差异 0** |
| `tools/全量核对.py` | **14 项全部通过** |

### 2. 模板机制（`tools/构筑模板.py`）

模板 = 一棵树，把「随卡变化的位置」标成占位符；参数绑定把真实实例读成一组实参；
展开把模板 + 实参还原成完整树。工具做**双向回环验证**：
实例 → 反推实参 → 展开 → 与原实例**逐字节比对**。

**原型 1 的验证结果：392/392 一致。**

机械推导出的参数（**不是我按语义猜的**，是从「取值签名」自动归并的）：

| 参数 | 绑定位置数 | 说明 |
| --- | --- | --- |
| 参数3（状态名） | **4 处** | 同一个名字的 4 遍重复被压成 1 个 |
| 参数2（层数） | **3 处** | 同上 |
| 参数8（阈值） | 1 处 | 取值只有 `2`/`3` |
| 参数10（每轮上限） | 1 处 | 取值 3 种，**可选**（12 个实例没有） |
| 参数5（读值上限） | 1 处 | 取值 4 种，**可选**（21 个实例没有） |
| 其余 5 个 | 各 1 处 | 事件、引爆名、伤害名、百分比等 |

### 3. 一个必须记住的实测结论：**同一原型内部并非完全同构**

原型 1 的 392 个实例有 **4 种字段集合**：

| 路径数 | 实例数 | 差异 |
| --- | --- | --- |
| 54 | 224 | 完整 |
| 53 | 147 | 少 `每次行动最多触发` |
| 52 | 12 | 少 `数值/最高值` |
| 51 | 9 | 两者都少 |

所以模板机制**必须支持可选参数**：实例里没有该路径时，展开就把那个键**删掉**，
而不是填个默认值。原型里已实现（`_ABSENT`）。

### 4. 另一个实测结论：**同名符号不等于同一个参数**

`名称` 与 `数值/状态` 看着像同一个东西，实测是**两个不同的值**
（如 `雷丹养元` vs `雷丹灵印`）。所以参数归属只能由数据定，不能按字段名猜。
工具现在的做法是：把每个变化位置写成「在每个实例上的取值向量」，向量相同才归为一组。

反过来也要注意：**「状态载体名」（4 处）与「读取来源名」（1 处）在某张卡上恰好同值**，
但向量不同，必须保持两个参数——并了别的卡就还原不出来。所以工具保守地拆开是对的。

### 5. 迁移覆盖实测（`tools/构筑模板迁移.py --覆盖`）

| 排名 | 实例 | 节点占比 | 单模板可还原 | 参数数 |
| --- | --- | --- | --- | --- |
| 1 | 392 | 12.7% | 是 | 10 |
| 2 | 372 | 11.1% | 是 | 11 |
| 3 | 268 | 8.7% | 是 | 8 |
| 4 | 259 | 7.7% | 是 | 7 |
| 5 | 58 | 1.6% | **多形态** | 16 |
| 6 | 64 | 1.2% | 是 | 11 |
| 7 | 37 | 1.1% | **多形态** | 13 |
| 8–12 | — | 各约 1.0% | 是 | 4–11 |

**前 12 个原型覆盖 49.2% 的效果节点**，其中 **10 个**单模板即可精确还原。

### 6. 一个已知局限：多形态原型

排名 5 与 7 的原型里，**没有任何一个实例同时带有全部参数位置**，
所以单模板装不下它们，需要「多形态模板」（一个原型下挂几个形态，按实例选）。
工具遇到这种原型会标注 `多形态` 并继续，**不会假装通过**。
比例不大（前 12 个里 2 个），可以留到第二阶段处理。

## 四、还没做、需要决定的事

### 决定 1：模板住在哪、卡里存什么

三个选项，收益与风险差别很大：

| 方案 | `data/` 是否变短 | 需要改引擎 | 风险 |
| --- | --- | --- | --- |
| A. 只用模板生成，`data/` 仍存展开后的树 | **否** | 否 | 零 |
| B. 卡里存模板引用（按编号），加载期展开 | **是** | 是 | 中 |
| C. 模板写进代码，JSON 只留参数 | 是 | 是 | 高，违背「JSON 是唯一主体」 |

**我的建议是 B**，理由是 A 解决不了「`data/` 又多又深」这个原始诉求，而 C 破坏架构原则。
B 还能顺带消掉「同一个名字写 5 遍」的隐患。

若选 B，模板应当是**带编号的正式实体**（与功法、状态同级的编号机制），
而不是按名字查找——按名字查找会引入重名与「改一处漏一处」的脆弱点。

### 决定 2：迁移范围与批次

- 先做**原型 1**（392 个实例、42,336 行）作为试点，还是先做前 5 个？
- 其余 626 个原型里，哪些值得建模板？前 20 个覆盖 47% 节点，前 50 个覆盖 65%。
  建议**按节点权重排序，做到收益明显下降为止**，不要追求全覆盖。
- 迁移后 `tools/基准/` 里的七条摘要基准要重新取（改数据必然改摘要），
  但**真实对局行为必须保持一致**——这条可以用语料对照卡住。

### 决定 3：那 18% 怎么拿

「省略 = 自身」需要先把依赖旧默认值的节点显式化。需要先做一个**全库扫描**，
列出哪些节点的省略目标依赖调用点语义，评估迁移量之后才能决定值不值得。

### 迁移过程中踩到并且已修掉的三类坑

1. **共享可变状态**：展开若发生在解析期（`parse_node` 原地改字典），
   校验与解析共用同一份实体对象，一处展开会污染另一处——实测 516 场对局漂移。
   修法：展开提前到**装载期**，在快照冻结之前完成（`GameDataLoader.load(expand)`）。
2. **工具绕过快照**：渲染正文、构筑形状、机械化盘点、单元测试都是**直接读 JSON 文件**，
   不经过快照，于是看到没有 `能力` 字段的引用节点。
   修法：`tools/构筑模板展开.py` 提供统一展开入口，这四个读取方接上它。
3. **键序**：模板主体以某个实例为基底，别的实例多出来的键由展开补在末尾，键序与原卡不同。
   键序不影响引擎语义，但**影响卡面正文**（`攻击+15、速度+12` 会变成 `速度+12、攻击+15`）。
   修法：模板主体的键序取「全部实例键序的超序列」（`构筑模板._union_order`），
   迁移时再按原卡逐条重排并做**键序敏感**的逐字节校验。

### 一件需要知情的事

迁移让 **4 条卡面正文的属性书写顺序**发生变化（2442 条中 4 条）。

## 七、机制翻译表服务谁（一处已修正的误判）

一开始我把机制翻译接成了 `catalog.template_label()` 供渲染用。**这是错的**，两个理由：

1. **玩家侧不需要它。** 「查看」的规则正文是**从展开后的能力树现算**的
   （见 `game/cmd/通用/查看/items.py` 的 `_build_description_lines`），已经是一整段
   中文；`说明` 只存卡头风味引言。再叠一个机制名没有信息增量。
2. **它根本到不了渲染层。** 引用在装载期就被展开替换掉了，模板 ID 那时已经不在了。

所以删掉死接口，让翻译表服务**真正读得懂它的人：直接打开 `data/` 文件的人**。
打开一张卡只看到 `{"模板": "430001"}` 时，机制名就是「这条在做什么」的答案。

现在它有四个明确用处，且**都进判据**（`tools/架构审查/检查构筑模板.py`）：

| 用处 | 判据 |
| --- | --- |
| 工具按 ID 查机制名（`构筑模板展开.template_name`） | 前 50 条必须能解析，否则报「翻译无法被工具解析」 |
| 描述一张卡的模板引用（`describe_reference`） | 同上 |
| 生成模块里的副本与 JSON 一致 | 逐条比对名称，漂移即失败 |
| 数据集的形状校验（`foundation._validate_template_translations`） | ID 必须 43 开头六位、名称非空 |

**「能被解析」这一条是专门加的**：防止翻译表再次退化成没人读的死数据。

### 模板文件长这样（原型 1，节选）

```jsonc
{
  "编号": "430001",              // 43 段，紧接真意 41 / 气机 42 之后
  "名称": "构筑模板-1",
  "覆盖实例数": 392,
  "参数": {
    "状态载体名": [              // 一个参数绑定 4 个位置 —— 那 5 遍重复被压成 1 个
      "/效果/[0]/成立效果/[0]/失败效果/[0]/状态/名称",
      "/效果/[0]/成立效果/[0]/尝试效果/[0]/效果/[1]/状态/名称",
      "/效果/[0]/成立效果/[0]/成功效果/[0]/状态/名称",
      "/效果/[0]/条件/[0]/左值/状态"
    ],
    "消耗层数": [ /* 3 个位置 */ ],
    "触发阈值": [ /* 唯一取值 2/3 */ ]
  },
  "主体": { /* 一棵带 {"$参数": 名字} 占位符的能力树 */ }
}
```

**205 行的模板，代表 392 个实例、42,336 行。** 前提是卡里改成存引用（决定 1）。

### 一个必须记住的点：校验的是**展开后**的结果

不能直接校验模板本体：参数位置是 `{"$参数": …}` 占位符，而像 `左值.状态` 这种位置
要求字符串，占位符必然过不了。`构筑模板生成.py` 的做法是先用一组真实实参展开，
再拿战斗核心自己的 `RuleSchemaValidator` 校验展开结果——这才对应
「模板能不能生成出合法游戏数据」这个真问题。
