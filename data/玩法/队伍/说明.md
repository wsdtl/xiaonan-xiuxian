# 队伍数据包

## 功能

### 一、启动期把规则读死

1. **依赖必须先就绪**：队伍核心初始化时依次要求 JSON 数据、核心数据库、人物状态三个核心已就绪，任一未就绪就抛「必须先于队伍核心启动」。
2. **规则硬校验**：`队伍规则` 必须含「队伍」对象，且 `人数` 的 `允许单人队伍` 必须为 true，`最多玩家`、`邀请` 的 `有效秒数` 必须是正整数（3 与 600）；不满足直接拒绝启动，其余项按 `玩家状态` 读成 `未组队` 520007、`组队中` 520008、`队伍编号字段` 队伍编号、`身份字段` 身份、`队长` 队长、`队员` 队员（`规则/队伍.json`）。
3. **玩法层依赖**：队伍玩法初始化要求队伍核心已初始化，否则抛「队伍核心必须先于队伍玩法启动」，随后装载展示数据；按钮页面只能是「未组队 / 待处理邀请 / 队长 / 队员」，按钮编号不得重复；展示文本必须恰好含 图标 / 格式 / 查看 / 结果 / 错误 五分区。

### 二、成员关系与状态槽

4. **关系解析**：读人物状态的「队伍」槽，槽值为 `未组队` 时返回空，既不是 `未组队` 也不是 `组队中` 就抛状态非法。
5. **身份一致性再校验**：按槽里的 `队伍编号` 读队伍快照，要求快照里确实含该用户；再要求槽里的 `身份` 与快照队长推出的一致，不一致抛身份不一致错误。
6. **快照自校验**：要求成员名单非空、第一名必须就是队长、成员不得重复，且人数不得超过 `最多玩家` 3，越界判快照溢出（`规则/队伍.json`）。
7. **队伍编号确定性**：首次邀请时按邀请者与请求编号推出队伍编号，同一请求必得同一编号。
8. **队伍槽只写两个字段**：切到 `组队中` 时上下文只写 `队伍编号` 与 `身份`；退回 `未组队` 时上下文置空（`规则/队伍.json`）。

### 三、邀请、接受与拒绝

9. **邀请入参校验**：先按「自主空闲或休息」校验邀请者状态（不通过抛「当前忙碌」），再解析目标（目标忙抛「目标忙碌」）；邀请者等于目标抛「不能邀请自己」；目标已组队抛「目标已经组队」。
10. **目标解析只认同处**：先取邻近玩家，只保留坐标与本人相同的候选，先按用户编号精确匹配，再按姓名匹配；姓名匹配到多个抛「目标不唯一」，一个都没有抛「目标不存在」，空查询抛「缺少目标」。
11. **队长与容量校验**：邀请者是队员时抛「不是队长」；队伍人数已达 `最多玩家` 3 抛「队伍已满」（`规则/队伍.json`）。
12. **待处理邀请查重**：读目标已有的邀请快照，若未过期且对应队伍仍存在就抛「已有邀请」，过期或队伍已消失则允许覆盖写入。
13. **邀请同事务**：首次邀请用一笔「队伍邀请」提交同时放入新建的队伍快照、邀请者切到 `组队中`、目标写入邀请快照（含 邀请者 / 目标 / 队伍编号 / 到期时间 = 现在 + 600 秒）（`规则/队伍.json`）。
14. **接受前置校验**：玩法层先要求接受者状态可变更，取得未过期邀请（没有邀请抛「没有邀请」、已过期抛「邀请失效」），再要求接受者与邀请者的（空间类型、空间编号、坐标）三元组全同，不同则抛「不在同处」。
15. **接受时的冲突分支**：没有邀请快照抛「没有邀请」；已过期或队伍已消失则先提交一笔「清理失效队伍邀请」把邀请置空、再抛「邀请失效」；接受者已组队抛「已经组队」；邀请者已不是队长抛「邀请失效」；队伍已满抛「队伍已满」。
16. **接受同事务**：队伍快照追加成员并版本加一、接受者切到 `组队中` 且 `身份` 为「队员」、邀请快照置空，三者在同一笔「接受队伍邀请」提交里。
17. **拒绝允许过期**：拒绝不校验状态守卫，读不到邀请快照抛「没有邀请」，写入则把邀请置空，返回邀请者编号。

### 四、离开、请离、移交与解散

18. **离开按规则折叠**：离开队伍后若只剩一人且 `只剩一人时解散` 为 true，则整队解散并让剩余成员一并退回 `未组队`；若一人不剩则只清队伍与本人槽位；否则排队并可能顺位移交队长（`规则/队伍.json`）。
19. **顺位移交**：离开者正是队长时，新队长取剩余名单中的第一位，同时把新队长的队伍槽上下文改写成 `队长`（`规则/队伍.json`）。
20. **请离校验**：操作者必须是队长（否则抛「不是队长」），目标不能是队长（否则抛「不能操作队长」），目标必须在成员名单里（否则抛「目标不是成员」）。
21. **移交校验与落点**：操作者必须是队长，目标不能是自己（否则抛「不能移交自己」）、必须在名单里（否则抛「目标不是成员」）；同一笔「移交队长」提交里写回队伍快照、原队长槽改为「队员」、新队长槽改为「队长」，并把新队长移到名单首位。
22. **解散同事务**：必须是队长；一笔「解散队伍」提交里把队伍快照置空，并把名单上每个人的队伍槽逐个退回 `未组队`。
23. **冲突统一收敛**：所有提交捕获状态版本冲突与人物状态冲突，统一转成「队伍变化」冲突码。

### 五、校验、公开与编排

24. **目标必须是队内成员**：要求操作者已组队（否则抛「未组队」），先按用户编号精确匹配成员，再按姓名匹配，匹配不到抛「目标不是成员」、匹配多个抛「目标不唯一」。
25. **资料条数不一致即判队伍变化**：读取成员公开资料时，返回条数与请求条数不等就抛「队伍变化」，防止名单在读取间隙被改写。
26. **附近公开只暴露两项**：附近公开输出「是否组队」与「队伍人数」两项，是否组队还要 `附近公开` 的 `显示组队状态` 为 true 且队伍快照仍存在，人数只在 `显示玩家人数` 为 true 时给出，否则为 0（`规则/队伍.json`）。
27. **行动参与者与越权**：没有组队时返回本人一人；组队时身份不是队长就报出「成员不能发起」（玩法层转成「只有队长可以带队执行该行动」），是队长则返回整份成员名单作为行动参与者。
28. **跨行动编排**：行动编排核心同时读队伍与宗门同行，两者并存时直接拒绝；有宗门同行时只有领队能发起，否则按队伍名单或单人名单给出参与者。
29. **邀请按钮隐藏**：队伍页动作按页面取按钮，当成员人数已达 `最多玩家` 3 时把带邀请含义的动作全部滤掉。
30. **操作返回新页**：邀请 / 接受 / 拒绝 / 离开 / 请离 / 移交 / 解散七个入口统一返回「结果 + 操作后重新渲染的页面」，页面再交给展示层处理。
