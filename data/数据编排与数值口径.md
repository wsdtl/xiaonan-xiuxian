# JSON 数据编排与数值口径

## 总原则

JSON 是游戏设计契约，代码只负责读取、索引、校验和执行。文件名表达分类，根节点直接表达文件内容；不要为文件名已经表达的类别再包一层同名键。

正式运行只读取 `data/基础/读取规则.json` 注册的数据。`tools` 可以读取全部正式 JSON 做校核、评分、平衡和生成，但游戏进程不得反向依赖 `tools`。

## 四层语义分类

正式数据按**大类 → 组件 → 四层语义**组织：`data/<大类>/<组件>/{定义,规则,内容,展示}`，
组件名与大类同名时省略组件那一段（`data/战斗/内容/…`）。同一业务的数据集中在自己的组件包内，
不再跨顶层目录寻找；每个组件包用 `组件.json` 声明本包的数据集、路径、结构和实体类别，
全局只由 `data/基础/读取规则.json` 登记**组件相对路径**与编号定义。

四层只表达包内语义，既不是顶层目录，也不是大类目录：

- `<组件>/定义`：编号、品级、属性、资源、事件、原子能力和读取结构。
- `<组件>/规则`：跨实体的初始化、成长、战斗、炼药、炼器、阵法和行路计算。
- `<组件>/内容`：实际实体和池。实体保存稳定编号，池保存编号或文件名引用。
- `<组件>/展示`：战报、行程等面向输出的结构和模板。

只建立需要的子目录，不为凑齐四层创建空壳。大类表达业务归属，组件目录不要求与代码服务一一对应：
世界包中的敌人由敌人核心解释，炼器包的器律由战斗核心执行最终能力。

数据库只保存编号、实例状态、玩家进度和结算结果，不复制 JSON 正文。修改 JSON 后重启服务，重新建立不可变数据快照。

## 编排规则

1. 一组同构实体使用“列表中的字典”；不再使用无意义的实体名键包裹列表。
2. 单一规则或单一对象直接使用字典；简单枚举和池使用字符串列表。
3. 跨文件引用只保存稳定编号、品级编号、池文件名或定义注册名，不复制被引用实体。
4. 编号是持久化主键，名称只用于展示；改名不改编号。
5. `权重`只控制逆权重随机抽取，单个候选的抽取量与 `1 / 权重` 成正比；数值越小越容易抽中，数值越大越难抽中。它不是评分、强度或稀有度标签。
6. `参考价`只作为当前项目统一货币单位下的静态估值锚，不能被战斗、评分或随机逻辑隐式使用；成交价由未来经济服务叠加供需和税率。
7. 品级独立保存为两位编号，能力倍率和价格系数由 `data/基础/定义/品级.json` 统一解释；不要把品级塞进实体主编号。
8. 功法、真意、气机、器律、丹药和阵法各自保持独立方向；跨方向只通过明确的编号引用连接。

## 数值口径

- 定义层默认值回答“没有任何角色覆盖时是多少”。
- 角色主体的属性覆盖回答“新建该类角色时是多少”。
- 成长规则回答“等级或境界变化增加多少”。
- 内容实体的 `参考价` 回答“当前经济系统的基准报价是多少”。当前 941 件物品（灵植 108 + 灵矿 108 + 兽宝 366 + 丹药 359，逐件都带 `参考价`）实体之间保持本项目原有相对价差。
- 角色与武器经验使用 1 至 40 级幂次基础曲线和 41 至 99 级后段放大曲线；服务必须执行 JSON，不得在代码另存默认公式。
- 敌人 JSON 保存最终可结算的灵石、人物经验和本命武器经验范围；玩法规则只处理玩家与敌人等级差带来的修正。
- 同名字段只有在语义、单位和结算层级都一致时才可从外部版本对齐；没有对应对象时保留当前设计，并以正式 JSON 为准。

## 服务边界

命令层只触发；玩法层组织玩法事务；核心层只放已经成立的跨玩法公共服务。数据、战斗、资源池、世界、角色、资产、炼药、炼器、阵法、队伍与宗门等核心服务均已按正式 JSON 契约运行。跨服务只调用对方包顶层公开的契约接口，不能导入另一服务的内部模型或 JSON 结构。

JSON 加载服务是所有服务的数据入口：启动时读取规则、解析四层目录、建立编号和池索引、校验重复与循环引用，然后向其他服务提供只读快照。业务服务不能自行扫描 `data`。

## 变更流程

1. 判断改动所属目录和数据集。
2. 更新 JSON 后运行 Prettier 默认格式化。
3. 检查所有编号、品级、池引用和读取规则匹配关系。
4. 运行全量 JSON 初始化、编译和已有领域验收；新测试只能在对应主体 JSON 审查完成后建立。
5. 价格、评分、平衡和生成只在 `tools` 运行并输出报告，不把维护结果写成游戏运行时依赖。
