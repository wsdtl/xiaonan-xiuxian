# 宗门数据包

本包按组件维护数据，文件归属由 [组件.json](组件.json) 声明。数据集名是公共读取契约；编号、池文件名不随目录变化。

## 功能

### 一、启动契约与宗门本体
1. **启动依赖**：`SectService.initialize()` 只要求 JSON 数据与核心数据库先就绪（否则抛「必须先于宗门核心启动」）；`SectAssetService` 额外要求先天灵宝核心已启动；`SectProductionService` 只要求数据已加载。（`game/core/sect/service.py`、`game/core/sect_assets/service.py`、`game/core/sect_production/service.py`）
2. **身份三值定死**：初始化读 `名称`/`创建`/`同行`/`邀请`/`身份` 五段规则，要求 `新入宗门` 必须等于 `弟子`、`宗主转让后` 必须等于 `长老`，且 `宗主`/`长老`/`弟子` 三个字符串互不相同，否则拒绝启动；`宗主` 与 `长老` 合成 `_officer_roles` 供后续权限判断。（`规则/宗门.json`、`game/core/sect/service.py`）
3. **名称入参校验**：`_validate_name` 要求长度落在 `最短长度` 2 到 `最长长度` 12 之间，并且 `re.fullmatch` 命中 `匹配` 正则，否则抛 `name_invalid`。（`规则/宗门.json`、`game/core/sect/service.py`）
4. **创建宗门四道闸**：`create()` 依次做「按 `创建.状态守卫` 调 `PlayerStateService.authorize`，不通过抛 `actor_busy`」→「已有宗门成员关系抛 `already_member`」→「`get_shared_entity_by_name` 重名抛 `name_occupied`」→「`shared_location_at(入口坐标)` 被占抛 `entrance_occupied`」。（`规则/宗门.json`、`game/core/sect/service.py`）
5. **创建落三个共享记录**：`宗门编号` 由 `sect:<user>:<request>` 派生、`洞天编号` 由 `cave:<sect_id>:<名称>` 派生；同一事务写 `SharedEntityMutation`（含 `名称`/`宗主`/`洞天编号`/`入口坐标`/`成员数量` 1）、`SharedMemberMutation`（角色 `宗主`、`join_order` 1）、`SharedLocationMutation`（入口坐标）；数据库唯一约束冲突按错误文本回译成 `name_occupied` 或 `entrance_occupied`。（`规则/宗门.json`、`game/core/sect/service.py`）
6. **邀请前置**：`invite()` 禁止自邀（`cannot_invite_self`），邀请者必须是本宗成员（`not_member`）且身份属于 `宗主`/`长老`（`not_officer`），目标不能已是成员（`target_already_member`），目标已有未过期邀请抛 `pending_invitation_exists`；到期时间 = 当前时间 + `邀请.有效秒数` 600。（`规则/宗门.json`、`game/core/sect/service.py`）
7. **接受邀请**：`accept()` 先取待处理邀请（无则 `invitation_missing`），`到期时间 <= 现在` 抛 `invitation_expired`，宗门已不存在同样抛过期；同一事务写「宗门实体（成员数量 +1，带版本）」+「成员记录（角色 `弟子`、`join_order` = 现有成员数 + 1）」+「把邀请状态置空（带邀请版本）」。（`规则/宗门.json`、`game/core/sect/service.py`）
8. **加入顺序**：成员顺序由 `成员.加入顺序` 声明为 `接受邀请顺序`，代码用「当前成员数 + 1」当 `join_order`，并不重排既有成员。（`规则/宗门.json`、`game/core/sect/service.py`）
9. **退出与逐出**：`leave()` 要求不是 `宗主`（否则 `leader_cannot_leave`），呼应规则 `退出.宗主必须先转让或解散`；`kick()` 要求执行者是 `宗主` 或 `长老`，目标必须同宗（`target_not_member`），不能踢 `宗主`（`cannot_remove_leader`），也不能直接踢 `长老`（`elder_must_be_removed_first`）。（`规则/宗门.json`、`game/core/sect/service.py`）
10. **成员删除事务**：`_commit_member_delete` 在同一事务里写「宗门实体（`成员数量` = 原成员数 - 1）」+「把该成员的成员记录清空」；若此人正在宗门同行中，再追加「同行实体去掉该成员」与「同行成员记录清空」两条操作。（`game/core/sect/service.py`）
11. **任命与罢免**：`appoint_elder` / `remove_elder` 只有 `宗主` 能调（`not_leader`），前者要求目标当前是 `弟子`（`target_not_disciple`），后者要求目标是 `长老`（`target_not_elder`）；二者都通过 `_change_role` 只改成员记录的角色字段，保留原 `join_order`，并用 `receipt.replayed` 决定返回版本是否 +1。（`规则/宗门.json`、`game/core/sect/service.py`）
12. **转让宗主**：`transfer()` 要求执行者是 `宗主`、目标不是自己（`cannot_transfer_self`）且是同宗成员；同一事务写「宗门实体 `宗主` 改成目标」+「原宗主降为 `长老`」+「目标升为 `宗主`」，并顺带执行同行解散操作；转让后强制 `解散本次同行`。（`规则/宗门.json`、`game/core/sect/service.py`）
13. **解散宗门**：`disband()` 要求执行者是 `宗主`；先检查 `宗门灵藏` 与 `宗门万珍殿` 的 `灵石` 与 `条目` 是否都为空，非空抛 `storage_not_empty`（对应 `解散.非空` 为 `禁止`）；随后同一事务清空宗门实体、宗门位置、全部成员记录、`宗门灵脉`/`宗门灵田` 两条生产记录以及同行记录。（`规则/灵藏.json`、`规则/万珍殿.json`、`game/core/sect/service.py`）
14. **同坐标检查在玩法层**：核心服务不比对坐标，`game/features/zongmen/service.py` 的 `_require_same_location_target` 按 `空间类型 + 空间编号 + 坐标` 三元组比对，不符抛 `not_same_location`，对应 `邀请.要求同一坐标` 与 `创建.入口来源` 的落地。（`规则/宗门.json`、`game/features/zongmen/service.py`）

### 二、宗门贡献与等级
15. **贡献参数装载**：`SectAssetService.initialize` 从 `宗门.贡献.来源.灵石` 读 `每份灵石` 100 与 `贡献` 1，从 `基础材料` 读 `计价字段`（`参考价`）、`贡献除数` 100；`使用品级价格系数` 必须为 true、`取整` 必须为 `向下取整`、`类别` 必须恰好等于灵藏的 `灵植`/`灵矿`/`兽宝`，任一不符拒绝启动。（`规则/宗门.json`、`game/core/sect_assets/service.py`）
16. **捐灵石换贡献**：`donate_stones()` 数量必须正整数，基础贡献 = `(数量 // 每份灵石 100) × 贡献 1`，再走先天灵宝的「宗门贡献入账」加成；同一事务写「人物灵石扣减 + 贡献增加」与「宗门灵藏灵石增加」两条。（`规则/宗门.json`、`game/core/sect_assets/service.py`）
17. **捐材料换贡献**：`donate_material()` 先按灵藏 `基础材料.类别` 校验类别（`_required_category`），再用 `entity_record("基础物品", 编号).number_category` 复核该物品真属于这个类别，品级经 `AssetService.grade()` 解析；贡献 = `floor(参考价 × 品级价格系数 / 贡献除数 100) × 数量`（先对单份向下取整再乘数量），`参考价` 缺失或非数值报「物品缺少有效参考价」，同一事务写个人扣减、灵藏增加、人物贡献增加。（`规则/灵藏.json`、`game/core/sect_assets/service.py`）
18. **等级不落库**：`SectProgressService` 明示不保存宗门等级，`snapshot()` 每次都现场汇总本宗全部成员的 `宗门贡献`（`CharacterService.contributions`）求和后落档。（`game/core/sect_progress/service.py`）
19. **阈值与增益静态校验**：`阈值` 必须从 0 开始、长度必须等于 `最高等级` 20、必须严格递增；三张增益表长度必须等于 20，`生产数量倍率` 与 `采集数量倍率` 必须递增、`炼制灵石消耗倍率` 必须递减，数值必须有限且大于 0，否则拒绝启动。（`规则/宗门.json`、`game/core/sect_progress/service.py`）
20. **等级落档**：`snapshot()` 从 0 号阈值起逐档比较，`总贡献 >= 阈值` 就抬一级、遇到第一个不满足即停，返回等级 = 下标 + 1；`next_threshold` 在满级时为 `None`。（`规则/宗门.json`、`game/core/sect_progress/service.py`）
21. **增益取值**：三张表各按等级下标取一项，随快照一起返回 `生产数量倍率`（1.0→1.19）、`采集数量倍率`（1.0→1.095）、`炼制灵石消耗倍率`（1.0→0.905）；生产端只把 `生产数量倍率` 用在数量上。（`规则/宗门.json`、`规则/生产.json`、`game/core/sect_progress/service.py`、`game/core/sect_production/service.py`）

### 三、宗门同行与山门
22. **召集同行**：`assemble()` 要求执行者是 `宗主`（`not_leader`），已有同行且宗主不是自己抛 `sect_changed`，宗主再次召集直接返回现状（幂等）；同一事务写同行实体（`名称`、`宗门编号`、`宗主`、成员列表、`成员数量` 1）与宗主的同行成员记录。（`规则/宗门.json`、`game/core/sect/service.py`）
23. **加入同行**：`join_follow()` 中宗主等价于召集；其他成员已在同行里直接返回；未召集抛 `follow_not_started`；`len(成员) >= 成员上限 15` 抛 `follow_full`；否则追加到成员列表末尾（对应 `成员顺序` 为 `加入同行顺序`、`宗主固定首位`）。（`规则/宗门.json`、`game/core/sect/service.py`）
24. **离开与请离**：`leave_follow()` 要求当前在同行（`not_following`）且不是宗主（`follow_leader_cannot_leave`）；`kick_follow()` 只有 `宗主` 能调，目标必须在同一同行且不能是宗主；`disband_follow()` 由宗主清空同行实体与全部同行成员记录。（`规则/宗门.json`、`game/core/sect/service.py`）
25. **同行玩法层的准入**：`game/features/zongmen_tongxing/service.py` 在调核心前先做 `自主空闲或休息` 状态守卫（不通过抛 `actor_busy`）、拒绝已有队伍的人（`fellowship_conflict`），加入时还要求与宗主同空间同坐标（`not_same_location`）。（`规则/宗门.json`、`game/features/zongmen_tongxing/service.py`）
26. **同行与队伍的互斥**：`规则/宗门.json` 把 `共同玩法` 列为 `行路`/`探险`/`闭关`/`采药`/`采矿`；代码侧由 `ActionGroupService` 按队伍与宗门同行两条来源解析出唯一行动组，同行成员必须一同进出。（`规则/宗门.json`、`规则/山门.json`、`game/core/action_group/service.py`）
27. **山门进出**：`山门.json` 的 `进入` 要求 `本宗成员`、位置取 `本宗山门入口`、同行取 `当前有效行动组`、`外宗成员` 为 `禁止整体进入`，状态守卫 `自主空闲或休息`；`离开` 从 `宗门洞天` 返回 `本宗山门入口`；两处都由 `game/features/zongmen_shanmen/service.py` 落到 `LocationService` 的洞天进出事务。（`规则/山门.json`、`game/features/zongmen_shanmen/service.py`、`game/core/location/service.py`）
28. **空间隔离的执行点**：洞天内 `附近修士` 只读同一空间、`附近地点` 不读地表地点、`行路` 被禁止；对应实现分散在 `game/features/xinglu/service.py`（报「当前身处宗门洞天，必须先出山门才能行路」）、`game/core/gathering/service.py`、`game/core/retreat/service.py`、`game/core/exploration/service.py`、`game/core/raid/service.py` 各自拒绝对应玩法；`山门.json` 的 `进入`/`离开`/`空间隔离` 三段字段本身没有读取点，核心只取 `空间类型` 一个值，其余条件由 `GateFeature` 的逐人同宗校验（`external_member`）、地表入口坐标比对（`not_at_gate`）、状态守卫（`current_busy`）与洞天判定（`not_in_cave`）硬编码实现。（`规则/山门.json`）
29. **设施只认本宗洞天**：灵藏、万珍殿、藏经阁、宗门生产与宗门设施在各自服务里都比对 `location.space_type == "宗门洞天"` 且 `space_id == sect.cave_id`，否则报「只有身处本宗洞天时才能使用…」。（`规则/灵藏.json`、`规则/万珍殿.json`、`规则/藏经阁.json`、`规则/生产.json`、`game/features/zongmen_lingcang/service.py`、`game/features/zongmen_wanzhen/service.py`、`game/features/zongmen_cangjing/service.py`、`game/core/sect_production/service.py`、`game/core/sect_facilities/service.py`）

### 四、灵藏、万珍殿与藏经阁
30. **灵藏装载校验**：`基础材料.类别` 必须恰好是 `("灵植", "灵矿", "兽宝")`，`万珍殿.成品类别` 必须恰好是 `("丹药", "真意", "气机", "器律", "阵法")`，两处 `每页上限` 都是 50，不符即拒绝启动。（`规则/灵藏.json`、`规则/万珍殿.json`、`game/core/sect_assets/service.py`）
31. **存入路径**：基础材料按 `编号 + 品级` 堆叠、数量正整数；灵石以 `宗门公共余额` 存储、不带品级、数量非负整数；两者都要求 `本宗成员` 与 `自主空闲或休息`。（`规则/灵藏.json`、`game/core/sect_assets/service.py`）
32. **取出被禁止**：`灵藏.取出.允许` 为 false，万珍殿同样 `取出.允许` 为 false 且 `方式` 只有 `发放`；`has_assets` 供解散前的非空检查使用（`灵石 > 0` 或 `条目` 非空即视为非空）。（`规则/灵藏.json`、`规则/万珍殿.json`、`game/core/sect_assets/service.py`）
33. **万珍殿发放**：`grant_product()` 的执行者限 `宗主`/`长老`（`发放.执行者`），目标必须是本宗成员，按 `原子转移` 一次事务把成品从万珍殿转出并按 `目标去向` 落点——`丹药`→纳戒、`真意`/`气机`→修行资粮、`器律`→器藏、`阵法`→阵藏。（`规则/万珍殿.json`、`game/core/sect_assets/service.py`）
34. **阵法两种存储**：黄/玄/地/天四品按 `阵法编号 + 品级` 堆叠；圣品为 `独立实例`、不堆叠、`一次性`，必填 `阵法实例编号`/`阵法编号`/`品级`/`实际投入`（投入类别限 `灵植`/`灵矿`/`兽宝`），且 `持久化计算值` 为空数组。落入仓库时堆叠键由代码拼成 `类别:编号:品级[:圣品实例键]`，与 `堆叠判同` 字段本身无关，条目正文固定为 `类别`/`编号`/`名称`/`品级`/`数量`/`实际投入`。（`规则/万珍殿.json`、`game/core/sect_assets/service.py`）
35. **藏经阁装载校验**：`来源.类别` 必须是 `功法` 且 `同编号处理` 必须是 `取最高品级`；`借阅.所有权` 必须是 `不转移`、`离开藏经阁` 必须是 `保持生效`，否则拒绝启动。（`规则/藏经阁.json`、`game/core/sect_library/service.py`）
36. **书目来源**：`_techniques` 遍历本宗全部成员的 `cultivation_library` 个人道藏快照，按 `编号` 聚合，只保留 `AssetService.grade().order` 更高的那一份品级（同编号取最高品级），并要求每条道藏实例的 `编号` 与 `品级` 都不为空。（`规则/藏经阁.json`、`game/core/sect_library/service.py`）
37. **借阅落点**：`borrow()` 先要求使用者是本宗成员（`尚未加入宗门`）、槽位是正整数且不超过人物 `功法` 槽数；把该槽写成 `{编号, 品级, 藏经阁借阅: {宗门编号, 原功法}}`，其中 `原功法` 会沿已有借阅记录回填到最底层，再按装好后的构筑查一次相冲（命中即拒绝）。（`规则/藏经阁.json`、`game/core/sect_library/service.py`）
38. **借阅生效与失效**：`effective_cultivation()` 只在读取视图里生效——成员关系仍在同一宗门时保留借阅槽，否则把该槽换回 `原功法`；`成员关系终止` 声明的「清除全部借阅构筑并恢复个人功法构筑」在代码里没有对应写操作——退出、被逐出、解散都不写 `cultivation`，借阅槽会留在库里，只在读取时被投影成原功法；另外 `plan_technique_grade_sync` 会跳过带 `藏经阁借阅` 的槽，借阅槽不参与升品同步。（`规则/藏经阁.json`、`game/core/sect_library/service.py`）

### 五、设施炼制、生产与宗门战
39. **身份权限与材料路径**：`宗主`/`长老` 的 `允许个人材料`/`允许宗门材料`/`允许圣品`/`允许发放` 全为 true，`弟子` 只 `允许个人材料`；`个人炼制` 取个人纳戒材料 + 宗门灵藏灵石、产出归个人；`宗门炼制` 材料与灵石都取宗门灵藏、产出归万珍殿；`个人材料与宗门材料` 禁止混用。（`规则/设施.json`）
40. **灵石消耗公式**：成本 = `基础[建筑] × 单个倍率`，基础为炼器 200、炼丹 300、炼阵 500；**炼器只乘器阶倍率**（凡器 1、灵器 2、法器 5、法宝 12、后天灵宝 24），**炼丹与炼阵只乘品级倍率**（黄品 1、玄品 2、地品 5、天品 12、圣品 64），三张表不相乘；炼阵圣品另加 `每点实际投入 × 1000`（硬编码），且只有从宗门灵藏取材时才乘宗门等级的 `炼制灵石消耗倍率`。（`规则/设施.json`）
41. **设施边界**：`百炼堂` 管本命武器与器律（凡器～后天灵宝）、`丹鼎阁` 管四类丹药（黄品～圣品）、`演阵台` 管一次性阵法（黄品～圣品）；生产设施只有 `灵脉` 与 `灵田`。（`规则/设施.json`、`规则/生产.json`）
42. **生产参数与产出**：`周期秒` 1800、`累计轮数上限` 6、`基础产量倍率` 1.0、`规则版本` 1；`灵脉` 每轮 `灵石范围` 20～60 与 `灵矿数量` 1～2，`灵田` 每轮 `灵植数量` 1～3，材料品级 `随机`、来源是 `全体灵矿`/`全体灵植`。（`规则/生产.json`、`game/core/sect_production/service.py`）
43. **收取与补算**：`collect()` 只允许 `宗主`/`长老`（否则「只有宗主和长老可以收取宗门资源」）；首次调用写一条基线记录并直接返回；之后按 `(现在 - 上次结算时间) // 周期秒` 算待结算轮数并 `min(累计轮数上限 6, ...)` 封顶，为 0 时不动账；结算时间按「上次结算时间 + 轮数 × 周期秒」推进，余数顺延到下一轮。（`规则/生产.json`、`game/core/sect_production/service.py`）
44. **随机种子与倍率**：每轮种子是 `sha256("规则版本|宗门编号|设施编号|结算序号")` 取前 8 字节，抽物品再用 `seed ^ 0xA5A5A5A5`、抽品级用 `seed ^ 0x5A5A5A5A`；`生产数量倍率` 只作用于数量，收成数量先乘 `基础产量倍率`、再乘宗门 `生产数量倍率`，向下取整后按小数部分做一次随机进位并保底 1，汇总后直接入库 `宗门灵藏`。（`规则/生产.json`、`game/core/sect_production/service.py`）
45. **约战与参战**：`宗门战.json` 的 `约战.有效秒数` 600、`必须双方同意` true、`过期自动退款` true；`参战.玩家上限` 15（锁阵时同行人数超过即抛 `participant_limit`）；战斗 `结算秒数` 120、`战斗行动上限` 2400、`每宗阵法上限` 1，启动期强制 `每宗阵法上限 == 1` 且 `阵法来源 == 宗门万珍殿`，否则报「宗门战必须允许每宗从万珍殿使用至多一座阵法」；阵法经 `sect_assets.plan_formation_consumption` 在同一事务里从万珍殿扣除，战丹取人物与同行道侣的待战战丹并在同事务清空，恢复丹取所属玩家纳戒库存。（`规则/宗门战.json`、`game/core/sect_war/service.py`）
46. **押注结算**：`押注.类别` 为灵石，`胜方比例` 0.9、`平局返还比例` 0.9、`损耗比例` 0.1，启动期强制「胜方比例 + 损耗比例 = 1」「平局返还比例 + 损耗比例 = 1」且三值都在 0～1 之间；赔付按 `floor(金额 × 比例)`，即胜方拿 `floor(1.8 × 押注)`、平局双方各拿 `floor(0.9 × 押注)`，两宗共押的 2 份里那 0.2 份无人获得；`记录.每页数量` 10 用于历史分页（页码非正整数即报错，`current_page = min(页码, 总页数)`），终局集合是 `已结算`/`已拒绝`/`已撤回`/`已过期`/`已取消`；参战期间行为状态写 `520013`（`宗门战中`），该状态 `可中断` 为 false、`结束后` 回 `520001`。（`规则/宗门战.json`、`data/角色/规则/状态/行为状态.json`、`game/core/sect_war/service.py`）

**注意**：第 83 轮按「没用的规则删掉」清掉了宗门规则里**没人读的声明**——万珍殿的 `存储` / `取出` / `发放.执行者|原子转移|目标去向`、灵藏的 `取出` / `消耗来源`、设施的 `材料路径` / `结算.扣除顺序`、宗门战的 `约战.必须双方同意|过期自动退款`、`参战.道侣随行|要求同一地表坐标`、`战斗.战丹来源|恢复丹来源`、`记录.保留战书|保留战报`、宗门的同行与贡献若干条。上面各条引用的取值与判定**仍与代码一致**，只是出处从规则文件变成了对应服务的代码（`game/core/sect_assets/service.py`、`game/core/sect_facilities/service.py`、`game/core/sect_war/service.py`、`game/core/sect/service.py`）。
