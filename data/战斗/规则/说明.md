# 战斗规则关系说明

本目录负责战斗定义落地后的全局结算规则。战斗规则不保存具体技能和具体参战者。

## 文件关系

| 文件 | 作用 | 主要引用 |
| --- | --- | --- |
| `行动.json` | 行动条、冷却推进、恢复时点和运行硬上限 | 速度、血气恢复、精神恢复、战斗核心 |
| `时序.json` | 功法、器律、真意、战丹、阵法与运行期对象的统一触发层级 | 战斗核心所有主动技能、事件监听和阵法轮转 |
| `伤害.json` | 命中、暴击、格挡、防御和伤害边界 | 战斗属性、造成伤害能力 |
| `状态反应.json` | 多个状态相遇时自动生成的反应 | 状态能力、原子能力 Schema |
| `构筑契约.json` | 功法、真意、气机、器律各自的形状 | 构筑内容、战斗核心启动校验 |

## 行动关系

`行动.json` 的速度参数读取 `战斗/定义/属性.json -> 速度`。技能冷却通过 `计量单位`、`推进.事件`、`推进.阶段`、`推进.每次减少` 和 `余数处理` 直接定义；它不使用真实秒数，也不存在蓄势回合。

`主动技能轮转` 把每门功法内部的 `释放顺序` 与运行期装配位序组成一条稳定技能序列。同一释放顺序不要求全池唯一；战斗核心从角色的技能游标开始循环查找首个冷却完成、资源足够且未被禁用的技能，成功施放后把游标移到该技能后一位。正式功法 JSON 不保存装配位序或游标。

`被动技能结算` 规定同一事件内所有监听器的统一裁决顺序。监听节点的显式优先级越高越先结算；优先级相同后，根被动的结算顺序越小越先结算，再依次使用参战位序、装配位序、物品编号和能力序号消除同序歧义。真意可以继续使用相同的局部结算顺序，不需要全池排号。

`时序.json` 是跨来源的唯一顺序契约。所有时点均使用事件、阶段、事件延迟数和布尔开关表达，不保存流程句子。来源层级固定为战场环境、阵法、功法、器律、真意、战丹、状态、战斗对象、战场规则；同一事件只建立一次监听快照，结算期间新增监听到下一个事件才生效。阵法不进入角色行动条，固定在`行动结束`完成后轮转；双方先读取同一个战场快照，再同时提交本次阵法冲击。

阵法冲击是宏观结算，不进入命中、闪避、暴击、格挡、防御或环境承伤链。阵法优先冲击敌方阵基；敌方没有阵法时才直达正式参战者。这样阵法不会反过来触发普通伤害监听，也不会推进地势承伤。

轮转间隔由三样东西决定：

```text
间隔 = ceil(时序.阵法轮转.基准周期 × 阶段.行动周期倍率 / 阵法.传导)
```

`基准周期` 在 `时序.json` 里（当前 12）。它原先写死在 `game/core/combat/engine.py`，现在和 `伤害.json` 的几个闸一样是可调数据。`传导` 与阶段倍率来自阵法内容：`传导` 在 `品级[].节点.传导`，周期倍率在 `品级[].地势阶段[].行动周期倍率`。

四条品级的 `传导` 是 1.0 / 1.45 / 2.1 / 3.05，所以**首轮落点按品级递进**：黄 12、玄 9、地 6、天 4 行动。圣品的 `传导` 在运行期由「运行值」推算，静态读不到。首轮之后的间隔由各地势阶段的周期倍率（0.44–1.53）逐段改变。

实测覆盖率（100 级满构筑、镜像、行动上限 60、行动中位 26）：黄品 82%、玄品 85%、地品 88%、天品 92%。没走到的对局集中在「1 行动就结束」那种（一方自我退场），所以低品级阵法在极短局不轮转是正常的。

`行动.json -> 最高行动效率` 是所有参战者共用的行动公式边界。角色初始化只提供最终速度，战斗核心不读取角色类型、等级阶梯或修行槽位。当前上限放开到 4，使超过标准速度的成长能够继续转化为行动效率。

行动开始恢复把资源映射到属性：

```text
血气 <- 血气恢复
精神 <- 精神恢复
```

事件链、能力链、触发技能、召唤物和构造物上限是防止组合能力无限递归或无限创建对象的运行硬边界。

## 触发名额

`每次行动最多触发` 与 `每场战斗最多触发` 是**监听声明的名额**，键是（修士, 词条, 监听声明），三条都不含「这是第几张卡」。所以：

- **同一个修士带两张同名词条，共用一个名额**。卡面写「每行动只能使用1次」就是 1 次，不会因为带了两张变成 2 次。这一条曾经是破的：名额键里含装配实例，而真实装配的实例号是 `f"{修士}:{方向}:{槽位下标}"`（`service.py`），于是每张卡各拿一个名额。
- **名额按修士算，不跨方合并**。对面的同名词条是另一份名额，双方各触发一次是合法的（与游戏王的 HOPT 一致：限制按玩家算，不按卡名全球算）。不走「全战场按词条名一次」是因为排序链在镜像双方之间只能落到 `参战位序`，那样等于每次名额争夺都判给先手方，镜像局变成系统性先手优势。
- **单位是行动**，即每个参战者的一次行动，不是双方合起来的一回合。名额在每个行动开始时清空。
- **同一张卡里的多条监听声明各自占一个名额**。`反哺` 的「恢复前」与「行动结束」是两条声明，各有各的 1 次。
- **名额在监听开始执行前就记账**，所以效果即使失败也算用掉。
- 战场环境、战斗对象、战场规则的名额键用的是运行期编号（`环境:…`、对象 id、`战场:…`），实际等同于每个实例一份。

## 事件转化

`转化事件` 只能发生在同类结算语义的事件之间：`恢复前`、`获得护盾前`、`资源恢复前` 三者可以互相转化，其余组合一律非法（结算时直接报错，属于内容错误）。

**转化目标若已经在结算栈上，这次转化被放弃**，原事件按自己的语义继续结算，并在该事件的 `事实` 里留下 `转化跳过`，记下被放弃的目标事件。

这条是**引擎语义，不是内容约束**，因为成环往往不是单张卡的问题，而是两张卡对向作用的结果。例：己方 `反哺` 把敌方的恢复转成护盾，那个护盾又引出一轮恢复，被敌方的 `反哺` 再转成护盾——两边各触发一次，名额限制完全生效，环却闭上了，因为名额**按修士**算，双方各有一份。卡作者在本地看不到这个环，所以语义只能由引擎定；而定成「报错终止战斗」意味着带这套构筑的玩家每打一架都拿不到结果，所以定为「放弃转化 + 留痕」。

放弃转化不会带来无界递归：目标必须不在结算栈上才允许转化，而栈上的事件种类有限，事件链深度上限也独立生效。

## 监听优先级

`优先级` 声明在**监听节点**上，只决定同一事件内多个监听的**结算先后**，不决定是否触发。

完整排序链来自 `时序.json -> 事件监听.排序`，逐级消歧：

```text
来源层级升序 -> 监听优先级降序 -> 结算顺序升序
-> 参战位序 -> 装配位序 -> 物品编号 -> 能力序号
```

**优先级排在第二位，越不过来源层级。** 来源层级固定为战场环境、阵法、功法、器律、真意、战丹、状态、战斗对象、战场规则，所以真意的监听无论优先级多高，都排在功法的监听之后。想改跨来源的先后，只能改 `时序.json` 的来源层级，不能用优先级绕。

取值按降序生效，越大越先。当前数据里用的是 10 的倍数（10 到 80），**未声明的按 0 算**，也就是排在所有声明过的之后。同一张卡在两个修士之间优先级相同，所以镜像双方比不出高低，仍会落到 `参战位序`。

**什么时候该声明**：同一事件上有两个监听，其中一个**改写数值或判定**、另一个**读取那个数值或判定**时，先后会改变结果——这时必须把意图写出来，否则顺序由 `结算顺序 / 参战位序 / 装配位序 / 物品编号 / 能力序号` 这些机械项决定，作者表达不了「谁先谁后」。

### 两个旋钮怎么选

表达先后有两个字段，都已在排序链里，但粒度不同：

| 字段 | 声明在 | 粒度 | 相对强弱 |
| --- | --- | --- | --- |
| `结算顺序` | `被动技能`（必填） | 整张卡 | 被 `优先级` 压过 |
| `优先级` | 监听节点 | 单条监听 | 压过 `结算顺序` |

**跨卡先后用 `结算顺序`**——它本来就是「这张卡在这一层里排第几」的声明，改一个数就够，不需要给每条监听都标。**`优先级` 留给两种情况**：同一张卡内多条监听需要不同先后（一张卡只有一个 `结算顺序`，分不开），或者要临时压过 `结算顺序` 又不想重排全表。

### 实测状态与缺口

`结算顺序` 的实际使用情况：

| 方向 | 声明 `结算顺序` | 非 1 的 |
| --- | --- | --- |
| 功法 | 600 | 206 |
| 真意 | 600 | **0** |
| 器律 | 64 | **0** |

**真意与器律的顺序意图为零**，跨卡先后完全落在 `参战位序 / 装配位序 / 物品编号` 上，也就是「谁装在前面谁先」。之前成环的 `反哺`、`夺春`、`万生逆流` 全是真意，不是巧合。

`优先级` 只声明了 72 处，且**全部是功法**。

工作面由 `tools/盘点监听顺序.py` 盘出（静态 triage）：改写共享量的声明 **934 处缺优先级**，涉及 **861 张卡**（按事件重复计）。分布最重的是 `行动结束`（146 处未标，且最多卡间交集）、`命中判定前`（63 处，**一处都没标**）、`恢复前`（43 处未标，已有 14 处可作范例）、`造成伤害前`（46 处未标）。

### 已成形的一条阶梯：`造成伤害前`

`造成伤害前` 上已有的 12 处声明读出来是一条**语义阶梯**（高优先级先执行）：

| 优先级 | 干什么 | 例 |
| --- | --- | --- |
| 40 | `修改事件目标` | 九转涅槃体、柳影回风真经、龙虎交泰行气诀 |
| 30 | `转移伤害` / `取消事件` | 泰山压顶镇岳诀、天河倒卷玄水经、混元调息典 |
| 20 | `分摊伤害` | 泥丸抱月心经、九死登真拳经、紫焰煅魂真经 |

顺序是「**先定目标 → 再转移或取消 → 最后分摊**」。这是**可从约定推出**的，
不是偏好：先分摊再改目标等于先把伤害摊开、再决定打谁，逻辑是倒的。

按这条阶梯补的第一张卡是 `400160 劫火铸身经·移锋`：它做 `修改事件目标`，
原先没标（=0，排在 `分摊伤害` 之后），现已补 `优先级: 40`。

**注意实测的稀疏性**：60 套满构筑、17577 次事件派发里，真正同层同事件互相咬住的
只有 **1 对卡、3 次**。补这种声明很难在单场战斗里看到结果变化，所以验证要靠
**排序链上的位置**（`优先级` 把该监听从 0 档抬进 40 档），而不是靠战报差分。



1. **来源层级排在最前，优先级越不过它。** 真意的监听永远排在功法之后，所以真意的顺序问题只在真意内部有意义。跨来源的先后改 `时序.json`。
2. **两个旋钮都是「事件内全局」的，表达不了成对的「A 先于 B」而不动 A 与 C 的相对位置。** 所以每个事件上要给出的是一条**全序**，不是几条成对关系。
3. **不要按盘点表批量刷。** 静态 triage 只能指出「这里有交集」，判不出作者想要谁先；写写冲突（两个监听都改写同一个量）尤其需要意图。应当逐个事件定序，`恢复前` 与 `造成伤害前` 上已有的 22 处声明就是可照抄的范例。

声明后会出现在卡面明细行里（渲染为 `优先级N`），所以它同时是给玩家看的。**不要用优先级去解来源层级冲突**，那属于 `时序.json`。

## 行动意图改写

`修改行动意图` 改的是 `context.action_intent`，也就是**下一个要执行的动作**。字段与效果：

| 字段 | 作用 |
| --- | --- |
| `取消` | 让这次行动整个不发生（发出 `行动跳过后`） |
| `行动` | 把行动类型改成指定值 |
| `目标` | 换掉行动的目标 |
| `技能` | 指定要放的技能 |

**`目标` 字段里的 `自身` / `敌方` 是相对「监听者」解析的，不是相对行动者**——`_target_select` 用 `enemies_of(source)`，而 `source` 是挂这条监听的修士。这一点最容易写反：

| `目标.范围` | 实际效果 |
| --- | --- |
| `自身` | 迫使行动者**来打我**（嘲讽、引战） |
| `敌方` | 迫使行动者**打它自己**（自伤、乱序） |

用法上最常见的是 `行动决策前` + `阵营关系: 任意敌方`，于是敌人每次决策都会被改写。**`取消` 这类效果必须带 `每场战斗最多触发`**：`每次行动最多触发` 挡不住任何东西，因为每个行动只有一次决策（见内容侧「`修改行动意图` 的取消写法」）。

## 伤害关系

`伤害.json` 与属性定义共同组成伤害流水线：

```text
命中率与闪避率
-> 暴击率、抗暴率与暴击伤害
-> 比例穿透、固定穿透与防御
-> 伤害加成与伤害减免
-> 格挡率、破格率与格挡减伤
-> 护盾和血气
```

具体能力可以声明无视防御、真实伤害、不可暴击或不可格挡，但全局上下限仍由规则和 Schema 共同约束。

## 构筑契约

`构筑契约.json` 是四个构筑方向各自的形状声明：编号前缀、允许的字段集合、允许的根能力、能力数量、是否要求主动技能、是否参与全库权重唯一。它由 `game/core/combat/builds.py` 在战斗核心装配时执行，越界即终止启动。契约必须正好声明功法、真意、气机、器律四项，少一项或多一项都会失败。

## 状态反应

当前 `状态反应.json` 是空数组，表示核心不自动把任意两个状态合成为第三种结果。以后新增反应时，每项能力树仍必须符合 `战斗/定义/原子能力.json`。

## 修改检查

- 修改速度、命中或伤害边界时同步检查相关属性上下限。
- 提高运行硬上限前评估事件爆炸、战报大小和死循环风险。
- 改 `每次行动最多触发` / `每场战斗最多触发` 前先读「触发名额」：名额按（修士, 词条, 声明）算，同方两张同名词条共用一份。
- 加监听声明后，如果它与已有监听在同一事件上互相读写数值或判定，补 `优先级`；跨来源的先后改 `时序.json`，不要用优先级绕。
