# 战斗规则关系说明

本目录负责战斗定义落地后的全局结算规则。战斗规则不保存具体技能和具体参战者。

## 文件关系

| 文件 | 作用 | 主要引用 |
| --- | --- | --- |
| `行动.json` | 行动条、冷却推进、恢复时点和运行硬上限 | 速度、血气恢复、精神恢复、战斗核心 |
| `时序.json` | 功法、器律、真意、战丹、阵法与运行期对象的统一触发层级 | 战斗核心所有主动技能、事件监听和阵法轮转 |
| `伤害.json` | 命中、暴击、格挡、防御和伤害边界 | 战斗属性、造成伤害能力 |
| `状态反应.json` | 多个状态相遇时自动生成的反应 | 状态能力、原子能力 Schema |
| `构筑契约.json` | 功法、真意、气机、器律各自的形状 | 构筑内容、战斗核心启动校验 |

## 行动关系

`行动.json` 的速度参数读取 `战斗/定义/属性.json -> 速度`。技能冷却通过 `计量单位`、`推进.事件`、`推进.阶段`、`推进.每次减少` 和 `余数处理` 直接定义；它不使用真实秒数，也不存在蓄势回合。

`主动技能轮转` 把每门功法内部的 `释放顺序` 与运行期装配位序组成一条稳定技能序列。同一释放顺序不要求全池唯一；战斗核心从角色的技能游标开始循环查找首个冷却完成、资源足够且未被禁用的技能，成功施放后把游标移到该技能后一位。正式功法 JSON 不保存装配位序或游标。

`被动技能结算` 规定同一事件内所有监听器的统一裁决顺序。监听节点的显式优先级越高越先结算；优先级相同后，根被动的结算顺序越小越先结算，再依次使用参战位序、装配位序、物品编号和能力序号消除同序歧义。真意可以继续使用相同的局部结算顺序，不需要全池排号。

`时序.json` 是跨来源的唯一顺序契约。所有时点均使用事件、阶段、事件延迟数和布尔开关表达，不保存流程句子。来源层级固定为战场环境、阵法、功法、器律、真意、战丹、状态、战斗对象、战场规则；同一事件只建立一次监听快照，结算期间新增监听到下一个事件才生效。阵法不进入角色行动条，固定在`行动结束`完成后轮转；双方先读取同一个战场快照，再同时提交本次阵法冲击。

阵法冲击是宏观结算，不进入命中、闪避、暴击、格挡、防御或环境承伤链。阵法优先冲击敌方阵基；敌方没有阵法时才直达正式参战者。这样阵法不会反过来触发普通伤害监听，也不会推进地势承伤。

轮转间隔由三样东西决定：

```text
间隔 = ceil(时序.阵法轮转.基准周期 × 阶段.行动周期倍率 / 阵法.传导)
```

`基准周期` 在 `时序.json` 里（当前 12）。它与 `伤害.json` 的几个闸一样都是可调数据。`传导` 与阶段倍率来自阵法内容：`传导` 在 `品级[].节点.传导`，周期倍率在 `品级[].地势阶段[].行动周期倍率`。

四条品级的 `传导` 是 1.0 / 1.45 / 2.1 / 3.05，所以**首轮落点按品级递进**：黄 12、玄 9、地 6、天 4 行动。圣品的 `传导` 在运行期由「运行值」推算，静态读不到。首轮之后的间隔由各地势阶段的周期倍率（0.44–1.53）逐段改变。


`行动.json -> 最高行动效率` 是所有参战者共用的行动公式边界。角色初始化只提供最终速度，战斗核心不读取角色类型、等级阶梯或修行槽位。当前上限放开到 4，使超过标准速度的成长能够继续转化为行动效率。

行动开始恢复把资源映射到属性：

```text
血气 <- 血气恢复
精神 <- 精神恢复
```

事件链、能力链、触发技能、召唤物和构造物上限是防止组合能力无限递归或无限创建对象的运行硬边界。

## 触发名额

`每次行动最多触发` 与 `每场战斗最多触发` 是**监听声明的名额**，键是（修士, 词条, 监听声明），三条都不含「这是第几张卡」。所以：

- **同一个修士带两张同名词条，共用一个名额**。卡面写「每行动只能使用1次」就是 1 次，不会因为带了两张变成 2 次。名额键里不含装配实例，所以同名的两张卡拿的是同一个名额。
- **名额按修士算，不跨方合并**。对面的同名词条是另一份名额，双方各触发一次是合法的（与游戏王的 HOPT 一致：限制按玩家算，不按卡名全球算）。不走「全战场按词条名一次」是因为排序链在镜像双方之间只能落到 `参战位序`，那样等于每次名额争夺都判给先手方，镜像局变成系统性先手优势。
- **单位是行动**，即每个参战者的一次行动，不是双方合起来的一回合。名额在每个行动开始时清空。
- **同一张卡里的多条监听声明各自占一个名额**。`反哺` 的「恢复前」与「行动结束」是两条声明，各有各的 1 次。
- **名额在监听开始执行前就记账**，所以效果即使失败也算用掉。
- 战场环境、战斗对象、战场规则的名额键用的是运行期编号（`环境:…`、对象 id、`战场:…`），实际等同于每个实例一份。

## 事件转化

`转化事件` 只能发生在同类结算语义的事件之间：`恢复前`、`获得护盾前`、`资源恢复前` 三者可以互相转化，其余组合一律非法。

**越界的转化与越界的改写都是「拒绝 + 留痕」，不是报错。** 白名单写在 `定义/事件.json` 的 `可修改` 里，运行期拿它逐条核：不在名单上的这次改写**不生效**，并在该事件的 `事实` 里留下 `改写非法`（写清是哪个事件、哪个字段）。声明本身写错由内容判据当场报出来；运行期碰到的是**声明合法、落到别的时点却越界**——保存下来的效果回放时，当前事件与声明时并不相同。

**转化目标若已经在结算栈上，这次转化被放弃**，原事件按自己的语义继续结算，并在该事件的 `事实` 里留下 `转化跳过`，记下被放弃的目标事件。

这条是**引擎语义，不是内容约束**，因为成环往往不是单张卡的问题，而是两张卡对向作用的结果。例：己方 `反哺` 把敌方的恢复转成护盾，那个护盾又引出一轮恢复，被敌方的 `反哺` 再转成护盾——两边各触发一次，名额限制完全生效，环却闭上了，因为名额**按修士**算，双方各有一份。卡作者在本地看不到这个环，所以语义只能由引擎定；而定成「报错终止战斗」意味着带这套构筑的玩家每打一架都拿不到结果，所以定为「放弃转化 + 留痕」。

## 两条链的上限

`行动.json` 的 `事件链深度上限` 与 `能力链深度上限` 是**防住无界连锁的墙，不是报错开关**：

- 事件链到顶：**这次事件照常发生、照常进战报，只是不再往下触发监听**，事实里留 `链深度跳过`；
- 能力链到顶：**这一层能力不执行**（算「没生效」），当前事件的事实里留 `能力链跳过`。

**上限要覆盖设计出来的最深连锁，而且要有余量。** 满编讨伐（15 名参与者 = 30 个我方单位、敌方 37 个单位，含镇域 `9/9/9` 与天灾 `12/12/12`）实测到最深 **事件 182 层 / 能力 317 层**，所以当前值取 `256` / `384`——正常战斗碰不到墙，真碰到也只会少触发几层，不会让玩家拿不到战果。

**墙不是性能旋钮**：压低两条上限省不下多少时间（**每行动约 2000~3500 个事件，绝大部分在浅层**），真正的开销在**监听表被反复重编**；详见 `战斗/说明.md` 第 67 条。

**墙不能定得比 Python 的递归还深。** 事件与能力是递归派发的，一层要吃掉好几个帧；战斗核心启动时会把进程的递归下限抬到 8000 帧（写在战斗核心的引擎模块里，`规则/行动.json` 的两条上限之和必须留在这个预算里）。改上限时两件事一起看。

## 监听优先级

`优先级` 声明在**监听节点**上，只决定同一事件内多个监听的**结算先后**，不决定是否触发。

完整排序链来自 `时序.json -> 事件监听.排序`，逐级消歧：

```text
响应等级降序 -> 来源层级升序 -> 监听优先级降序 -> 结算顺序升序
-> 参战位序 -> 装配位序 -> 物品编号 -> 能力序号
```

**先比较响应等级，再比较来源层级，随后比较优先级。** 同等级的来源顺序仍为战场环境、阵法、功法、器律、真意、战丹、状态、战斗对象、战场规则；三速裁断先于二速应式，不能用数值优先级绕过等级资格。

取值按降序生效，越大越先。当前数据里用的是 10 的倍数（10 到 80），**未声明的按 0 算**，也就是排在所有声明过的之后。同一张卡在两个修士之间优先级相同，所以镜像双方比不出高低，仍会落到 `参战位序`。

**什么时候该声明**：同一事件上有两个监听，其中一个**改写数值或判定**、另一个**读取那个数值或判定**时，先后会改变结果——这时必须把意图写出来，否则顺序由 `结算顺序 / 参战位序 / 装配位序 / 物品编号 / 能力序号` 这些机械项决定，作者表达不了「谁先谁后」。

### 两个旋钮怎么选

表达先后有两个字段，都已在排序链里，但粒度不同：

| 字段 | 声明在 | 粒度 | 相对强弱 |
| --- | --- | --- | --- |
| `结算顺序` | `被动技能`（必填） | 整张卡 | 被 `优先级` 压过 |
| `优先级` | 监听节点 | 单条监听 | 压过 `结算顺序` |

**跨卡先后用 `结算顺序`**——它本来就是「这张卡在这一层里排第几」的声明，改一个数就够，不需要给每条监听都标。**`优先级` 留给两种情况**：同一张卡内多条监听需要不同先后（一张卡只有一个 `结算顺序`，分不开），或者要临时压过 `结算顺序` 又不想重排全表。

### 实测状态与缺口

`结算顺序` 的实际使用情况：

| 方向 | 声明 `结算顺序` | 非 1 的 |
| --- | --- | --- |
| 功法 | 806（被动技能节点数；功法不保证一张卡只有一个被动） | 206 |
| 真意 | 600 | **0** |
| 器律 | 64 | **0** |

**真意与器律的顺序意图为零**，跨卡先后完全落在 `参战位序 / 装配位序 / 物品编号` 上，也就是「谁装在前面谁先」。成环的 `反哺`、`夺春`、`万生逆流` 全是真意，不是巧合。

`优先级` 当前声明了 **82 处：功法 57 · 真意 23 · 器律 2**。
真意与器律那 25 处**不是逐条手工定序**——是「时点配对」批量做法
（给单一时点的卡补一条配对时点的回响）**复制监听节点时把 `优先级`
字段一起复制过去了**。**这条值得记住：复制整条监听会连带复制它的顺序声明**，
所以「某方向有没有顺序意图」这个读数，会被复制型工具污染。

监听声明的静态 triage 读数：合计 **5343** 条，
其中**改写共享量却未标优先级的有 3113 处**，按事件重复计涉及 **569 张/词条**。
缺口最重的事件是 `行动开始`（待办 45 张，同层竞争对 348）、`造成伤害前`（43 / 249）、
`技能施放后`（38 / 180）、`造成伤害后`（33 / 141）、`添加状态前`（28 / 138）、
`恢复前`（21 / 132）。

### 已成形的一条阶梯：`造成伤害前`

`造成伤害前` 上已有的 12 处声明读出来是一条**语义阶梯**（高优先级先执行）：

| 优先级 | 干什么 | 例 |
| --- | --- | --- |
| 40 | `修改事件目标` | 九转涅槃体、柳影回风真经、龙虎交泰行气诀 |
| 30 | `转移伤害` / `取消事件` | 泰山压顶镇岳诀、天河倒卷玄水经、混元调息典 |
| 20 | `分摊伤害` | 泥丸抱月心经、九死登真拳经、紫焰煅魂真经 |

顺序是「**先定目标 → 再转移或取消 → 最后分摊**」。这是**可从约定推出**的，
不是偏好：先分摊再改目标等于先把伤害摊开、再决定打谁，逻辑是倒的。

做 `修改事件目标` 的监听要标 `优先级: 40`——不标就是 0 档，会排在 `分摊伤害` 之后
（`400160 劫火铸身经·移锋` 就是按这条阶梯补的）。

**注意实测的稀疏性**：60 套满构筑、17577 次事件派发里，真正同层同事件互相咬住的
只有 **1 对卡、3 次**。补这种声明很难在单场战斗里看到结果变化，所以验证要靠
**排序链上的位置**（`优先级` 把该监听从 0 档抬进 40 档），而不是靠战报差分。

1. **来源层级排在最前，优先级越不过它。** 真意的监听永远排在功法之后，所以真意的顺序问题只在真意内部有意义。跨来源的先后改 `时序.json`。
2. **两个旋钮都是「事件内全局」的，表达不了成对的「A 先于 B」而不动 A 与 C 的相对位置。** 所以每个事件上要给出的是一条**全序**，不是几条成对关系。
3. **不要按盘点表批量刷。** 静态 triage 只能指出「这里有交集」，判不出作者想要谁先；写写冲突（两个监听都改写同一个量）尤其需要意图。应当逐个事件定序，`恢复前` 与 `造成伤害前` 上已有的 22 处声明就是可照抄的范例。

声明后会出现在卡面明细行里（渲染为 `优先级N`），所以它同时是给玩家看的。**不要用优先级去解来源层级冲突**，那属于 `时序.json`。

## 真意与器律的监听分工

两者形状相同（都只有被动技能、恰好一项、效果根是 `监听事件`），但**角度不同**：真意从**战场**说话，器律从**器物与持有者**说话。

### 判据：按「谁的角度」，不按时点清单

按时点判是**枚举**——每加一个时点就要回来改规则，而且等于把"当前用到的时点"当规范。判据要落在**可判的语义**上，就是四问：

| 四问 | 器物向（器律） | 叙事向（真意） |
| --- | --- | --- |
| ① 观察谁 | `观察角色`=来源/承受者 且 `阵营关系`=自身/主人 | 涉及其他己方 / 任意敌方 / 任意 |
| ② 作用于谁 | 只作用于 自身 / 主人，或打**持有者选定的** `当前目标` | 打到 事件来源 / 事件承受者 / 己方 / 敌方 / 全体 / 关联对象 |
| ③ 读谁的状态 | 自身属性 / 自身当前·已损失 / 构筑计量 / 状态层数 / 行动条 / 技能冷却 | 目标属性 / 目标当前·已损失 |
| ④ 有没有改写战场事件 | 无 | `取消事件` / `修改事件目标` / `分摊伤害` / `转移伤害` |

**②里 `当前目标` 不算越界**：武器打持有者选定的目标正是器物本职（攻伐类器律全是这个形状），
把它算成越界会把 17/64 张器律误判（实测效果打到【当前目标】的正是 17 张）。实施工具 `tools/报告与生成/判归属.py`。

### 判据的两种强度：硬规则与偏重

实测（600 真意 / 64 器律）划出一条清晰的线——**只有两条能当硬规则，其余是偏重**：

| | 器律 | 真意 | 性质 |
| --- | --- | --- | --- |
| 用「语义上不属于器物」的战场时点（`战斗对象入场后`/`退场后`/`战场规则变化后`/`形态切换后`/`复活后`） | **0 张** | 50 张 | 器律**硬规则**（一把剑不该知道别的修士进场了） |
| 改写战场事件（`取消事件`/`修改事件目标`/`分摊伤害`/`转移伤害`） | **0 张** | 28 张 | 器律**硬规则** |
| 伸向战场（观察他人 / 作用于他人 / 读他人状态） | 6 张（**9.4%**） | 526 张（87.7%） | **偏重**——不做判定 |

**所以"只观察持有者与武器的交互界面"是偏重，不是边界**：器律里确实有 26 张会帮队友、
给触发的敌人挂状态（`器律-同契`、`器律-牵制` 各有一批）。把它当硬边界会误判四成器律卡。
能当硬规则的只有上表前两行——它们**可以从四问推出来**（不是枚举现状），而且**当前 0 违例**，
所以将来想启动即校验，就校验这两条。

### 时点特征（佐证，不参与判定）

| 方向 | 监听节点 | 不同时点 | 时点性质 |
| --- | --- | --- | --- |
| 真意 | 1295 | **55** | 593 张偏裁定结算 · **7 张用结构性时点** |
| 器律 | 141 | **29**（真意的真子集，无独有时点） | **64/64 全部偏裁定结算** |

器律的 29 个时点是真意 55 个的真子集，真意独占 26 个。按节点占比，器律相对真意偏重最明显的是
`事件转化后`（6.1 倍）、`行动决策后`（5.5）、`技能冷却变化后`（5.4）、`添加状态前`（5.1）、
`格挡判定前`（3.1）、`受到致命伤害`（3.1）；反过来 `造成伤害后` 上真意有 111 张卡在听、器律只有 3 张。

**时点特征只是佐证**：它和四问的结论一致（器律落在裁定与结算点、真意才用结构性时点），
但判定不看它——这样以后新增时点不需要改规则。

### 为什么不写成硬契约

`构筑契约.json` 目前只约束根能力，不约束时点集合；`tools/架构审查/检查构筑形状.py` 里只有气机被限定
「不监听事件」。要把上面两条硬规则变成启动即校验是**可以的**（判据在语义上、且当前 0 违例），
但**不要**写成「把器律当前没用到的时点全列进禁用表」——那是把现状当规范。
真要落，落法是判据本身：**器律不得使用战场时点、不得改写战场事件**，由 `tools/报告与生成/判归属.py` 判。

## 行动意图改写

`修改行动意图` 改的是运行期的行动意图，也就是**下一个要执行的动作**。字段与效果：

| 字段 | 作用 |
| --- | --- |
| `取消` | 让这次行动整个不发生（发出 `行动跳过后`） |
| `行动` | 把行动类型改成指定值 |
| `目标` | 换掉行动的目标 |
| `技能` | 指定要放的技能 |

**`目标` 字段里的 `自身` / `敌方` 是相对「监听者」解析的，不是相对行动者**——目标按**来源的敌方**解析，而来源就是挂这条监听的修士。这一点最容易写反：

| `目标.范围` | 实际效果 |
| --- | --- |
| `自身` | 迫使行动者**来打我**（嘲讽、引战） |
| `敌方` | 迫使行动者**打它自己**（自伤、乱序） |

用法上最常见的是 `行动决策前` + `阵营关系: 任意敌方`，于是敌人每次决策都会被改写。**`取消` 这类效果必须带 `每场战斗最多触发`**：`每次行动最多触发` 挡不住任何东西，因为每个行动只有一次决策（见内容侧「`修改行动意图` 的取消写法」）。

### 代为支付：`资源消耗前` + `修改事件目标{自身}`

能力消耗资源时，扣减对象**是在派发 `资源消耗前` 之后**才取的，而且「够不够」（`变化前数值 < 数值`）与「从谁身上扣」都用改写后的目标。所以这样写就是**代付**：

```text
监听 资源消耗前 · 观察角色=承受者 · 阵营关系=其他己方
效果 修改事件目标{范围: 自身}
```

即「队友要花资源时，改由我来花」——**不够则队友那一手直接失败**（除非那份消耗写了 `不足时是否失败: false`）。库里既有的代付卡是 `400334`、`400226`、`400474`、`410472`，`400503`、`410128`、`400026`、`410272` 也统一成了这个形状。

**不要用 `修改行动意图{字段: 目标, 目标: 自身}` 去做这件事**：那是把队友的**整次出手**改向我（他会来打我），不是替他付钱。改的是目标还是代价，是两件事。

## 伤害关系

`伤害.json` 与属性定义共同组成伤害流水线：

```text
命中率与闪避率
-> 暴击率、抗暴率与暴击伤害
-> 比例穿透、固定穿透与防御
-> 伤害加成与伤害减免
-> 格挡率、破格率与格挡减伤
-> 护盾和血气
```

具体能力可以声明无视防御、真实伤害、不可暴击或不可格挡，但全局上下限仍由规则和 Schema 共同约束。

## 地形战斗节奏

`地形.json` 决定**一场仗打多久**，落点在伤害流水线的第一段——输出倍率：

```text
实际输出倍率 = 伤害.json.输出倍率（基准 340） × 地形百分比 / 100
```

- **有名有姓的地势按特色配倍率**（54 档全配到）：一览无余的平原出手干脆（冲积平原 / 原野 / 沃野 150，平原 / 草原 / 草甸 155），林深叶密视线受限（林地 / 松林 / 枫林 165、寒林 175），起伏谷地（丘陵 170、泉谷 180），高处风急（高地 180、云岭 190、黑岩山岭 195），隘口绝壁（山口 190、峡谷 200、丹崖 205、断崖 210），火山雷谷最暴烈（火山 230、熔岩谷 235、雷谷 225），水泽缠斗（湿地 / 芦苇湿地 170、寒沼 180、湖汊 185）。
  每一档地形在 `地形分区.json` 里都有一行，判据会查「有没有漏配」（漏了就会静默落到无相那一档，
  「火山打得凶」这种设计就悄悄没了）。
- **无名之地（没有特殊地势，或场地没登记地形）走 `无相地势`，随进度加**：
  倍率 = `无相地势.基础倍率`（150）+ 等级 × `无相地势.每级加成`（0.5）——等级越高出手越决，
  仗打得越快。所以没有地势的对局（含语料里那些不带场地的对局）也会随进度整体变快。
- 倍率**同时乘在双方的伤害上**，所以它是**节奏旋钮**、不是强弱旋钮：谁打谁都更疼，仗更早结束。
  以后嫌仗长嫌仗短，就调这张表，别再动 `伤害.json` 的基准。

## 构筑契约

`构筑契约.json` 是四个构筑方向各自的形状声明：编号前缀、允许的字段集合、允许的根能力、能力数量、是否要求主动技能、是否参与全库权重唯一。它由战斗核心在装配时执行，越界即终止启动。契约必须正好声明功法、真意、气机、器律四项，少一项或多一项都会失败。

## 状态反应

当前 `状态反应.json` 是空数组，表示核心不自动把任意两个状态合成为第三种结果。以后新增反应时，每项能力树仍必须符合 `战斗/定义/原子能力.json`。

## 修改检查

- 修改速度、命中或伤害边界时同步检查相关属性上下限。
- 提高运行硬上限前评估事件爆炸、战报大小和死循环风险。
- 改 `每次行动最多触发` / `每场战斗最多触发` 前先读「触发名额」：名额按（修士, 词条, 声明）算，同方两张同名词条共用一份。
- 加监听声明后，如果它与已有监听在同一事件上互相读写数值或判定，补 `优先级`；跨来源的先后改 `时序.json`，不要用优先级绕。
