# 战斗定义关系说明

> 本说明只写现行规则与边界；历史变更见 git 历史，待补事项与缺功能见 [待补内容.md](../内容/待补内容.md)。

本目录是战斗语言的词典和语法，不是具体技能库。

## 四层关系

```text
属性.json       定义参战者可拥有的数值
资源.json       把血气、精神、护盾关联到上限属性
事件.json       定义战斗过程中可以观察和改写的时点
原子能力.json   定义能力节点的字段、类型和执行器
规则层.json     定义效果之外的常驻规则（归属、消费者、优先级、可改写）
        │
        v
功法、真意、气机、器律  用这套语言直接写出完整能力树
战场环境             使用同一语言定义入阶能力与常驻监听
```

原子能力是唯一的战斗词汇表，构筑不再有中间层：卡片里写下的每个节点都必须是 `原子能力.json` 登记的键。需要表达新语义时先在这里登记能力与执行器，再去卡片里使用。

**不要把「暂时没有卡片用」的原子能力删掉。** 实测**展开模板之后**的全库 1739 个实体用到了 **65 条里的 62 条**，登记但六个面都没用到的是 3 条——`固定属性加成`、`规则文本`、`顺序执行`；它们不是被淘汰：`顺序执行` 只声明「依次结算」、不产生新的结算点，规范化把它的子项并进父数组，`固定属性加成` 与 `规则文本` 是属性与规则文本两个载体专用的节点。词汇表、执行器与渲染分支都还在（`tools/架构审查/检查原子能力.py` 每次现算这三个数）。词汇表是**设计余量**，不是内容——内容里没人读的钩子可以清（`tools/一次性迁移/清惰性节点.py`），词汇表里的词不能。判断词汇表干不干净只看两件事：卡片用了但没登记的（应为 0）、登记了但字段与执行器对不上的（应为 0）。

## `规则层.json`

**效果之外的规则住这里，而且整层都是数据。** 它回答「引擎怎么看这个单位、这一行」，
不回答「发生了什么」：效果管线负责结算，规则层负责合法性，所以规则层天然免疫
「效果无效」这一类改写。

每项规则声明：

| 字段 | 意思 |
| --- | --- |
| `归属` | `单位` 或 `行`。**单位级有四处写法**：卡面根能力 `规则文本` 的 `规则[]`、被动技能行自己的 `规则[]`、状态定义里的 `规则[]`（跟状态一起生灭）、**参战者固有规则**（`固有规则`，不挂在任何一张卡上）；行级写在能力行自己的 `规则[]`，目前只有技能行 `主动技能` |
| `拦截点` | 在哪一处判定上被问；每个拦截点只认它读得到的归属 |
| `处置` | `拒绝` 或 `允许`（`允许` 用来写「这条可以被某规则覆盖」） |
| `优先级` | 同一拦截点上的先后，全表唯一 |
| `名额` | **同一条锁定技全库最多几张卡能带**，正整数、默认 1。它不是稀有度崇拜，是防一条闸门被抄到所有卡上；想多发一张，先在登记表里抬这个数（一次显式的决定），判据每轮把用量打出来 |
| `种族名额` | 可选，只有单位级规则该有它：**同一条锁定技最多几个种族能带**（种族是天生层，与卡是两本账）。不写就与 `名额` 同额；行级规则不许写它（种族只能用单位级规则） |
| `原因` | 可选。**被这条锁定技拒绝时对玩家说的说法**（例如 `控制免疫` / `状态免疫`），只有 `状态被添加` 这类会报原因的拦截点用得上；没写就回落一个中性说法 |
| `可改写` | 默认空 = 不可被任何规则改写；要允许某条规则覆盖它，就列出那条规则名 |
| `条件` | **用已登记的条件原子写**（现在只用 `标签条件`），参数以 `$字段` 占位 |
| `字段` | 卡片可以传的参数；`允许空` 的参数留空表示这一项不设限 |
| `卡面` | 卡面上的说法，由渲染器按它成句（**规则文本不许手写**） |

**写在哪不影响语义，只影响它跟谁生灭**：写在根能力或被动行上跟参战者一起进战斗，写在
状态定义里跟状态一起走（状态没了规则就没了），写成参战者固有规则则**不依赖任何内容**——
生成敌方修士时按种族一类的东西直接挂上去。四种写法共用同一张登记表、同一份校验、
同一套行为探针——`tools/验证规则层.py` 的「载体验证」就是拿同一条规则四种写法各跑一场，
要求结果一样；单元测试另外从服务入口把固有规则钉住（生效、写重报错、行级规则写进单位报错）。

**加一条规则 = 写一行数据**（只要它落在已有拦截点上）：整层没有一条规则需要写 Python。
只有**新增一种拦截点**才动代码，那相当于新增一个原子能力。

**条件对两种载体一视同仁，而且不许为空**：没有条件的规则拦的是这一处的**全部**请求
（`不可禁用` 第一版就是这样顺带把改冷却、改名称也拦了）。

**可空参数的占位符要独占一条条件。** 参数留空（`允许空`）时，**含它的那条条件整条丢掉**，
语义是「这一项不设限」；所以它不许跟固定标签写在同一条里——留空会把固定标签一起吞掉，规则
就变成无条件拦截。实测踩过：`不受控制` 的条件写成 `[控制:真, 来源关系:$来源]`，卡里不写来源
时整条被丢，结果它拦掉了**所有**状态（连自己挂的状态都挂不上）。启动期与判据都会拦下这种
写法（`不受行动条提前` 也踩过同一个坑：固定标签 `方式:增加` 会被一起丢掉）。

拦截点会把「这次请求」编码成标签（`来源关系:敌方`、`方式:增加`、`改写:取消`、
`字段:禁用`、`值:真`、`控制:真`、`类别:负面`、`资源:精神`、`限制:行动`、`计量:某某`…），
条件用 `标签条件` 匹配——所以规则层**不新增任何条件词汇**。当前十二个拦截点：`被选为目标`、
`行动条被改写`、`事件被改写`、`技能被改写`（行级）、`状态被添加`、`状态被移除`、
`资源被消耗`、`行动被限制`、`归属被修改`、`形态被切换`、`计量被修改`、`造物被召唤`。

**名字叫锁定技，机制照游戏王的「效果外文本」实现，判据只有一条：它不是效果**——不进效果
管线（不产生事件、没有触发点、不进连锁），所以效果无效 / 取消 / 转化 / 改数值够不着它；它由
规则读来做合法性判定，也没有发动时点（因此与「必发 / 可选」无关；三国杀那套「必须发动」的
语义**不采用**，必发在本引擎里是默认底色）。**注意「改不掉」不等于锁定技**：气机的属性加成、
形态的属性变化、战场环境的常驻能力都改不掉，但那只是因为**暂时没有能改它们的东西**，它们
仍然是效果。

所以这一层的发行量也由两个数字管：**最多几种**（只有 12 个拦截点，想要更多种类得加拦截点，
那是代码，不是把别的机制也叫成锁定技）、**每条几个载体**（`名额` 是卡的发行量、`种族名额`
是种族的发行量，默认 1，判据每轮打出两笔用量，超一个就红）。

登记表自洽由启动期与 `tools/架构审查/检查规则层.py` 共用同一份校验：归属与拦截点相符、
处置合法、优先级唯一、`可改写` 只指向已登记规则、条件按原子能力契约逐条校验、
参数不许有死项、行级规则必须真的有读它的技能行（行级载体只有 `主动技能`，加一种载体要动代码）。行为由 `tools/验证规则层.py` 验：
每条规则按自己的拦截点落进标准探针场景，跑「声明 / 不声明」两场，两个方向都要成立；
再拿同一条规则四种写法各跑一场，要求**写在哪不影响结果**。

## `属性.json`

每个键就是属性引用名。定义中的 `默认值` 用于补齐参战者未显式覆盖的属性，**也是这个属性的
基准值（不增不减的那个值）**，`最低值/最高值` 是合法边界，`显示` 和 `单位` 供界面解释。

`口径` 声明引擎**怎么读**这个属性（合法取值与读法见下表）：

| 口径 | 基准 | 读法 | 例子 |
| --- | --- | --- | --- |
| 数值 | 各自 | 直接参与加减与曲线 | 攻击、防御、速度、各类上限、固定穿透 |
| 加成 | **必须 100** | `×比值`，卡面写 120 就是 +20% | 伤害加成、技能威力、治疗加成、护盾强度 |
| 倍率 | 各自 | 本身就是倍率 | 暴击伤害 150 = ×1.5、连击伤害 100 = ×1.0 |
| 概率 | 0 | 百分点相抵 | 暴击率、格挡率、连击率（命中率自己那条是 100 = 必中） |
| 减免 | **必须 0** | `- 比值` | 伤害减免、格挡减伤、韧性、冷却缩减、精神消耗修正 |
| 比率 | **必须 0** | 直接当比率 | 比例穿透 |

**加成类的基准是 100，减免/比率类必须是 0**：减法没有 100 基准（「没减免」要是 0 而不是
100，否则一减就把伤害乘成 0）。启动校验按这条锁死，写错会直接拒绝启动。

`属性.json` 的引用者包括：

- `角色/规则/主体/人物.json.属性覆盖`；
- `角色/规则/成长/修士修炼.json.属性成长`；
- 世界中的道侣和敌人 `属性覆盖/实力波动.属性`，以及灵兽敌人的 `每级成长`；
- 气机 `固定属性加成.属性`；
- 卡片能力树中的属性读取、修改、聚合；
- `战斗/展示/战报.json` 的属性摘要和百分比显示。

## `资源.json`

资源不是属性的别名。资源保存当前值，属性提供上限：

```text
血气 -> 血气上限
精神 -> 精神上限
护盾 -> 护盾上限
```

`角色/规则/主体/人物.json.资源` 决定初始资源值，`战斗/规则/行动.json` 决定行动开始恢复所读取的属性，战斗能力负责消耗、恢复、转移和设置资源。

## `事件.json`

事件定义两类契约：

- `携带事实`：监听器能够读取什么；
- `可修改`：事件改写能力允许改变什么。

监听节点按事件名订阅窗口。删除或改名事件会使相应监听失效；新增事件必须同时有核心实际派发点，否则只是无法触发的声明。

`战场形成`、`地势承伤后`、`地势变化前`和`地势变化后` 是环境生命周期事件。其中承伤事实用于战报与其他监听观察，不允许监听器改写阶段计量。

## `原子能力.json`

每项原子能力声明：

- `类别`：装配、组合、读取、选择、效果等；
- `执行器`：Python 通用执行语义；
- `字段`：允许字段、类型、默认值、必填项和嵌套限制。

卡片能力树中的 `能力` 必须对应这里的键。功法和真意可以同时使用装配节点、组合节点与监听节点；气机只使用 `固定属性加成`；器律只使用被动技能，被动技能的效果必须是监听节点。

## 与战斗规则的区别

定义回答“字段和语义是否合法”，`规则/战斗` 回答“合法语义怎样结算”。例如 `造成伤害` 是原子能力，命中上下限、防御常数和最低伤害属于 `战斗/规则/伤害.json`。

## 修改检查

1. 新增属性时确定默认值、边界、显示方式，并决定是否需要气机覆盖。
2. 新增资源时必须指定上限属性，并补充战报资源展示。
3. 新增事件时同时补核心派发、监听验证和战报分类。
4. 新增原子能力时同时补通用执行器、Schema 验证、卡片样例和边界测试。
