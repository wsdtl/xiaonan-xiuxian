# 战斗数据包

本包按组件维护数据，文件归属由 [组件.json](组件.json) 声明。数据集名是公共读取契约；编号、池文件名不随目录变化。

## 功能

### 一、启动期的基石校验
1. **启动顺序**：`CombatService.initialize()` 要求阵法核心已就绪（否则抛「阵法核心必须先于战斗核心启动」）；`load_battle_foundation` 再要求 JSON 数据已加载，并一次性 materialize `战斗定义` 与 `战斗规则` 两个数据集。（`game/core/combat/service.py`、`game/core/combat/foundation.py`）
2. **属性定义逐项校验**：每个属性只允许 `默认值`/`单位`/`最小单位`/`最低值`/`最高值`/`显示`/`口径`/`说明` 八个键，`默认值`、`最低值`、`最高值`、`口径` 缺一不可；`口径` 必须在已登记集合内；`加成` 口径的 `默认值` 必须是 100（`倍率` 口径不限），`减免`/`比率` 口径必须是 0；`默认值` 必须落在 `最低值`～`最高值` 内。（`定义/属性.json`、`game/core/combat/foundation.py`）
3. **资源定义逐项校验**：每个资源必须有 `上限属性`/`恢复前事件`/`恢复后事件`/`卡牌加成属性`/`受疗加成属性`，`上限属性` 与写了的 `加成属性`/`卡牌加成属性`/`受疗加成属性` 都必须引用已登记属性；`加成属性` 允许留空（表示不参与基准缩放）。（`定义/资源.json`、`game/core/combat/foundation.py`）
4. **事件定义字段与改写面**：每个事件只允许 `携带事实`/`可修改` 两个键，两项都不许重复；`可修改` 只能是 `当前数值`/`目标`/`标签`/`取消`/`类型` 的子集；只有 `恢复前`、`获得护盾前`、`资源恢复前` 允许带 `类型`，别的事件带 `类型` 直接报「没有可转化的共同结算语义」。（`定义/事件.json`、`game/core/combat/foundation.py`）
5. **原子能力词汇表自洽**：全部原子能力按 `原子能力.json` 逐条过 `RuleSchemaValidator`；所有已声明的 `执行器` 必须至少有一条原子能力声明，漏一个就报「执行器没有原子能力声明」。（`定义/原子能力.json`、`game/core/combat/foundation.py`）
6. **转移伤害的事件约束**：`转移伤害` 只能出现在 `造成伤害前` 或 `受到致命伤害` 的监听树里，`_validate_event_bound_abilities` 与构筑侧的 `_validate_event_binding` 各查一遍，越界即拒绝启动。（`game/core/combat/foundation.py`、`game/core/combat/builds.py`）
7. **行动规则字段锁死**：`行动规则` 只允许 13 个字段；`标准速度`、`最低有效速度`、`最高行动效率` 必须是正数，六个上限（追加攻击 3、事件链 32、能力链 64、触发技能嵌套 8、每方召唤物 6、战斗构造物 12）必须是正整数；`技能冷却` 必须逐字等于「`自身行动` + `行动开始`/`技能选择前`、每次减少 1 + `向上取整`」；主动技能轮转四项、被动结算六项的排序集合与长度都要完全吻合（这两处只在启动期校验，运行时排序键另有出处）；`行动开始恢复` 的资源名与属性名都必须已登记。（`规则/行动.json`、`game/core/combat/foundation.py`）
8. **时序字段锁死**：`时序` 只允许 `来源层级`/`主动技能`/`事件监听`/`阵法轮转` 四个键；来源层的 `来源` 不重复、`序位` 非负且不重复；主动技能执行时点必须是 `行动决策后` 的 `事件完成后`、五项排序齐全；事件监听必须是「事件创建后 → 事实提交前」、快照固定、新增监听延迟 1 个事件、同一监听递归跳过、事件转化另起新事件链、七项排序齐全；阵法必须 `行动结束` 后轮转、双方读同一战场快照后同时提交、冲击判定跳过六项、排序恰为 `方位序位`→`阵法编号`。（`规则/时序.json`、`game/core/combat/foundation.py`）
9. **伤害规则字段与关系**：`伤害规则` 的十个字段一个不多一个不少，全部非负（`防御常数` 可为零外其余必须大于零）；还要求 `最低命中率 ≤ 基础命中率 ≤ 最高命中率`。（`规则/伤害.json`、`game/core/combat/foundation.py`）
10. **五行集合与关系表**：`属性集合` 必须是木火土金水加无相、`根性字段` 与 `效果字段` 必须分别为 `五行根性` 与 `属性构成`、`无相规则` 必须是 `固定中性`；`相生`/`相克` 各五条且恰好覆盖木火土金水、来源不重复。（`规则/五行.json`、`game/core/combat/foundation.py`）
11. **环境规则六项锁死**：字段必须完整；`地表环境来源` 必须逐字等于「数据集 `地形分区` + 坐标字段 `坐标带` + 环境字段 `地形`」；`承载基准` 只能是 `["血气上限"]`；`承伤事件` 必须已登记且其 `携带事实` 包含 `承伤数值`；`排除来源身份` 只能是 `["战场环境"]`；`阶段方式` 必须是 `替换`。（`规则/环境.json`、`game/core/combat/foundation.py`）
12. **战场环境与中立性校验**：环境必须非空、只允许 `编号`/`名称`/`说明`/`阶段`，`编号` 必须等于索引键、`名称` 非空且不重复，`阶段` 必须非空且阶段名不重复，阶段只允许 `名称`/`起始承伤比例`/`入阶能力`/`常驻能力`，`起始承伤比例` 第 0 段必须是 0 且之后严格递增；`入阶能力` 只能用 `组合`/`引用`/`效果` 三类节点，`常驻能力` 只能挂 `监听事件`；中立性检查禁止 `选择目标.范围` 取 `自身`/`己方`/`敌方`/`关联对象`/`主人`/`控制者`，也禁止 `读取数值.来源` 取 `自身属性`/`效果来源属性` 或以 `自身当前`/`自身已损失` 开头。（`内容/战场环境/`、`game/core/combat/foundation.py`）
13. **状态反应空表可启动**：`规则/状态反应.json` 当前是空数组；校验只要求它是数组、每条反应名称非空不重复、`需要状态` 至少两项不重复、`消耗层数` 是非负整数、`生成状态` 会被当成一次「添加状态」节点校验、`效果` 逐条过节点校验。（`规则/状态反应.json`、`game/core/combat/foundation.py`）
14. **战报目录反查事件**：`BattleReportCatalog.from_mapping` 装载期读战斗展示数据集的战报一项，并用 `战斗定义.属性` 当百分比属性的基准来源；`initialize()` 末尾再调 `validate_event_kinds(tuple(engine.catalog.events))`，要求战报登记的事件类型与 `定义/事件.json` 逐事件一致，不一致报「战报事件映射与战斗事件定义不一致」，直接拒绝启动。（`game/core/combat/catalog.py`、`game/core/combat/service.py`）

### 二、构筑契约与模板展开
15. **四方向契约**：`load_build_contracts` 要求 `构筑契约.json` 恰好声明 `功法`/`真意`/`气机`/`器律` 四项，多一项少一项都报「构筑契约必须正好声明功法、真意、气机、器律」。（`规则/构筑契约.json`、`game/core/combat/builds.py`）
16. **编号前缀与字段全集**：每类实体的编号必须以契约的 `编号前缀` 开头（功法 `40`、真意 `41`、气机 `42`、器律 `70`）；实体键集合必须与契约 `字段` **完全相等**（缺字段与多字段分开报出）。（`规则/构筑契约.json`、`game/core/combat/builds.py`）
17. **根能力与数量**：每项的根 `能力` 必须在契约 `根能力` 内——功法只能是 `主动技能`/`被动技能`，真意与器律只能 `被动技能`，气机只能 `固定属性加成`；有 `能力数量` 的类别（气机 1）必须正好这么多项，其余受 `最少能力` 1 约束；`要求主动技能` 为 true 的功法必须至少有一项主动技能。（`规则/构筑契约.json`、`game/core/combat/builds.py`）
18. **属性构成**：`属性构成` 必须是非空对象、键必须在已登记五行内、数值合计必须等于 100（误差 1e-6）；器律另有 `器阶`、`铸法` 非空与 `兽引` 非空字符串数组的额外要求。（`game/core/combat/builds.py`）
19. **权重唯一性**：`参与权重唯一` 为 true 的功法/真意/气机，`权重` 必须正整数且在该三类之间全局不重复（`weights` 表跨三段共用），撞号报「权重与某实体重复」；器律该项为 false，不参与唯一性检查。（`规则/构筑契约.json`、`game/core/combat/builds.py`）
20. **模板装载期展开**：`JsonDataService.initialize` 在快照冻结前调 `expand_build_section`，只对 `功法`/`真意`/`气机`/`器律`/`战场环境`/`伤势`/`丹药` 七段生效；含 `模板` 键的树先深拷贝再原地展开，展开结果逐个实体重新裹回只读并同步改写 `entities` 与 `entity_records` 两份索引；模板编号是 `43` 前缀加正文摘要的内容寻址值，循环引用、模板不存在、参数位置缺失都会展开失败。（`game/core/combat/service.py`、`game/core/combat/templates.py`、`game/core/data/service.py`）
21. **相冲与生成参数**：`GrowthService` 初始化时从 `构筑/生成.json` 读 `尝试上限` 200，从 `构筑/相冲.json` 读五条规则并校验「名称不重复、每组恰好两组、两组非空且互不重叠、引用编号真实存在于三类实体」；`random_companion_build` 最多试 200 轮，每轮只在无相冲时返回，超限抛「道侣个人修行池无法生成无相冲构筑」；同一份 `生成.json` 里的 `相冲规则`/`权重算法`/`候选去重` 三个字段没有任何代码读取——逆权重在 `game/core/pool/selection.py`、按编号去重由展开模式写死。（`规则/构筑/生成.json`、`规则/构筑/相冲.json`、`game/core/growth/service.py`）

### 三、行动、事件与阵法
22. **行动条推进**：`_action_window` 每次给每个存活且可行动的角色按 `行动效率` 累进行动条，取整后把余数夹在 `[0, 1-1e-12)`；就绪项按「首次到达时刻 / 负速度 / 阵营 / 序号 / 参战位序」排序出队，同一行动条可一次给出多个行动。（`game/core/combat/engine.py`）
23. **行动效率公式**：`efficiency = limit × 有效速度 / (有效速度 + (limit-1) × 标准速度)`，`有效速度 = max(最低有效速度 25, 速度)`，`limit` 取全局 `最高行动效率` 4 与角色 `战斗规格.行动效率上限` 的较大者；`寡敌应变` 再按额外敌人数追加、并按 `行动效率增量上限` 封顶。（`规则/行动.json`、`game/core/combat/engine.py`）
24. **一次行动的固定次序**：`_take_action` 依次是「行动开始」事件 → 按 `行动开始恢复` 恢复资源 → 递减全部技能冷却 → 未被限制时使用丹药 → 决定行动意图 → 「行动决策前」→「行动决策后」→ 执行技能或普通攻击 → 生命周期推进 → 「行动结束」→ 阵法轮转。（`规则/行动.json`、`game/core/combat/engine.py`）
25. **行动开始的恢复与冷却**：`_recover_at_action_start` 按 `行动开始恢复` 逐项读角色属性，值大于 0 才走一次带 `自然恢复` 标签的资源恢复；`_tick_cooldowns` 对每个在冷却的技能做 `max(0, 值 - 每次减少 1)`，并在由正转零时补发「技能冷却完成后」。（`规则/行动.json`、`game/core/combat/engine.py`）
26. **技能轮转与兜底**：`_next_skill_from_cursor` 从 `skill_cursor` 起循环正序找第一个「可用且精神够」的技能，找不到就按契约 `无可用行动` 回落到 `普通攻击`；技能真正用出去（`uses` 增加）后游标才按 `成功后偏移` 1 前进；技能施放失败也会补一次普通攻击；运行时的技能排序键取自 `时序.主动技能.排序`，被动装载排序是引擎里写死的 `结算顺序 → 装配位序 → 物品编号 → 能力序号 → 效果序号`。（`规则/行动.json`、`game/core/combat/engine.py`）
27. **行动决策的优先来源**：`_decide_action` 先按 `战斗规格.tactic` 的 `优先级` 降序找第一条条件成立、且能选到目标的规则；战术规则全不成立才落到技能轮转。（`game/core/combat/engine.py`）
28. **事件监听的执行窗口**：`context.event` 在事件创建后、事实提交前执行监听，监听集合取事件创建时的固定快照，新增监听延迟 1 个事件生效，同一监听递归跳过，事件转化在原事件提交后另起新事件链；排序为 `来源层级升序 → 监听优先级降序 → 结算顺序升序 → 参战位序 → 装配位序 → 物品编号 → 能力序号`。（`规则/时序.json`）
29. **来源层级序位**：`战场环境` 0、`阵法` 10、`功法` 20、`器律` 30、`真意` 40、`战丹` 50、`状态` 60、`战斗对象` 70、`战场规则` 80；主动技能在 `行动决策后` 的 `事件完成后` 按 `释放顺序 → 来源层级升序 → 装配位序 → 物品编号 → 能力序号` 执行。（`规则/时序.json`）
30. **运行期硬上限**：追加攻击每次主行动最多 3、事件链深度 32、能力链深度 64、触发技能嵌套 8、每方召唤物 6、战斗构造物 12，全部在启动期按正整数读入；运行时超限分别抛「战斗事件链超过安全深度」「战斗能力链超过安全深度」，追加攻击/触发嵌套/召唤物/构造物则静默拒绝。（`规则/行动.json`）
31. **阵法轮转时点**：`_rotate_formations` 在「行动结束」之后执行，只处理 `action_number >= next_rotation` 的活跃阵法；先按引擎里写死的 `阵营 → 方位序位 → 阵法编号` 排序定目标（`时序.阵法轮转.排序` 只做启动期等值校验），轮转间隔 = `基准周期 12 × 阶段轮转倍率 / 传导` 向上取整，再汇总冲击、落地伤害、播报、处理崩解；`next_rotation` 与轮转计数在选目标之前就推进，因此无目标的阵法也算轮转过一次。（`规则/时序.json`、`game/core/combat/engine.py`）
32. **行动限制**：`行动决策前` 允许改 `目标`/`取消`；被取消、或任一状态的 `行动限制` 命中 `行动` 时，只派发「行动跳过后」，不再执行技能或普通攻击。（`game/core/combat/engine.py`）

### 四、伤害流水线与边界
33. **唯一入口与固定七段**：`DamageEngine.resolve` 顺序执行「输出倍率 → 命中 → 暴击 → 防御 → 增减伤 → 格挡 → 边界与落地」，每段一个 `_*_stage`；命中/暴击/格挡三个判定统一走传入的 `judge`，不传就按 `rng.random() < 概率` 自判。（`game/core/combat/damage.py`）
34. **输出倍率只放大对敌伤害**：`raw = max(0, 数值)`，只有 `source.side != target.side` 时才乘 `输出倍率 340 / 100`，自伤不吃这一层。（`规则/伤害.json`、`game/core/combat/damage.py`）
35. **命中段**：`命中率 = clamp(来源命中率 - 目标闪避率, 最低命中率 20%, 最高命中率 100%)`，`基础命中率` 95% 只作为来源无该属性时的默认值；`能否闪避` 为 false 时不掷判定值、直接命中。（`规则/伤害.json`、`game/core/combat/damage.py`）
36. **暴击段**：`暴击率 = clamp(来源暴击率 - 目标抗暴率, 0, 1)`；暴击时 `倍率 = max(1, 暴击伤害 - 暴击伤害减免)` 再夹到 `最高暴击倍率 400%`，未暴击倍率恒为 1.0。（`规则/伤害.json`、`game/core/combat/damage.py`）
37. **防御段**：`无视防御`/`真实` 两种规则完全跳过防御；其余先算 `有效防御 = 防御 × (1 - 比例穿透) - 固定穿透`，非负时 `倍率 = 防御常数 / (防御常数 + 有效防御)`，为负时翻到 `2 - 常数/(常数 - 有效防御)`（等于加伤）。（`规则/伤害.json`、`game/core/combat/damage.py`）
38. **增减伤段**：`真实` 跳过；其余 `倍率 = clamp(伤害加成 - min(目标伤害减免, 最高伤害减免 80%), 0, 最高伤害倍率 400%)`。（`规则/伤害.json`、`game/core/combat/damage.py`）
39. **格挡段**：`格挡率 = clamp(目标格挡率 - 来源破格率, 0, 最高格挡率 80%)`；`真实` 不掷判定值；格挡成立时 `格挡减伤` 夹在 90% 以内，伤害乘 `1 - 减伤`。（`规则/伤害.json`、`game/core/combat/damage.py`）
40. **落地与过量**：结算后先托底到 `最低伤害` 1（原值大于 0 时），再依次扣护盾、扣血气，`护盾伤害 + 血气伤害 = 实际伤害`，超出部分记为 `overkill`；`bypass_shield` 可整段跳过护盾；`with_minimum_health` 与 `with_limited_damage` 供「保底血量」「伤害前裁定」两类改写重建资源变化。（`规则/伤害.json`、`game/core/combat/damage.py`）

### 五、五行与资源池
41. **根性生成**：`generate_five_elements` 要求 `算法` 必须是 `主次定值`，把 `主属性` 45、`次属性` 25、`余属性` 10×3 打乱后发到木火土金水，并校验五项之和等于 `总和` 100；`持久化来源` 与 `战斗实例来源` 两组字段只被等值断言，运行时「谁持久化、谁每次新生成」由各消费服务写死，人物/道侣把结果存进自己状态，灵兽/敌方修士每场新生成。（`规则/五行.json`、`game/core/combat/elements.py`）
42. **相生相克表**：`relation_maps` 把 `相生`（木→火→土→金→水→木）与 `相克`（木→土→水→火→金→木）转成两张映射，要求各自恰好覆盖木火土金水且来源不重复。（`规则/五行.json`、`game/core/combat/elements.py`）
43. **实体属性构成**：来源类别限 `功法`/`真意`/`气机`/`器律`，读的字段是 `属性构成`，缺省是 `{"无相": 100}`，继承层级为 `能力节点` → `实体`。（`规则/五行.json`）
44. **内容与池的装载**：`内容/功法/功法-*.json` 600 门、`内容/真意/真意-*.json` 600 道、`内容/气机/气机-*.json` 703 道、`内容/战场环境/*.json` 55 个，全部按编号实体列表进实体索引；三类方向各在 `池/道侣/`（264 个个人池，内容为六位实体编号列表）、`池/敌方修士/`（6 个）、`池/灵兽/`（6 个）下放资源池文件，后两者内容是别的池文件名，装载时递归展开。（`内容/功法/`、`内容/真意/`、`内容/气机/`、`内容/战场环境/`、`game/core/data/loading.py`）
45. **池的消费方**：`GrowthService.random_companion_build` / `redraw_companion_category` 按 `EXPAND_DEDUPLICATED` 展开编号池与源池并按 `1 / 权重` 抽取（`game/core/pool/selection.py` 的 `inverse_weighted_sample`，代码不读 `权重算法` 字段），`EnemyService` 用同一入口给每个敌对实例抽构筑，但敌对内容自身的抽取走 `random.choices(权重)`——权重越大越易中，方向与资源池相反，`PoolService.draw` 对缺 `权重` 或权重非正整数的实体报错。（`game/core/pool/service.py`、`game/core/pool/selection.py`、`game/core/growth/service.py`、`game/core/enemy/service.py`）
46. **环境进战斗**：`_prepared_field` 用 `environment_id` 到 `engine.catalog.environments` 里取环境，未登记报「战斗核心未登记战场环境」；`origin` 只允许 `地表` 或 `秘境`（地表必须给 `xy` 与海拔、地形，秘境不许伪造地表坐标）；`秘境默认环境` 只在启动期被要求字段存在、取值无人读取，实际环境编号来自世界服务按 `地形` 名匹配到的战场环境实体。（`规则/环境.json`、`game/core/combat/service.py`）
47. **环境承伤与阶段**：承载基准只按参战者 `血气上限` 求和（排除召唤物与构造物）并保底 1，运行时累计的就是 `受到伤害后` 的 `实际数值`，来源身份排除写死为「不是战场环境」；阶段一律用 `替换` 切换，升阶时派发 `地势变化前`/`地势变化后` 并结算新阶段的 `入阶能力`（目标为本次承伤者），旧阶段 `常驻能力` 随即失效。（`规则/环境.json`）

### 六、事件改写与状态反应
48. **事件分发与判定改写**：所有事件先过 `catalog.require_event`（未登记抛「战斗核心未登记事件」），再补默认事实并压栈；`修改事件数值` 支持 `设置`/`增加`/`减少`/`百分比`，字段不在该事件的 `可修改` 白名单里抛「不允许修改」，`转化事件` 只在 `恢复前`/`获得护盾前`/`资源恢复前` 之间互转；判定被 `judgement_overrides` 以 `必定成功`/`必定失败`/`反转`/`重掷取优` 改写，影响 `命中`/`暴击`/`格挡`/`概率`/`控制`/`连击`/`反击` 七类。（`定义/事件.json`、`game/core/combat/mechanics.py`）
49. **状态反应**：`_resolve_status_reactions` 只在「添加状态」成功添加或叠层之后调用；当前 `状态反应` 是空元组，循环零次，所以核心不会自动把两个状态合成为第三种；规则非空时要求新加的状态名在 `需要状态` 内、目标同时持有全部 `需要状态`、各自层数不低于 `消耗层数`（扣到 0 即移除），随后追加 `生成状态`、跑 `效果` 并派发 `状态反应后`。（`规则/状态反应.json`、`game/core/combat/mechanics.py`）
