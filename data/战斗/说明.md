# 战斗数据包

> 本说明只写现行规则与边界；历史变更见 git 历史，待补事项与缺功能见 [内容/待补内容.md](内容/待补内容.md)。

本包按组件维护数据，文件归属由 [组件.json](组件.json) 声明。数据集名是公共读取契约；编号、池文件名不随目录变化。

## 功能

### 一、启动期的基石校验

1. **启动顺序**：战斗核心启动时要求阵法核心已就绪，否则报「阵法核心必须先于战斗核心启动」；随后要求数据已经加载，并一次性装载 `战斗定义` 与 `战斗规则` 两个数据集。
2. **属性定义逐项校验**：每个属性只允许 `默认值`、`单位`、`最小单位`、`最低值`、`最高值`、`显示`、`口径`、`说明` 八个键，`默认值`、`最低值`、`最高值`、`口径` 缺一不可；`口径` 必须是已登记的取值之一；`加成` 口径的 `默认值` 必须是 100（`倍率` 口径不限），`减免` 与 `比率` 口径必须是 0；`默认值` 必须落在 `最低值` 到 `最高值` 之间。（`定义/属性.json`）
3. **资源定义逐项校验**：每个资源必须有 `上限属性`、`恢复前事件`、`恢复后事件`、`卡牌加成属性`、`受疗加成属性`；`上限属性` 以及写了的 `加成属性`、`卡牌加成属性`、`受疗加成属性` 都必须引用已登记的属性；`加成属性` 允许留空，表示这个资源不参与基准缩放。（`定义/资源.json`）
4. **事件定义字段与可改写面**：每个事件只允许 `携带事实` 与 `可修改` 两个键，两者的取值都不许重复；`可修改` 只能是 `当前数值`、`目标`、`标签`、`取消`、`类型` 的子集；只有 `恢复前`、`获得护盾前`、`资源恢复前` 三类事件允许带 `类型`，别的事件带 `类型` 直接报「没有可转化的共同结算语义」。（`定义/事件.json`）
5. **原子能力词汇表自洽**：全部原子能力逐条按统一的规则结构校验；凡是已经声明过的 `执行器`，都必须至少有一条原子能力声明，漏一个就报「执行器没有原子能力声明」。（`定义/原子能力.json`）
6. **转移伤害的事件约束**：`转移伤害` 只能挂在 `造成伤害前` 或 `受到致命伤害` 的监听树里；启动期与构筑期各查一遍，越界即拒绝启动。
7. **行动规则字段锁死**：`行动规则` 只允许 13 个字段；`标准速度`、`最低有效速度`、`最高行动效率` 必须是正数；六个上限必须是正整数——追加攻击 3、事件链 32、能力链 64、触发技能嵌套 8、每方召唤物 6、战斗构造物 12；`技能冷却` 的 `计量单位` 必须是 `自身行动`、`余数处理` 必须是 `向上取整`，并且必须逐字等于「在 `自身行动` 的 `行动开始` 与 `技能选择前` 各减一次，每次减少 1、余数 `向上取整`」；`主动技能轮转` 的四项与 `被动技能结算` 的六项（`监听优先级降序`、`结算顺序升序`、`参战位序`、`装配位序`、`物品编号`、`能力序号`），其排序集合与条数都要完全吻合，这两处只在启动期校验；`行动开始恢复` 里的资源名与属性名都必须已登记。（`规则/行动.json`）
8. **时序字段锁死**：`时序` 只允许 `来源层级`、`主动技能`、`事件监听`、`阵法轮转` 四个键；来源层级里 `来源` 不许重复，`序位` 必须非负且不重复；主动技能的执行时点必须是 `行动决策后` 的 `事件完成后`，五项排序齐全；事件监听必须在事件创建后、事实提交前执行，监听集合按 `事件监听` 的 `监听快照`（`固定` 为 true、`时点` 为 `事件创建`）取创建当时的固定快照，新加的监听按 `事件监听` 的 `新增监听` 的 `生效延迟事件数` 1 延迟 1 个事件才生效，同一条监听递归时跳过，事件转化另起一条新事件链，七项排序齐全；阵法必须在 `行动结束` 之后轮转，双方按 `阵法轮转` 的 `双方结算` 先读 `读取快照` 的 `同一战场`、再用 `提交方式` 的 `同时` 提交，冲击判定跳过六项，排序恰为 `方位序位` 再 `阵法编号`。（`规则/时序.json`）
9. **伤害规则字段与关系**：`伤害规则` 的十个字段一个不多一个不少，取值全部非负——`防御常数` 可以为零，其余必须大于零；还要求 `最低命中率` 不超过 `基础命中率`，`基础命中率` 不超过 `最高命中率`。（`规则/伤害.json`）
10. **五行集合与关系表**：`属性集合` 必须是木火土金水再加无相；`根性字段` 与 `效果字段` 必须分别是 `五行根性` 与 `属性构成`；`无相规则` 必须是 `固定中性`；`相生` 与 `相克` 各五条，且恰好覆盖木火土金水，来源不许重复。（`规则/五行.json`）
11. **环境规则六项锁死**：字段必须完整；`地表环境来源` 必须逐字等于「数据集 `地形分区`、坐标字段 `坐标带`、环境字段 `地形`」这三项的组合；`承载基准` 只能是 `血气上限` 一项；`承伤事件` 必须是已登记的事件，且它的 `携带事实` 包含 `承伤数值`；`排除来源身份` 只能是 `战场环境`；`阶段方式` 必须是 `替换`。（`规则/环境.json`）
12. **战场环境与中立性校验**：战场环境必须非空，每份只允许 `编号`、`名称`、`说明`、`阶段` 四个键；`编号` 必须与索引键一致，`名称` 非空且不重复，`阶段` 非空且阶段名不重复；单个阶段只允许 `名称`、`起始承伤比例`、`入阶能力`、`常驻能力`；`起始承伤比例` 的第 0 段必须是 0，之后严格递增；`入阶能力` 只能用 `组合`、`引用`、`效果` 三类节点，`常驻能力` 只能挂 `监听事件`；中立性检查禁止 `选择目标` 的 `范围` 取 `自身`、`己方`、`敌方`、`关联对象`、`主人`、`控制者`，也禁止 `读取数值` 的 `来源` 取 `自身属性`、`效果来源属性`，或以 `自身当前`、`自身已损失` 开头的取值。（`内容/战场环境/`）
13. **状态反应空表可启动**：`状态反应` 当前是空数组；校验只要求它是数组，每条反应的名称非空且不重复，`需要状态` 至少两项且不重复，`消耗层数` 是非负整数，`生成状态` 会被当成一次「添加状态」节点校验，`效果` 逐条过节点校验。（`规则/状态反应.json`）
14. **战报目录反查事件**：装载战报展示数据时，用战斗定义里的属性作为百分比属性的基准来源；启动末尾再逐个比对战报登记的事件类型与事件定义里的每一个事件，不一致就报「战报事件映射与战斗事件定义不一致」，直接拒绝启动。

### 二、构筑契约与模板展开

15. **四方向契约**：`构筑契约` 必须恰好声明 `功法`、`真意`、`气机`、`器律` 四项，多一项少一项都报「构筑契约必须正好声明功法、真意、气机、器律」。（`规则/构筑契约.json`）
16. **编号前缀与字段全集**：每类实体的编号必须以契约里的 `编号前缀` 开头——功法 `40`、真意 `41`、气机 `42`、器律 `70`；实体实际带的键集合必须与契约 `字段` 完全相等，缺字段与多字段分开报出。（`规则/构筑契约.json`）
17. **根能力与数量**：每一项的根 `能力` 必须在契约的 `根能力` 之内——功法只能是 `主动技能` 或 `被动技能`，真意与器律只能 `被动技能`，气机只能 `固定属性加成`；写了 `能力数量` 的类别（气机 1）必须正好这么多项，其余类别受 `最少能力` 1 的下限约束；`要求主动技能` 为 true 的功法必须至少有一项主动技能。（`规则/构筑契约.json`）
18. **属性构成**：`属性构成` 必须是非空对象，键必须在已登记的五行之内，数值合计必须等于 100（允许 1e-6 的误差）；器律另有 `器阶`、`铸法` 非空与 `兽引` 必须是非空字符串数组的额外要求。
19. **权重唯一性**：`参与权重唯一` 为 true 的功法、真意、气机，其 `权重` 必须是正整数，并且在这三类之间全局不重复（权重表跨三段共用），撞号报「权重与某实体重复」；器律该项为 false，不参与唯一性检查。（`规则/构筑契约.json`）
20. **模板装载期展开**：数据快照冻结之前先做一次模板展开，只对 `功法`、`真意`、`气机`、`器律`、`战场环境`、`伤势`、`丹药` 七段生效；带 `模板` 键的树先深拷贝再就地展开；展开结果逐个实体重新包成只读，并同步更新按编号与按记录的两份实体索引；模板编号是 `43` 前缀，按正文内容寻址，正文相同就得到同一个编号；循环引用、模板不存在、参数位置缺失都会让展开失败。
21. **相冲与生成参数**：成长服务初始化时读 `生成` 的 `尝试上限` 200，并在 `相冲` 里读五条规则，校验名称不重复、每条恰好两组、两组非空且互不重叠、引用的编号真实存在于功法、真意、气机三类实体中；为道侣随机生成构筑时最多试 200 轮，只有无相冲才返回，超过上限报「道侣个人修行池无法生成无相冲构筑」；`生成` 里的 `相冲规则`、`权重算法`、`候选去重` 三个字段没有任何代码读取——逆权重抽样与按编号去重都由选取逻辑自己决定。（`规则/构筑/生成.json`、`规则/构筑/相冲.json`）

### 三、行动、事件与阵法

22. **行动条推进**：每次推进时，每个存活且可行动的角色按自己的 `行动效率` 累积行动条，取整后把不足 1 的余数留在条上；就绪的角色按首次到达时刻、速度（快的在前）、阵营、序号、参战位序依次排序出队，同一轮推进可以一次给出多个行动。
23. **行动效率公式**：行动效率 = 效率上限 × 有效速度 ÷ (有效速度 + (效率上限 - 1) × `标准速度`)；有效速度取 `最低有效速度` 25 与实际速度中的较大者；效率上限取全局 `最高行动效率` 4 与角色战斗规格里 `行动效率上限` 的较大者；`寡敌应变` 再按多出的敌人数追加，并以 `行动效率增量上限` 封顶。（`规则/行动.json`）
24. **一次行动的固定次序**：派发「行动开始」→ 按 `行动开始恢复` 恢复资源 → 递减全部技能冷却 → 未被限制时服用丹药 → 决定本次行动意图 → 派发「行动决策前」→ 派发「行动决策后」→ 执行技能或普通攻击 → 推进生命周期 → 派发「行动结束」→ 阵法轮转。（`规则/行动.json`）
25. **行动开始的恢复与冷却**：按 `行动开始恢复` 逐项读角色属性，只有数值大于 0 才走一次带 `自然恢复` 标签的资源恢复；每个在冷却中的技能减 `每次减少 1`，减到 0 为止；某个技能由正值转到 0 时，补派发一次「技能冷却完成后」。（`规则/行动.json`）
26. **技能轮转与兜底**：从当前技能游标起循环正序找第一个「可用且精神足够」的技能，一个都找不到就按契约的 `无可用行动` 回落到 `普通攻击`；技能真正用出去之后，游标才按 `成功后偏移` 1 前进；技能施放失败也会补一次普通攻击；运行时的技能排序取 `主动技能` 的 `排序`，被动装载排序固定为结算顺序、装配位序、物品编号、能力序号、效果序号。（`规则/行动.json`）
27. **行动决策的优先来源**：先按角色战斗规格里战术的 `优先级` 从高到低找第一条条件成立、且能选到目标的规则；战术规则全不成立才落到技能轮转。
28. **事件监听的执行窗口**：监听在事件创建之后、事实提交之前执行；监听集合取事件创建当时的那一份固定快照，新加的监听延迟 1 个事件才生效，同一条监听递归时跳过，事件转化在原事件提交后另起一条新事件链；排序为 `来源层级` 升序、`监听优先级` 降序、`结算顺序` 升序，再按参战位序、装配位序、物品编号、能力序号。（`规则/时序.json`）
29. **来源层级的序位**：`战场环境` 0、`阵法` 10、`功法` 20、`器律` 30、`真意` 40、`战丹` 50、`状态` 60、`战斗对象` 70、`战场规则` 80；主动技能在 `行动决策后` 的 `事件完成后` 执行，顺序为 `释放顺序`、来源层级升序，再按装配位序、物品编号、能力序号。（`规则/时序.json`）
30. **运行期硬上限**：追加攻击每次主行动最多 3 次、事件链深度 256、能力链深度 384、触发技能嵌套 8、每方召唤物 6、战斗构造物 12，全部在启动期按正整数读入；**两条链到顶不是报错，是「不再往下」**——事件链到顶时这次事件照常发生并进战报、只是不再触发监听（事实留 `链深度跳过`），能力链到顶时这一层能力不执行（事实留 `能力链跳过`）；追加攻击、触发嵌套、召唤物与构造物则静默拒绝。上限必须覆盖设计出来的最深连锁并留余量，还要留在引擎抬高的进程递归预算之内（当前 8000 帧）。（`规则/行动.json`）
31. **阵法轮转时点**：在派发「行动结束」之后执行，只处理已经到达轮转时点的活跃阵法；先按阵营、`方位序位`、`阵法编号` 排序定目标（`阵法轮转` 的 `排序` 只在启动期做等值校验）；轮转间隔 = `基准周期` 12 × `阶段轮转倍率` ÷ `传导`，向上取整；随后汇总冲击、落地伤害、播报、处理崩解；轮转时点与轮转计数在选目标之前就推进，因此没有目标的阵法也算轮转过一次。（`规则/时序.json`）
32. **行动限制**：`行动决策前` 允许改写 `目标` 与 `取消`；行动被取消、或任一状态的 `行动限制` 命中 `行动` 时，只派发「行动跳过后」，不再执行技能或普通攻击。

### 四、伤害流水线与边界

33. **唯一入口与固定七段**：伤害结算顺序固定为输出倍率、命中、暴击、防御、增减伤、格挡、边界与落地七段，每段各管一件事；命中、暴击、格挡三个判定统一走外部传入的判定结果，没有传入时才按随机数小于概率自行判断。
34. **输出倍率只放大对敌伤害**：先把伤害值托底到 0；只有来源与目标阵营不同时才乘 `输出倍率` 340 ÷ 100，自伤不吃这一层。（`规则/伤害.json`）
35. **命中段**：命中率 = 来源命中率 − 目标闪避率，夹在 `最低命中率` 20% 与 `最高命中率` 100% 之间；`基础命中率` 95% 只在来源没有该属性时作为默认值；`能否闪避` 为 false 时不掷判定值，直接命中。（`规则/伤害.json`）
36. **暴击段**：暴击率 = 来源暴击率 − 目标抗暴率，夹在 0 与 1 之间；暴击时倍率取 `暴击伤害` 减 `暴击伤害减免` 后的值，最低不小于 1，再夹到 `最高暴击倍率` 400%；未暴击时倍率恒为 1.0。（`规则/伤害.json`）
37. **防御段**：`无视防御` 与 `真实` 两种规则完全跳过防御；其余先算有效防御 = 防御 × (1 − 比例穿透) − 固定穿透；有效防御非负时倍率 = `防御常数` ÷ (`防御常数` + 有效防御)；为负时倍率翻到 2 − `防御常数` ÷ (`防御常数` − 有效防御)，等于加伤。（`规则/伤害.json`）
38. **增减伤段**：`真实` 跳过这一层；其余倍率 = 伤害加成 − 目标伤害减免与 `最高伤害减免` 80% 中的较小者，再夹在 0 与 `最高伤害倍率` 400% 之间。（`规则/伤害.json`）
39. **格挡段**：格挡率 = 目标格挡率 − 来源破格率，夹在 0 与 `最高格挡率` 80% 之间；`真实` 不掷判定值；格挡成立时 `格挡减伤` 最多按 90% 计，伤害乘 (1 − 减伤)。（`规则/伤害.json`）
40. **落地与过量**：结算出的伤害先托底到 `最低伤害` 1（仅当原值大于 0 时），再依次扣护盾、扣血气，护盾承伤与血气承伤之和等于实际伤害，超出部分记为过量伤害；伤害落地时可以整段跳过护盾；「保底血量」与「伤害前裁定」两类改写各自重建资源变化。（`规则/伤害.json`）

### 五、五行与资源池

41. **根性生成**：`算法` 必须是 `主次定值`；把 `主属性` 45、`次属性` 25、`余属性` 10×3 打乱后发到木火土金水，并校验五项之和等于 `总和` 100；`根性来源` 必须恰好声明 `人物`、`道侣实例`、`灵兽`、`敌方修士` 四项，`持久化来源` 与 `战斗实例来源` 两组字段只做等值断言，运行时「谁持久化、谁每场新生成」由各消费方决定——人物与道侣把结果存进自己的状态，灵兽与敌方修士每场重新生成。（`规则/五行.json`）
42. **相生相克表**：把 `相生`（木→火→土→金→水→木）与 `相克`（木→土→水→火→金→木）转成两张关系表，要求各自恰好覆盖木火土金水且来源不重复。（`规则/五行.json`）
43. **根性倍率**：效果结算时按效果的 `属性构成` 把来源的五行根性加权折成一个根性分（按 100 折算），根性倍率 = 1 + (根性分 − `基准` 20) × `每点修正` 0.005，再夹在 `最低` 0.9 与 `最高` 1.4 之间；它与相生相克关系算出的倍率一起乘在能力数值上。（`规则/五行.json`）
44. **实体属性构成**：来源类别限 `功法`、`真意`、`气机`、`器律` 四类，读的字段是 `属性构成`，缺省按 `无相` 100 计；继承顺序是从能力节点向下到实体。（`规则/五行.json`）
45. **内容与池的装载**：功法 600 门、真意 600 道、气机 703 道、战场环境 55 个，全部按编号实体列表进实体索引；三类方向各在道侣池（264 个个人池，内容是六位实体编号列表）、敌方修士池（6 个）、灵兽池（6 个）下放资源池文件，后两者的内容是别的池文件名，装载时递归展开。（`内容/功法/`、`内容/真意/`、`内容/气机/`、`内容/战场环境/`）
46. **池的消费方**：为道侣生成构筑、以及重抽道侣类别时，都按去重展开后的编号池与源池、以 1 ÷ 权重 抽样（权重越小越容易中；`权重算法` 字段其实没人读）；敌方服务用同一入口给每个敌对实例抽构筑，但敌对内容自身的抽取按权重正比随机——权重越大越容易中，方向与资源池相反；池服务在实体缺 `权重` 或权重不是正整数时报错。
47. **环境进战斗**：按环境编号到已登记的战场环境中取用，未登记就报「战斗核心未登记战场环境」；环境来源只允许 `地表` 或 `秘境`——来源是 `地表` 时必须给出平面坐标、海拔与地形，来源是 `秘境` 时不许伪造地表坐标；`秘境默认环境` 只在启动期要求字段存在，取值无人读取；实际使用的环境编号由世界服务按 `地形` 名称匹配到的战场环境实体决定。（`规则/环境.json`）
48. **环境承伤与阶段**：承载基准只按参战者的 `血气上限` 求和（排除召唤物与构造物）并保底 1；运行时累计的是「受到伤害后」的 `实际数值`；来源身份一律排除战场环境自身；阶段一律用 `替换` 切换，升阶时派发「地势变化前」与「地势变化后」，并结算新阶段的 `入阶能力`（目标为本次承伤者），旧阶段的 `常驻能力` 随即失效。（`规则/环境.json`）

### 六、事件改写与状态反应

49. **事件分发与判定改写**：所有事件先要求已在事件定义中登记，未登记就报「战斗核心未登记事件」，然后补上默认事实再压栈；`修改事件数值` 支持 `设置`、`增加`、`减少`、`百分比` 四种方式，要改的字段不在该事件的 `可修改` 白名单里就报「不允许修改」；`转化事件` 只在 `恢复前`、`获得护盾前`、`资源恢复前` 三类之间互转；判定可以被改写成 `必定成功`、`必定失败`、`反转`、`重掷取优`，作用于 `命中`、`暴击`、`格挡`、`概率`、`控制`、`连击`、`反击` 七类。（`定义/事件.json`）
50. **状态反应**：只在「添加状态」成功添加或叠层之后才检查；当前 `状态反应` 是空表，检查循环零次，所以核心不会自动把两个状态合成为第三种；规则非空时要求新加的状态名在 `需要状态` 之内、目标同时持有全部 `需要状态`、各自层数不低于 `消耗层数`（扣到 0 即移除），随后追加 `生成状态`、跑 `效果` 并派发「状态反应后」。（`规则/状态反应.json`）

### 七、规则层（效果之外的常驻规则）

51. **一条规则 = 拦截点 + 条件 + 处置**：规则层登记表里每条规则声明 `归属`（`单位` 或 `行`）、`拦截点`、`处置`（`拒绝` 或 `允许`）、`优先级`、`可改写`、`条件`、`字段` 与 `卡面`；`条件` 用已登记的**条件原子**写（现在只用 `标签条件`），参数以 `$字段` 占位。**两种载体都必须写条件**：没有条件的规则拦的是这一处的**全部**请求，而卡面写的总比这窄，启动期直接拒绝。**加一条落在已有拦截点上的规则只写数据**，改动引擎只发生在新增拦截点的时候。（`定义/规则层.json`）
52. **拦截点决定载体**：拦截点表在代码侧，每个拦截点声明它读得到的载体；`被选为目标`、`行动条被改写`、`事件被改写` 只认单位级规则（写在卡面根能力 `规则文本` 的 `规则[]` 里），`技能被改写` 只认行级规则（写在能力行自己的 `规则[]` 里；行级载体目前只有技能行 `主动技能`，加一种载体要动代码）。载体写错、或行级规则落在没有声明 `规则` 字段的技能行上，启动期直接拒绝。（`定义/规则层.json`、`定义/原子能力.json`）
53. **拦截点把请求写成标签**：引擎在四处判定上按需询问规则——选目标时问候选、改行动条时问被改写的单位、取消 / 转化 / 改事件数值时问事件的承受者、改技能时问那条技能行；请求被编码成标签（`来源关系:敌方`、`方式:增加`、`改写:取消`、`字段:禁用`、`值:真`…），条件用 `标签条件` 直接匹配，所以规则不需要新的条件词汇。
54. **参数留空 = 不设限**：条件里的 `$字段` 在装载期替换成卡片声明的取值；`允许空` 的参数留空时，**含它的那条条件整条丢掉**（所以「来源不限」不必另写一条规则）。参数与条件在装配期校验：未登记规则、未声明参数、越界取值、重复声明都会当场报错，不会带进战斗。
55. **优先级与可改写都真有语义**：同一拦截点上按 `优先级` 升序依次问；先成立的结论只有在它把后一条列进 `可改写` 时才能被改掉。登记表校验优先级全表唯一、`可改写` 只能指向已登记的规则、且不许指向自己。
56. **锁定技由登记表渲染，整段在主动技能之上、一条一个 `•`**：卡面正文最前是「规则：」，**不管这条锁定技写在哪儿**（根能力 `规则文本`、被动技能行、状态定义、主动技能行），都进这一段，**一条一个 `•` 开头的行**；不是写在根能力上的那几份带尾注说清跟谁生灭（`〔被动：<名称>〕`、`〔随[<状态名>]〕`、`〔主动：<名称>〕`），同名写两处只印一次（**参战者固有规则不印**：它长在参战者身上，没有卡面可印）。渲染器不认识任何具体规则名，拿不到登记表就印「缺少登记表」，不会静默少印一段。（`定义/规则层.json`）

### 八、越界改写与两条链

57. **越界的事件改写是「拒绝 + 留痕」**：事件白名单写在 `定义/事件.json` 的 `可修改` 里；运行期不在名单上的改写（改数值 / 目标 / 标签 / 取消 / 类型）**不生效**，并在该事件的事实里留下 `改写非法`（写清哪个事件、哪个字段）。**声明本身写错仍由内容判据负责**，不靠运行期报错兜。
58. **池子按自己声明的集合抽**：资源池的集合是池子自己的属性，抽池子的人**不许**再传一个集合（`兽宝-*` 是基础物品、`丹药池` 是丹药，对照表在 `基础/读取规则.json` 的资源池字段表里）。

### 九、锁定技落在已有机制上（名字用我们的，机制用游戏王的）

**名字叫锁定技，机制照游戏王的「效果外文本」实现。** 名字沿用我们自己的口径（设计侧与卡面
都叫锁定技）；**语义不采用三国杀那一套**——三国杀的锁定技讲「必须发动」，而「必须发动」在
这个引擎里是默认底色（全部被动、环境常驻、阵法都必发，没有一处能写「可以不发动」），拿它
当判据等于没有判据。锁定技的判据只有一条——**它不是效果**：

- **不进效果管线**：不产生事件、没有触发点、不进连锁——所以「效果无效 / 取消 / 转化 /
  改数值」这一类改写**根本够不着它**（不是「免疫」，是「不在射程内」）；
- **由规则读它做合法性判定**：能不能被选为目标、能不能被改、能不能被禁——像召唤条件与
  属性那样，是卡片的结构性文字，不是「发生了什么」；
- **它不「发动」**：没有发动时点，所以「必发 / 可选」「强 / 弱」这些维度都与它无关。

**「改不掉」不等于锁定技**：一个效果改不掉，可能只是暂时没有能改它的东西。按这条标准重审全库：

| 机制 | 规模 | 它是效果吗 | 判定 |
| --- | --- | --- | --- |
| 规则层登记表（根能力 `规则文本` / 被动行 / 状态定义 / 参战者固有规则） | 40 条 | **不是效果**：不产生事件、没有触发点 | **是锁定技**，全库唯一一处 |
| `固定属性加成` | 703 处（全部在气机） | 是效果（装配型持续效果） | 不是——它只是**没有对手**：没有任何能力在改属性 |
| 被动技能 | 5679 条监听 | 是效果（有触发点、进事件链） | 不是 |
| 形态的属性变化 | 321 处切换 · 319 处带属性变化 | 是效果（「切换形态」本身就是个效果） | 不是 |
| 战场规则的监听 | 250 处 | 是效果（由效果创建，带监听） | 不是 |
| 战场环境的常驻能力 | 55 环境 · 217 阶段 · 392 条 | 是效果（场地级的监听） | 不是 |
| 状态（`行动限制` 93 处；`效果免疫` 已退役） | 行动限制 技能71 · 行动22 | 是效果（由「添加状态」产生） | 不是 |
| 开局带的战斗状态（战丹 / 长期伤势） | 战丹 160 · 伤势 260 | 是效果 | 不是 |
| 阵法 | 46 座 | 不是效果，但也不是技能：数值型场地机制 | 不是（另一类东西） |

**结论**：全库只有规则层是锁定技。想要一个效果真的改不掉，正确做法是**给它挂一条锁定技**，
而不是指望别人没有对应的能力。

59. **单位级规则有四处写法，写哪不影响语义**：卡面根能力 `规则文本` 的 `规则[]`、被动技能行自己的 `规则[]`、状态定义里的 `规则[]`、**参战者固有规则**（形状与前几处一样，直接写在参战者身上）。前三处跟参战者一起进战斗；状态那一处**跟状态一起生灭**（状态一没，规则立刻不再被问）；固有规则**不挂在任何一张卡上**，留给「种族天生如此」这一类内容。四处共用同一张登记表、同一份启动校验、同一套行为探针（规则层的行为验证工具拿同一条规则四种写法各跑一场，要求结果一样）；同一张卡或同一个参战者身上写了两遍同名规则当场报错，不挑一条悄悄用。行级仍然只有技能行 `主动技能`——`技能被改写` 这个拦截点问的是那一条技能，被动没有对应的运行期对象。（`定义/规则层.json`、`定义/原子能力.json`）
60. **效果免疫已退役，免疫类的判定一律走锁定技**：`效果免疫`（状态上的一个字段，只认 `伤害` / `恢复` / `负面状态` / `控制` 四个字面量）已退役——它与锁定技表达的是同一件事（「这类效果对我不生效」），留着就是第二条路。三张免疫卡（`磁极灵兆` / `青鸾灵契` / `四象灵契`）的状态改成在状态定义里挂 `不吃负面状态` 与 `不受控制` 两条锁定技；**拒绝时对玩家说的说法没变**（登记表的 `原因` 写着 `状态免疫` / `控制免疫`）。要写新的免疫，就登记一条锁定技挂在 `状态被添加` 上——能按状态名、类别、是不是控制、来源分别挡，比那四个字面量细得多。（`定义/规则层.json`）
61. **两种场地级机制留着没并进规则层**：`战场规则` 与 `战场环境的常驻能力` 都是**效果**，要它们改不掉应该给它们挂锁定技；而它们眼下没并进来，是因为**问「谁」没有唯一答案**——锁定技每一条都要回答「问哪个载体」，而它们是场地的、不是某个参战者的。要并进来，得先定它们的归属是「场地对全场生效」还是「挂在来源身上」。（`定义/规则层.json`）

### 十、锁定技的发行量是写出来的

62. **两个旋钮都写得出数字。** 种类由**拦截点个数**决定；同一条锁定技能让几个载体带，由登记表里那条规则的 `名额`（卡）与 `种族名额`（种族，只有单位级规则有）决定——**两本账分开算**，卡的闸门不被种族撑宽，两条渠道**连名字都不许重叠**（敌人的构筑里随时可能抽到带规则的那几张卡，同一张脸上写两条同名规则是启动期错误）。判据每轮把两笔用量都打出来（`不可被指定 卡0/1·族16/16` 这样），**超一个就红**：想多发一个，先在登记表里抬对应的那个数。要更多**种类**就加拦截点（代码，量级相当于加一个原子能力），不要把别的机制也叫成锁定技。
63. **常见需求走常见机制，别挤锁定技的名额。** 两条通道都不限量、也都有各自的口径：想表达「这条数值要一直算在基础里」用 `固定属性加成`；想表达「场地上一直有一条规则」用 `战场规则`。锁定技要给的内容只有一类——**判定本身不成立**；免疫类（控制 / 负面状态…）也归它，但请登记在 `状态被添加` 上，别再另开字段。（`定义/规则层.json`、`定义/原子能力.json`）
64. **第五个拦截点是「状态被添加」**：给别人挂状态之前问**被打上的那个单位**，请求摊成四类标签——`状态:<名称>`、`类别:<正面|负面|中性>`、`控制:<真|假>`、`来源关系:<自身|己方|敌方>`。于是「不受控制」「不吃负面状态」「只不受某一条」都能用现成的条件原子写，不必给引擎加词汇。被拒绝的状态**不落地**，只派发 `添加状态失败后`，原因由登记表的 `原因` 给出。（`定义/规则层.json`）
65. **拦截点一次补齐到十个，随后把方向补齐、再开第十一个点。** 又接了五个同形状的闸门（都在代码侧那一张表里登记 + 在判定处问一句），全部只写数据就能用；标准探针已从「**敌人对你**」扩到「**同伴对你 / 你对自己**」，于是同一个拦截点上「挡敌方 / 挡同伴 / 挡自己」是三条不同形状的锁定技；另有**状态被移除**（`原因` 分清除 / 消耗 / 到期 / 来源退场：不腐、治不好、诅咒摘不掉都靠它）：

| 拦截点 | 问谁 | 请求标签 | 已经登记的锁定技 |
| --- | --- | --- | --- |
| `被选为目标` | 候选自己 | `来源关系:*` | 不可被指定 / 不可被同伴指定 / 不可被自己指定 |
| `行动条被改写` | 被改写的单位 | `方式:*`、`来源关系:*` | 不受行动条提前 / 行动条不可被同伴改写 / 行动条不可被自己改写 |
| `事件被改写` | 事件的承受者 | `改写:*` | 不可取消 / 不可转化 / 不可被改写数值 |
| `技能被改写` | 那一条技能行 | `字段:*`、`方式:*`、`值:*` | 不可禁用 / 冷却不可被延长 |
| `状态被添加` | 被打上的单位 | `状态:*`、`类别:*`、`控制:*`、`来源关系:*` | 不受控制 / 不吃负面状态 / 不可被同伴控制 / 不可被同伴施加负面状态 / 不可被自己施加状态 |
| `状态被移除` | 状态挂着的单位 | `状态:*`、`类别:*`、`原因:*`、`来源关系:*` | 状态不可被清除 / 负面状态不可被清除 / 状态不可被同伴清除 / 状态不可被自己清除 / 状态不可被消耗 / 状态不到期 / 负面状态不到期 |
| `资源被消耗` | 被扣资源的单位 | `方式:消耗`、`资源:*`、`来源关系:*` | 不被抽取 / 血气不可被消耗 / 资源不可被同伴消耗 / 代价不可被自己支付 |
| `行动被限制` | 被限制的单位 | `限制:*`、`来源关系:*` | 不受行动限制 / 技能不可被限制 / 行动不可被同伴限制 |
| `归属被修改` | 被改归属的单位 | `字段:*`、`来源关系:*` | 归属不可被改 / 归属不可被同伴改 / 归属不可被自己改 |
| `形态被切换` | 要被切形态的单位 | `形态:*`、`来源关系:*` | 形态锁定 / 形态不可被同伴切换 / 形态不可被自己切换 |
| `计量被修改` | 计量记在谁身上 | `计量:*`、`方式:*`、`来源关系:*` | 计量不可被改 / 计量不可被同伴改 |

行为判据按拦截点自动分派场景（8 个单位级场景都已加上方向：敌方那一路照旧，同伴那一路把探针与目标摆在同一侧，自身那一路把探针与规则写在同一张脸上；`状态被移除` 场景按 `原因` 分派「清除 / 消耗 / 到期」三条探针），所以**再加一条落在这些点上的锁定技，代码与判据都不用动**；**要加一个新的方向、新的标签值或新的拦截点，先扩探针场景，再把标签登记进拦截点表**（判据会要求）。（`定义/规则层.json`、`定义/原子能力.json`）

66. **锁定技的第四处写法：参战者固有规则**。锁定技原来都要挂在某张卡或某个状态上（卡面根能力 `规则文本`、被动技能行、状态定义），而**种族那一类「天生如此」的东西没有卡可挂**。所以多一处写法：参战者自己带一份 `固有规则` 数组，形状与卡面 `规则文本` 一样（`名称` + 参数），从生成参战者的那一侧直接交进来。**同一张登记表、同一份启动校验、同一套行为判据**：写重了当场报错（同一处写两遍、或与卡面撞车），写错载体也当场报错（`不可禁用` 是行级规则，写进单位就是启动错误）。它**没有卡面**——不挂在卡上就没有可印的地方，所以卡面渲染与查看页里看不到它，那不是漏印。判据：规则层行为验证拿同一条规则**四种写法各跑一场**，要求结果一样（现在打的是「四种写法（没有规则时受伤害 1000）：规则文本 0 · 被动技能 0 · 状态·整场战斗 0 · 状态·1 行动 816 · 固有规则 0」）；单元测试另有一条从服务入口走完整条路（生效 / 写重报错 / 行级规则写进单位报错）。**第一批用户是种族**：`角色/规则/种族/种族.json` 是这张登记表，**当前 180 条、18 个族系**，其中 179 条 `天生规则` 非空、只有基准族人族是空数组，用这一处写法挂天生锁定技；强度按设计走「有负面就必须配至少一条强正面」，口径见 `角色/规则/说明.md` 的「种族」一节。**这里的条数不写死**：登记表会继续扩，准确条数以该文件为准（仓库自带的规则层审查脚本会把每条单位级规则的族用量打出来，那就是现状）。（`定义/规则层.json`、`定义/原子能力.json`）

67. **监听表只在状态真的挂了 `监听` 时才标脏。** 五路监听（被动 / 状态 / 战场环境 / 战斗对象 / 战场规则）汇成一张「事件 → 监听列表」的表，表脏了整张重编，而重编一次要走遍场上每个单位的所有被动；状态进出的六处出口按「状态上真挂了 `监听` 才标脏」处理，没有 `监听` 的状态进出不再触发重编。这条改动**没有语义**——监听表里本来就只有 `监听` 节点，所以它不需要新的行为判据，保护它的是语料通道。反过来记一条：**以后凡是往监听表里加东西的机制，必须一起改这个判据**，否则会漏编。（`规则/行动.json`）

68. **首领档就该比玩家满编：修行槽位是档次的表达，不是玩家专属的上限。** 同一个主体内部，档次越高修行槽位不得变少，功法 / 真意 / 气机三项齐全；超不超过玩家不是缺陷。**性能压力不许拿数据顶**——人数、槽位、档位这些数一个都不许动，要快就去改引擎的常数项与索引。（`角色/规则/主体/敌方修士.json`、`角色/规则/说明.md`）

69. **地形决定战斗节奏：输出倍率住在 `规则/地形.json`**。`伤害.json.输出倍率` 是**基准**（340），实际值 = 基准 × 地形百分比 / 100：**有名有姓的地势按特色配**（平原 150~155 出手干脆、峡谷 200、断崖 210、火山 230、熔岩谷 235），**无名之地（没有特殊地势，或场地没登记地形）走 `无相地势`，随进度加**——`无相地势.基础倍率` 150 + 等级 × `无相地势.每级加成` 0.5，等级越高出手越决、仗打得越快。倍率**同时乘在双方伤害上**，所以它是**节奏旋钮**不是强弱旋钮；以后嫌仗长嫌仗短就调这张表，别再动基准。每一档地形都要配到（判据查：漏配会静默落到无相那一档，「火山打得凶」这种设计就悄悄没了）；标准探针把节奏**钉死**在基准（战斗引擎有一条给判据用的节奏钉子），免得调地势把行为判据带偏。（`规则/地形.json`、`规则/伤害.json`）

### 十一、战斗速度：拷贝走快路径、监听候选按阵营并桶

这一节的各处改动都是**常数项**——语义与判定一条没改，改的全是「同一件事少花点时间」。快慢本身
不是判据，所以每一处都要能对着语料说「逐场一样」，护栏见第 72 条。

70. **事件事实、效果历史、技能对象这三处不再整棵深拷贝。** 事件事实要进战报，必须与调用方解耦（`添加状态` 会在派发之后接着改自己那份状态定义），所以拷贝跑不掉，但可以不做整棵树：**容器里只有字符串与数字时就地重建**（标量不可变，重建与深拷贝逐字等价），出现一个容器值才退回深拷贝。效果历史的节点则**根本不用拷**：它是本次调用现造的字典，除历史之外没有别的持有者，而读它的那一方（`回放效果`）自己会先深拷一份。技能对象（`复制技能`、形态切换）只复制**真会被就地改的三张字典**（行级规则 / 临时变化 / 属性构成），效果与代价这些元组共享——运行时改写技能走的是「整个字段换掉」，从不就地改元组里的字典，这一点有全语料兜底。

71. **监听候选按「阵营」在装配期并好，事件目标被改写时按位次补问。** 派发一条事件不必把整张监听表问一遍：监听自己写了「观察角色 + 阵营关系」，而谁和谁同侧是装配期就定死的，所以**预先按侧并好、按持有者索引**，派发时只做几次取值。代价是「漏给」静默无声——少问一条监听就是少一段结算，战报照旧能出。`修改事件目标` 会在派发途中把事件目标改掉，改完之后**位次在后的**监听里就有人重新符合条件；收窄版一开始按「事件开始那一刻的目标」定候选，于是漏问；改成「目标一变就整表重扫」，又会把**位次在前、当时已经问过且不合**的那些重问了一遍（同一场多出 30 条事件）。正解是候选**带位次**返回：目标一变就按新目标重算候选，再**只补位次在后面的那些**——原实现本来就是「每条约在它自己的位次上问一次」，不会回头。候选顺序与整张排序表逐条一致，同序是硬要求（结算先后决定结果）。

72. **判据：监听收窄对照（同一批语料跑两条腿）。** 它把「收窄候选」与「整张排序表」在**同一批 1967 场语料**上各跑一遍，逐场比抹名摘要（事件骨架 + 参战者快照 + 终局），一致才放行，已进全量核对的慢项（跑法与用途见 `tools/说明.md`）。**单场自测证明不了这件事**：1 组那场没有「改目标」的效果，两条腿当然一样。
73. **配置不许拿性能顶。** `玩法/讨伐/规则/讨伐.json` 的 `最多参与用户` 是 15；**组队上限 3 人、组团上限 15 人都是玩法口径，战斗快慢是引擎的事**。这与第 69 条同一条规矩：要快就去改引擎的常数项与索引，人数、槽位、档位这些数一个字都不许动。判据侧也**不写「上限必须是 15」这种断言**——那条线由玩法决策定，性能改动不该有能力去碰它。

### 十二、战斗日志只记重要的东西

74. **日志的闸门是数据里的一张名单，不是「记下来再藏起来」。** 事实键分两份写在 `展示/战报.json` 的 `标准化.记录事实`：`保留`（进日志）与 `丢弃`（明确想过、决定不记）。引擎在**记录那一刻**就按 `保留` 筛（战斗引擎与战斗上下文两条记录口共用同一份筛法，不是各写一遍），所以不在名单上的键既不进事件、也不进战报与落库记录——`玩法/探险` 存的那份战斗记录跟着一起瘦。三条自洽规矩在启动时校验：两份名单不许重叠；`标准化.内部明细`（屏上不许出现的账）必须也在 `丢弃` 里；`展示.伤害事实`、`标准化.百分比明细`、`标准化.倍率明细`、`标准化.紧凑事实` 里提到的事实键必须都在 `保留` 里。
75. **该省的省：内部账、掷点过程、伤害链中间值、死字段。** 丢掉的 42 个键分三类——**引擎记账**（`事件` / `来源` / `承受者` / `行动者` / `原始数值` / `当前数值` / `目标ID` / `对象ID` / `状态定义` / `标签` / `已取消` / `保留血气` / `左方` / `右方` / `行动` / `技能键` / `行动类型`，事件自己的字段已经带了同一件事）、**掷点过程**（`命中率` / `命中判定值` / `暴击率` / `暴击判定值` / `格挡率` / `格挡判定值`，结果已经记了命中 / 暴击 / 格挡）、**伤害链中间值**（`暴击后伤害` / `防御后伤害` / `增减伤后伤害` / `格挡后伤害` / `边界后伤害` 与防御内部 `原始防御` / `有效防御` / `防御倍率` / `伤害倍率` / `防御规则`；玩家要看的是原始伤害与实际伤害）、以及阵基内部与事件自身数值的重复项。**顺带删掉一个死字段**：战报每个事件都带的那份伤害漏斗明细没有任何一处消费（页面、查看页、判据都没有），它依赖的 `标准化.伤害步骤` 一并删掉。**事件骨架、简要行（页面的「战斗记录」）与参战者快照逐场一模一样**——玩家看得见的那层一个字没变。
76. **判据：战报记录对照（同一批仗跑两条腿）。** 裁剪最怕的是静默少记（少记一个键，战报照旧能出，只是那一行空了）。这条判据把同一批仗跑两遍——一遍全记、一遍按名单筛——要求骨架与显示层逐场一致，记下来的键全在 `保留` 里，并且**语料里出现的每个键都被决定过**（在 `保留` 或 `丢弃` 里）：冒出一个新键就红，逼作者做决定，免得新机制悄悄往日志里塞账、或者悄悄被丢掉。阵法与地势那些键在 1v1 语料里根本不出现，所以它同时跑战场环境与阵法（只抽卡面是盖不到的）。跑法与用途见 `tools/说明.md`。
77. **展示载荷也照同一套办法瘦：先量「谁真读」，再删。** 展示包是发给页面的重量，一条事件原先带九个键加一份事实；按字段对账后确认**「每条事件抄一遍时间」「抄一遍能力名」「序列号」「事件序号」这四个字段页面上一个都不读**，事实里的「事实键」（与标签同值）与「原值」也没人读，这四项已删。页面能拿到的信息一条没少（标签、显示串、色调、分类、正文、来源与目标的名字与颜色都还在）。护栏是**形状白名单**：`协议.事件字段` / `协议.事实字段` 声明载荷只许带什么，`检查战报展示` 的第 5 项逐条核，多一个少一个都红——**要加字段就先加进白名单**，加了就是协议变了。
78. **重复的按份数据收成载荷级的两张表。** 除了「没人读的」要删，还要处理「**人人各带一份**」的：角色颜色字典与来源/目标小字典原先每条事件各带一份。现在载荷带两张表——**演员表**（角色键 → 名字）与**调色板**（角色键 → 序号 / 颜色 / 前景色），事件只记「谁」（键），时间线条上的每条行动记「行动者键」，页面查表；表里含系统那一项（系统事件的来源）。键查不到时前端**当场抛错**，不安静画空白。协议版本 **4 → 5**（旧页面会拒绝渲染而不是画错），战报头与明细包各带一份表（各自自成一体）。判据加第 6 项：角色键必须查得到，两张表必须与战报自己写的参战者一致。
79. **快照只留会变的那一半，不变的去花名册。** 行动前后状态原先给每个参战者各存一份**完整**快照，两次快照里六成是同一个人的功法 / 招式 / 能力 / 属性列表。现在载荷多一份**花名册**（名字 / 阵营 / 队名 / 颜色 / 分组标题 / 功法能力分组，按人算一次），快照记录只剩**键 + 血气精神护盾 + 当前状态**三项；页面加载后用花名册合成完整记录（前端加载时合成，查不到档案当场抛错），判据侧同样先合再判。协议版本 **5 → 6**。判据加第 7 项「快照与花名册」。
80. **战报页面有服务端，展示包不进存档。** 战报页由二级组件（战报）与对应的玩法微服务承载，按编号从**存档战报现算**展示包，再照页面拼的路径切片（战报头 / 片段 / 事件 / 参战者 / 行动前后状态）。两处口径：**首屏只给片段头部信息**（时间线与参战者按需取）；**宗门战只存战报**，展示包按需重建。判据是单元测试里的两条：切片与一次算完整的展示包**逐项相同**、路由与页面拼的路径一一对应；静态资源审查另核下发 HTML 的模块必须带内容安全策略。
81. **战报页面是实时取的：一个接口、不缓存、没有离线模式。** 页面是实时查看的（缓存了玩家看的就是上一版），而且**多半只看一次、战报记录本身只留很短一段时间**。因此：五条路径并成**一个数据接口**（数据口带一个说明「要哪一份」的参数）、**服务端与页面都不缓存**（每次按存档现算，响应头禁止缓存）、**不提供离线与预览模式**。判据两条：五种画面与一次算完整的对应部分**逐项相同**（切片只许搬运）、接口只有一个且参数正好是页面拼的那几个。
