# 组件数据包

data 分两层：**顶层是七大类，大类里是组件**。修改战斗先进 `战斗/`，修改炼丹先进 `物品/炼丹/`，
不再从 29 个平铺目录里找一个。

```text
data/
  基础/     组件.json 定义/编号.json 定义/品级.json 读取规则.json 内容/ 展示/ 规则/
  世界/     组件.json 内容/ 定义/           ← 世界组件自己
            位置/ 组件.json 规则/ 展示/     ← 子组件
            行路/ 组件.json 定义/ 规则/ 展示/
  角色/     组件.json 内容/ 定义/ 规则/
  战斗/     组件.json 内容/ 定义/ 展示/ 规则/
  物品/     基础物品/ 组件.json …
            炼丹/   组件.json 内容/ 规则/ 展示/
            炼器/   组件.json 内容/ 规则/ 展示/
            阵法/   组件.json 内容/ 规则/ 展示/
  宗门/     组件.json 规则/ 展示/
  玩法/     交易/ 先天灵宝/ 切磋/ 培养/ 归元/ 托管/ 探险/ 易形/ 服丹/ 补天/ 讨伐/
            赠送/ 道侣/ 采矿/ 采药/ 铜雀台/ 闭关/ 队伍/    ← 各一份 组件.json
```

**组件名与大类同名时不再多一层**：`基础`、`世界`、`角色`、`战斗`、`宗门` 这五个组件的面直接
放在大类目录下，其余组件各占一层。所以 `data/世界/内容/…`（世界自己的地点）与
`data/世界/位置/规则/…`（子组件）同住 `世界/`——**大类既可以是组件，也可以装组件**。
判据见 `tools/架构审查/检查数据驱动.py` 的 `check_category_layout`。

扫描目录写的是**组件相对路径**（`["基础", "世界", "世界/位置", …, "物品/炼丹", …]`），
读取器据此发现每个组件自己的 `组件.json`，并让父目录扫描时跳过子组件。

每个组件拥有 `组件.json`，声明本包的数据集、路径、结构和实体类别。只建立需要的子目录：定义登记概念，规则保存裁定参数，内容保存实体和资源池，展示保存文本及界面契约。**字段契约是裁定参数，只能住 `定义/` 或 `规则/`，不进 `内容/`**（判据 `check_contract_placement`）。说明跟随所属数据，不创建空壳目录。

**两条公约只在这里写一次**，各组件的 `说明.md` 不再逐份重复：

1. 本包按组件维护数据，文件归属由 `组件.json` 声明；数据集名是公共读取契约，编号与池文件名不随目录变化。
2. 修改前先读对应领域说明，新增文件要更新本包清单；只在基础读取入口登记新组件，不把玩法规则放进基础。

**规则里的每个键都要有人读**（判据 `check_unread_rule_keys`）。
一条规则只有在有人读的时候才算规则：代码要读中文键就必须在源码里写出这个字符串，所以
「键名在 `game`/`launch`/`message`（`tools`/`tests` 也算消费者）里出现过、或者能被
`f"{prefix}系数"` 这类拼法拼出来」就是有消费者。**没人读的声明接上消费者，或者删掉**——留着它
比没有更坏，改数据的人会以为改了它就改了玩法。`定义/` 不适用这条：属性表、编号用途是按表
遍历的词表，不要求逐键有人读。

**展示文案同理**（`展示/**/文本.json`）：展示层按「节 / 键」取文案，没人取的字符串玩家永远
看不到，也算「声明了却没人执行」。分区名与按钮、分页按约定整份读，不在判定内。

## 组件说明要写功能

**每个组件的 `说明.md` 里要有一节 `## 功能`，按点写清这一包的中文逻辑**，便于逐条审改
（判据 `check_component_function_docs`）。写法：

```markdown
## 功能

### 一、<逻辑段：启动期 / 一次操作 / 结算 / 事务>

1. **<逻辑点名>**：谁触发 → 读哪份规则、按什么顺序判断 → 改哪些状态、落到哪里。
2. ……

### 二、<逻辑段>

3. ……
```

**不写代码**。说明是**中文逻辑描述**，不是实现的注解：

- 不出现代码路径与文件名（`game/...`、任何 `.py`），也不出现函数名、类名、异常名、变量名、
  内部字段名——这些是实现，改实现时说明不该跟着动；
- 反引号只留给**数据**：数据键与数据取值（`有效秒数`、`结算秒数`）、数据文件路径
  （组件内相对路径 `规则/切磋.json`、跨组件 `物品/炼器/规则/本命武器.json`）。本包读过哪些
  文件在文末的 `## 数据集` 表里统一列一遍，那张表的路径判据会逐条验存在；条目里点到具体
  文件是允许的（改数据的人要照着找），点到代码不行；
- 交互流程写「读 → 校验 → 写入」的中文步骤；边界写「不满足就拒绝（「原因」）」，原因直接写
  玩家看到的那句中文；
- 算法细节不进说明（例如「编号取某个摘要的前若干位」写成「同一请求重复提交回放上次结果」）。

**讲逻辑，不讲展示**：页面、文案、按钮、命令措辞都在 `展示/` 目录里，那里已经是唯一出处
（判据会拦下 `展示/文本.json`、`展示/按钮.json` 这类引用）。`展示/` 底下**被代码读取与校验**
的数据（如 `展示/行程.json` 的七段叙事模板）算逻辑，可以引用。

其他要求：

- 一条只说一件事，写成**可验收的点**；条目编号全篇连续（`1.` 到 `N.`），段标题只分节不重编号。
- **只写真实存在的逻辑**；没实现的不写。
- 字段名、数值、上限照抄数据，不改写、不约等。发现说明与实现对不上时，**说明是准的**——
  负责人直接改这段中文逻辑，实现照它改。

**这份说明是逻辑的事实源**：负责人改这里的中文描述，代码随后对齐；反过来代码改了也要回来同步。

## 组件说明的 Markdown 格式

说明要能直接交给 markdownlint（仓库根有 `.markdownlint.json`，只关掉行长限制），
判据 `check_component_markdown` 按同一套规则卡：一级标题唯一且在第一行；标题级别不跳级；
标题、列表、表格、代码块前后都留空行；代码块写语言（目录树写 `text`）并闭合；表格每行列数
与表头一致；没有连续空行、行尾空白与制表符；文件以单个换行结尾。**排版只由判据管**，
写说明时不用手数空行。

## 说明的层级与出处

`data/` 里的说明分两层，**各管各的，不重复**：

- **组件说明**（每个组件的 `说明.md`）：这一包**行为的唯一出处**。`## 功能` 一节按点写中文
  逻辑，负责人改这里、实现照着改；文末 `## 数据集` 表交代本包读过哪些文件。
- **领域说明**（`<组件>/<面>/说明.md` 与更深的 `<面>/<子目录>/说明.md`）：只讲**数据形态与
  分组**——这个子目录放什么、按什么分组、字段怎么组织、改动时要同步什么；不重复行为逻辑。

**两层都不引代码**（判据 `check_data_docs_no_code`）：`game/…` 与函数名、类名、异常名、
变量名都不进说明，工具入口（`tools/…`）与数据路径（`规则/xx.json`、`xy`、`z` 这类数据键与
符号）可以留。唯一例外是 `data/说明.md`——它是这套约定本身，要举例。

## 体量特征

战斗构筑卡片在内容文件中保存卡头和构筑模板引用；模板正文集中保存在战斗核心的只读模板库中，装载时展开供战斗和文本渲染使用。当前模板库按被引用闭包收敛为 328 条；构筑模板是现行存储契约，不是历史兼容层。

当前 `data/` 下共有 1790 份 JSON，其中 31 份 `组件.json` 是加载元数据，其余 1759 份为定义、规则、内容和展示数据。该口径只统计文件，不代表实体、资源池或卡片数量；实体数量应由正式数据装载结果确定。

模板主体按内容寻址并携带参数位置映射。共享仅发生在完全符合模板契约的正文之间；旧字段、旧模板格式和旧内部引用不作为第二种输入形态保留。模板编号、索引映射、参数绑定和展开结果必须与正式数据引用保持一致。

卡片 `说明` 里**只放卡头**（风味简介与五行），规则正文由能力树渲染，`查看` 现拼现显示——正文不会再出现"JSON 改了说明没改"的漂移。渲染规则见 `战斗/内容/文本规范.md`。

构筑显示名称属于卡片自身定义；底层模板只保存执行结构、参数和必要的数据键，不生成玩家可见名称。状态、计量、规则和判定是否共享，按战斗规则及实体作用域决定，不通过历史命名约定推断。

## 加载契约

1. 读取唯一入口 `基础/读取规则.json`，取得组件相对路径、编号定义和池引用字段。
2. 每包必须存在 `组件.json`，只注册本包路径；未登记目录、清单身份错误和越界规则拒绝加载。
3. 正式 JSON 必须唯一匹配一条规则。
4. 按稳定数据集、实体类别和池文件名交付，领域服务不解释目录布局。

组件清单是加载元数据，不计入业务文档数量。清单不虚构业务依赖顺序；快照建立后由领域服务检查真实引用，服务依赖由 `game/app.py` 装配。

所有组件的内容文件名仍全局唯一。实体引用保存稳定编号，池引用保存不带扩展名的文件名。目录迁移不改变身份或状态所有权。

维护目录里不留一次性改写脚本；历史数据改写只存在于 git 历史里，不得当作日常维护入口重跑。

## 顶层分类的解释权归谁（2026-10-12 加的对照表）

**判定标准**：《微服务边界规范》「**玩法领域的解释权归同名核心服务**」→ **数据跟着解释权走**。

**怎么测出来的**：把每个顶层分类的**路径字符串**（如 `世界/`）拿到 `game/**` 里数出现处数 ✓ ——
**中文对中文，不用任何命名约定** ✓。注意：相当一部分路径是**拼出来的**（不是字面量 ✓），所以下表的数只表示**最低限度** ✓。

**根因（一句话）**：**`data/` 是按「东西」分的（世界／物品／宗门／战斗），代码是按「业务」分的（world／asset／sect／combat），两套轴不一致** ✓。
所以才会出现「一道菜挂两头」：`意境` 是角色的事，却因为「看着像战斗的东西」住进了 `战斗/` ✓。

**处置原则（写在这里免得下一个人猜）**：

1. **评判一个概念该住哪，看解释权，不看它像什么** ✓；
2. **展示槽位**（`文本`／`按钮`／`图标`）**本来就该一处一份**，不算重复 ✓；
3. **同一个主体概念两头挂**才算病 ✓（如 `道侣`／`灵兽`／`敌方修士` 同时挂在 `战斗/…/池/` 与 `角色/规则/主体/`）✓；
4. **搬迁属上线后的事** ✓ —— 它牵动所有加载点与 170 条回执，爆炸半径最大 ✓；一次一类、可回退、三证齐 ✓。
