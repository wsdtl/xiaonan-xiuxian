# 组件数据包

data 分两层：**顶层是七大类，大类里是组件**。修改战斗先进 `战斗/`，修改炼丹先进 `物品/炼丹/`，
不再从 29 个平铺目录里找一个。

```text
data/
  基础/     组件.json 定义/编号.json 定义/品级.json 读取规则.json 内容/ 展示/ 规则/
  世界/     组件.json 内容/ 定义/           ← 世界组件自己
            位置/ 组件.json 规则/ 展示/     ← 子组件
            行路/ 组件.json 定义/ 规则/ 展示/
  角色/     组件.json 内容/ 定义/ 规则/
  战斗/     组件.json 内容/ 定义/ 展示/ 规则/
  物品/     基础物品/ 组件.json …
            炼丹/   组件.json 内容/ 规则/ 展示/
            炼器/   组件.json 内容/ 规则/ 展示/
            阵法/   组件.json 内容/ 规则/ 展示/
  宗门/     组件.json 规则/ 展示/
  玩法/     交易/ 先天灵宝/ 切磋/ 培养/ 归元/ 托管/ 探险/ 易形/ 服丹/ 补天/ 讨伐/
            赠送/ 道侣/ 采矿/ 采药/ 铜雀台/ 闭关/ 队伍/    ← 各一份 组件.json
```

**组件名与大类同名时不再多一层**：`基础`、`世界`、`角色`、`战斗`、`宗门` 这五个组件的面直接
放在大类目录下，其余组件各占一层。所以 `data/世界/内容/…`（世界自己的地点）与
`data/世界/位置/规则/…`（子组件）同住 `世界/`——**大类既可以是组件，也可以装组件**。
判据见 `tools/架构审查/检查数据驱动.py` 的 `check_category_layout`。

扫描目录写的是**组件相对路径**（`["基础", "世界", "世界/位置", …, "物品/炼丹", …]`），
读取器据此发现每个组件自己的 `组件.json`，并让父目录扫描时跳过子组件。

每个组件拥有 `组件.json`，声明本包的数据集、路径、结构和实体类别。只建立需要的子目录：定义登记概念，规则保存裁定参数，内容保存实体和资源池，展示保存文本及界面契约。**字段契约是裁定参数，只能住 `定义/` 或 `规则/`，不进 `内容/`**（判据 `check_contract_placement`）。说明跟随所属数据，不创建空壳目录。

## 组件说明要写功能

**每个组件的 `说明.md` 里要有一节 `## 功能`，写清这一包的代码逻辑，按点分类**，便于逐条审查
（判据 `check_component_function_docs`）。写法：

```markdown
## 功能

### 一、<逻辑段：启动期 / 一次操作 / 结算 / 事务>
1. **<逻辑点名>**：谁触发 → 读哪份规则、按什么顺序判断 → 改哪些状态、落到哪张表。（`game/core/xxx/service.py`、`规则/xxx.json`）
2. ……

### 二、<逻辑段>
3. ……
```

- **讲代码逻辑，不讲展示**：页面、文案、按钮、命令措辞都在 `展示/` 目录里，那里已经是唯一出处，
  说明里不再重复（判据会拦下 `展示/文本.json`、`展示/按钮.json` 这类引用）。要写的是：入口方法
  与调用顺序、校验与拒绝条件、数据驱动参数、状态与事务落点、跨服务依赖、边界与上限。
  **例外**：`展示/` 底下被代码读取与校验的数据（如 `展示/行程.json` 的七段叙事模板）算代码逻辑，
  可以引用。
- 一条只说一件事，写成**可验收的点**。
- 末尾用反引号标出**依据**：优先写实现它的代码（`game/core/<包>/service.py`、`game/features/<包>/…`），
  再带上它读的规则（组件内相对路径 `规则/闭关.json`，跨组件写完整路径）。判据会逐条验它是否存在。
- **只写代码与数据里真实存在的逻辑**；没实现的不写。
- 字段名、数值、上限照抄来源文件，不改写、不约等。发现说明与代码对不上时，**说明是准的**——
  负责人直接改这段中文逻辑描述，代码照它改。

**这份说明是逻辑的事实源**：负责人改这里的中文描述，代码随后对齐；反过来代码改了也要回来同步。

## 主要归属

| 大类 | 组件 | 内容 |
| --- | --- | --- |
| 基础 | 基础 | 全局编号、跨领域品级、读取入口与编写规范 |
| 世界 | 世界、位置、行路 | 地势、区域、地点、道路，以及位置页与行程 |
| 角色 | 角色 | 性别、主体、成长、突破、伤势、人物状态 |
| 战斗 | 战斗 | 原子定义、结算规则、构筑形状、环境、功法、真意、气机及战报 |
| 物品 | 基础物品、炼丹、炼器、阵法 | 物品分类与材料、丹药与丹方、器律与铸法、阵法与阵师 |
| 宗门 | 宗门 | 宗门规则及山门、灵藏、藏经阁、设施、生产、宗门战展示 |
| 玩法 | 交易、先天灵宝、切磋、培养、归元、托管、探险、易形、服丹、补天、讨伐、赠送、道侣、采矿、采药、铜雀台、闭关、队伍 | 各自的通用玩法规则与展示 |

地点子目录继续表达地点归属。数据包归属与服务解释权不同：世界包中的敌人由敌人核心解释，炼器包的器律由战斗核心执行最终能力。目录不要求与代码一一对应。

## 体量特征

模板化之后，四类卡片自己只剩下卡头、词条表与 `{"模板": "43…"}` 引用：**功法 306 ·
真意 296 · 气机 354 · 器律 8 = 964 个文件、390 万字符**；正文搬进了
`game/core/combat/template_data.py`（144 万字符 = 1300 份模板正文 + 簇表与面表）。两者相加占全库
JSON（1787 个文件、560 万字符）的约 95%。

搬走的是**存放位置**，不是选择本身：每张卡仍然自带完整战斗文本，同一套设计被多张卡
使用时正文仍然逐张复制——复制现在发生在模板库里（模板按正文摘要去重，逐字相同的才
合并成一份）。这是刻意的，不要为了压缩体积去引入中间层或共享片段。

卡片 `说明` 里**只放卡头**（风味简介与五行），规则正文由 `game/core/combat/card_text.py` 从能力树现算，`查看` 现拼现显示。正文不会再出现"JSON 改了说明没改"的漂移。渲染规则见 `战斗/内容/文本规范.md`。

词条命名跟这条选择配套：每张卡的**计量与状态逐实例唯一**，名字取"卡名前缀 + 场景词"（`九转归元`、`太白回元`），全库不重名。名字只描述本卡自己的池子，不许引用别的卡定义的名字——撞名会把互不相关两张卡的效果接在一起。`判定` 与 `规则` 是引擎按名字取用的口令，不参与改名。审查入口见 `tools/架构审查/检查词条作用域.py`。

实测结论，避免以后重复讨论（每条都是**那一轮当时**的量法，单位与基数保留原样）：

- 把计量上限与状态定义收回到"卡内词条表 + 运行时绑定"，净省约 6 万字符，只占当时四类卡片的 **0.5%**；体积不在这里。
- 把规则正文从 `说明` 里裁掉、改成渲染，省下 46 万字符，也只占 **4%**；体积同样不在这里。
- 四类卡片在裁掉正文前是 322 万字符；展开词条与内联机制把它推到 **1168 万字符**，模板化又把它收回 **534 万**（卡片 390 万 + 模板库 144 万）。体积与解析耗时都随卡片内容走，改文本的读法不会改变量级。

因此卡片正文的复制是刻意选择，不要为了压缩体积去引入中间层或共享片段。

## 加载契约

1. 读取唯一入口 `基础/读取规则.json`，取得组件相对路径、编号定义和池引用字段。
2. 每包必须存在 `组件.json`，只注册本包路径；未登记目录、清单身份错误和越界规则拒绝加载。
3. 正式 JSON 必须唯一匹配一条规则。
4. 按稳定数据集、实体类别和池文件名交付，领域服务不解释目录布局。

组件清单是加载元数据，不计入业务文档数量。清单不虚构业务依赖顺序；快照建立后由领域服务检查真实引用，服务依赖由 `game/app.py` 装配。

所有组件的内容文件名仍全局唯一。实体引用保存稳定编号，池引用保存不带扩展名的文件名。目录迁移不改变身份或状态所有权。

## 验证

先阅读所属说明，再修改正文或清单。新增组件同时登记入口；新增文件匹配本包规则。运行期间不热重载 JSON，修改后重启进程。

```powershell
.venv/Scripts/python.exe -X utf8 tools/audit_data.py
.venv/Scripts/python.exe -X utf8 -m pytest -q tests
.venv/Scripts/python.exe -X utf8 tools/验证契约引擎.py
.venv/Scripts/python.exe -X utf8 tools/架构审查/检查边界.py
.venv/Scripts/python.exe -X utf8 tools/架构审查/检查构筑形状.py
```

`pytest` 是开发期工具，不在 `requirements.txt` 中：`.venv/Scripts/python.exe -m pip install pytest`。`start.bat` / `start.sh` 只安装运行依赖，因此全新克隆后需要先补装 `pytest` 再执行第二条命令。

迁移映射与哈希保存在 `tools/一次性迁移/组件迁移清单.json`，只用于那次验收，不冻结后续合法数据编辑。一次性迁移脚本统一放在 `tools/一次性迁移/`，不得当作日常维护入口重跑。
