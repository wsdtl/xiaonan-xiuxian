# 命令层

`game/cmd` 只把玩家输入转换为玩法调用和协议中立回复。命令按领域分 `查看与工具`、`修行`、`关系`、`行动`、`战斗`、`炼制`、`宗门`、`特殊地点`、`后台入口`；二级组件沿用中文目录，跨组件基础设施用英文文件名。

## 二级组件

```text
组件/
  __init__.py   命令注册、文本解析、玩法调用、回复、router
  reply.py      复杂消息与按钮（按需）
  input.py      可独立测试的复杂语法（按需）
  site.py       Web 入口（按需）
```

`__init__.py` 是声明 `GameCommand` 的地方；唯一例外是「帮助」的 `branches.py`。`reply.py` 与 `input.py` 不得取得游戏服务，也不得反向调用命令回调。组件不建 `service.py` / `business.py`，不写自己的 `说明.md`：职责与边界写在 `data/玩法/<域>/<组件>/说明.md` 与本节。

## 域与 scope

目录按玩家领域分九类：`查看与工具/`、`修行/`、`关系/`、`行动/`、`战斗/`、`炼制/`、`宗门/`、`特殊地点/`、`后台入口/`。帮助里的 `category` 与目录一致，不再保留旧 `通用/专属/特殊地点/后台` 分类。

每条命令在 `metadata` 声明 `scope`，只有三个值：

- `通用`：不依赖具体玩法、对象或地点功能。
- `专属`：依赖某个玩法、对象或地点功能；具体在哪执行由守卫规则判断。
- `后台`：隐藏入口，不进玩家帮助。

`特殊地点` 是域，不是 `scope`；地点专属命令仍是 `专属`，由守卫规则限定到具体地点。后台命令必须 `hidden=True` 且不提供 `help`。不同组件注册同名命令由启动契约阻止。

三个例外：`修行/升阶` 只有命令，数据和规则归 `物品/`；`宗门/共用` 只有规则与展示，没有命令；`查看与工具/使用` 只有命令，使用档案在 `物品/规则/使用.json`，成功回执复用各玩法展示文案。

## 注册与元数据

- 三种注册器：`fullmatch` 整条匹配、`command` 匹配命令词与参数、`regex` 完整正则。QQ 按钮由适配器处理，不新增第四种。
- 公开命令必须在 `metadata["help"]` 登记帮助；后台命令不得进帮助注册表。
- 每条游戏命令必须在 `metadata["guard_rule"]` 声明 JSON 中存在的守卫规则；不受状态影响的入口用 `始终可用`。
- 托管命令按需声明 `metadata["hosting"]` 的活动与阶段。

## 按钮归属

玩家回复只允许三类按钮：

1. `位置` 与 `去` 成功抵达后的地点面板；
2. 业务组件在自身业务按钮后复现当前地点面板；
3. 其他组件只展示本业务内部存在直接下一步的强联动按钮。

三类之外不附加按钮。命令回调只组合玩法返回的动作，不解释地点功能；错误回复不附地点面板。

地点面板只按该地点 `可用功能` 生成：配了 `采药`/`采矿` 才出这两个按钮，特殊地点只配自己的专属功能；位置按钮不拼进地点面板，`附近`/`去` 等命令照旧。

## 分支控件

`branches.py` 是唯一在 `__init__.py` 之外声明命令的例外：任何含 `|` 的消息先进入它。它只按结构解析、出菜单；不查命令是否存在、不判断能否执行、不发送。

- **共享尾**：`去|前往 天衡城` → 两条都带 天衡城；只有最后一段可带参数。
- **全量**：`查看 清心散|小还丹` → 每段原样作为一条命令；裸段也原样收下，不判断它是不是命令。
- **共享头**：`>使用 黄品功法 1|2|3` → 第一段最后一个词是第一个值，前面全是前缀；前缀可以多词，后面每段是同一前缀的另一个单值。
- 第一段有空格进全量；第一段无空格进共享尾；整条以 `>` 开头进共享头。
- 共享尾的中间段不能带参数；共享头第一段必须同时有前缀和第一个值；空段、少于两段只按结构判错。
- **分支串属于展示区**：生成方必须用中文名/品级名，不写编号；编号只用于 help 与存储。分支控件不校验这一点，也不校验命令是否存在或能否执行。
- 菜单每条是无边框按钮，只填入、不发送；固定结尾「点一条填入，确认后发送」。
- 参数里不能出现 `|`，没有转义。

## 守卫与参数

**守卫先行，参数在后**：守卫回答「你能不能做」，参数回答「怎么做」。对做不了的人先报语法是噪声；卡上已有「查看帮助」兜底。这条是既定口径，不是缺陷。

## 展示口径（全局）

以下口径从「查看」组件推广到所有玩家回包，新增或改动命令按这条验收：

- **编号只在输入/存储/help 出现，展示区一律中文名。** `reply_composer` 对标题里的 6 位编号统一做一次 `display_name` 替换；命令正文仍不得手写编号。
- **实体引用用无边框命令，不用纯文本。** 能直接 `查看 <中文名>` 的对象，名字必须放进 `M.command`；按钮的 `command` 可以带编号，但标签必须是中文名。
- **栏目层级要真的分层。** `主动/被动/常驻` 这类能力段用 `section` 出 `>` 标题，不能作为 `> >` 正文行；并列阶段之间留空行。
- **数值来自数据或原子能力渲染器。** 增幅、触发、条件、倍率从规则树渲染，不写「增强一档」这类摘要；没有数据就不编中间字段。
- **特殊物品先看 `无品级`。** 特殊丹不印品级；用途、地点从 `使用规则` 取，同一地点有多条命令时写全。
- **单一事实源。** 目录/池名/实体字段已经有的事实，不再造同义字段；灵植的地形只在目录与 `灵植-<地形>` 池上。
- **展示块要测块，不只测文字。** 按钮至少断言 `DocumentMessage` 里的 `CommandLink.command`，不能只看渲染后的 Markdown。
- **删改编号先查存档引用。** 数据连续、旧存档映射、`database/` 红线一起看；没有委托方明确授权，不动存档。

## 约束

- 命令层不读写 SQLite、不解释人物状态 JSON、不把 QQ 私有事件对象传进核心。
- 需要身份时只收 `user_id`；玩家回包走 `send_game_reply(message)`，由 composer 前置人物头与命令标题，目标取当前 `reply_target`；系统推送走 `send_system_message(message, target)`。
- `reply_composer.py` 是发送边界的游戏层 composer；组件内的 `reply.py`/`input.py` 仍是纯适配模块，不取组合根服务。
- 命令标题前的图标固定为 `cmd`，不按帮助分类换图；游戏图标词表在 `game/cmd/icons.py`，只登记当前客户端能渲染的彩色图形（八卦符号是唯一单色例外），词表键统一用 `game.` 前缀。
- 栏目标题按三类收口：纯标题（默认）、`标题: 简短方向`（只在有歧义时）、单行通知（`inline_section`）；普通栏目一律“标题 + 下面正文”，不把字段值塞进标题。
- 每条玩家回包由 composer 按 `game/cmd/closings.py` 的业务表补 `ClosingBlock`；未登记来源模块才退回通用帮助提示，业务自带 `closing` 时原样保留且不重复追加，系统推送不加。
- 动作命令用明确动词；`去/前往` 只接受地点名或 `x y`，不计算路线、海拔或境界叙事。
