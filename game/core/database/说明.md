# 核心数据库微服务

本服务是所有玩法共享的本地持久化边界，不解释角色、物品、战斗或世界 JSON。它负责读取当前状态与位置，并把不同玩家的状态变化和位置变化连同一次幂等事务原子写入 SQLite。

## 表

```text
state_snapshot
  user_id + state_type + state_key  唯一定位一个状态
  state_json                         当前状态正文
  version                            乐观并发版本

committed_transaction
  transaction_id                     一次提交的稳定事务编号
  user_id + request_id               防止QQ或任务重试重复结算
  changes_json                       业务提交摘要与状态版本变化

player_location
  user_id                            玩家地表位置唯一身份
  x + y                              当前地表坐标
  version                            乐观并发版本
  updated_at                         最近位置变化时间

player_space
  user_id                            玩家当前空间唯一身份
  space_type                         地表或宗门洞天
  space_id                           非地表空间编号
```

数据库不建立账号表、角色表、背包表、功法表或每玩法一张表。QQID就是`user_id`；一般玩家资产通过状态类型和状态键扩展。位置因为存在 `xy -> 多个玩家` 的反向范围查询，使用唯一的结构化位置表和 `(x, y, user_id)` 联合索引，不在人物 JSON 中复制坐标。`player_location`保存地表坐标，`player_space`保存当前空间；两者只允许在同一事务中一起改变。共享实体的主键、名称和按实体类型定义的业务编号字段分别由表列或实体地址唯一承载，`value_json`只保存可变正文，读取接口再组成公共视图，避免 `编号`、`宗门编号`、`托管编号`、`宗门战编号` 等身份事实重复落盘。活动会话和结算记录同样以 `state_key` 唯一承载自身编号，正文只保存流程事实；玩家当前状态、最近记录和事务载荷中的活动编号属于指向该记录的引用，仍须保留。

## 状态边界

角色、人物行为状态、物品、修行所得、武器和阵法的状态都归属于玩家。每个 `state_type` 只能由一个核心服务声明写入权，启动时由 `game/app.py` 执行唯一归属审计；重复声明或未声明的状态类型都会阻止启动。角色服务拥有人物主体和角色资产写入权，资产服务拥有人物物资状态写入权，人物状态服务拥有人物行为状态写入权；探险与闭关核心分别拥有自己的会话、最近记录和结算事实。跨领域创建或结算仍把所有变化组成一笔数据库事务。任何命令或玩法不得直接写 SQLite。

创建人物时，角色服务只负责角色主体和编排；初始背包、功法库、阵法储备等资产突变由 `AssetService` 生成，再由角色服务把这些突变与角色、状态、位置放入同一原子事务。这样不会因为创建入口临时写入资产而破坏状态所有权。

普通物品使用 `inventory/<编号>:<品级>`，类别由 JSON 编号定义解析。功法所有权使用 `cultivation_library/<编号>`，只保存当前最高品级；未装配的真意和气机使用 `cultivation_reserve/<编号>:<品级>` 累计数量。当前装配聚合在 `cultivation/main`：功法换装不消耗所有权，功法升品时在同一业务事务中同步已装配槽位；真意和气机装配时消耗一份储备，被替换内容不退回。待覆炼器律使用 `law_reserve/<编号>` 并保存数量，本命武器及已覆炼器律聚合在 `weapon/main`。天地玄黄阵法使用 `formation_reserve/<编号>:<品级>` 合并数量，圣品阵法使用 `formation_reserve/<实例编号>` 独立保存真实材料投入；布阵后转为唯一的 `prepared_formation/main`，下一场正式战斗建立时原子清除。已掌握丹药使用 `knowledge/<编号>`。

## 事务边界

一次业务结算必须把所有相关操作放进同一个 `TransactionCommand`。异步玩法使用 `SettlementTransactionPlan` 明确归组角色或公共结果、奖励、参与者状态释放和不可变结算事实，缺少任一必要组都会在提交前失败。开始阶段先扣的消耗必须与会话和预计算结果同笔提交；结束阶段不重复扣除。`StateMutation` 和 `LocationMutation` 都显式携带目标 `user_id`，多人结算可以在一笔事务中修改多个玩家。每项操作带 `expected_version`，任一版本不一致则整笔事务回滚；相同请求编号只能幂等重放完全相同的事务。

读取不使用全局写锁；WAL 下不同连接可以并发读取。一条命令之内的读取还会**复用连接**：驱动器在消息开始时开启请求范围（`launch/adapter/request_scope.py`），本服务按「当时的库路径 + 线程」各留一条只读连接，消息处理完（含守卫拦下与业务抛错）统一关闭。省下的是每次重开库文件、重读分页器的固定开销；句柄不跨请求存活，两次请求之间换库（快照回档、测试换库）自然拿到新连接，请求范围之外（脚本、调度器、启动期）照旧每次新建连接。写入与建表恒走新建连接，事务语义不变。写入使用 `BEGIN IMMEDIATE`、进程内写锁和 SQLite 忙等待共同串行。批量状态读取每批最多三百个地址，避免不同 SQLite 构建的绑定参数上限差异。

数据库服务本身不监听 JSON 变化；JSON 更新必须重启进程后生效。数据库也不负责迁移旧业务表或旧人物位置，不保留兼容读取。
