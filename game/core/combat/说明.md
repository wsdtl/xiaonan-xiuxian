# 战斗核心微服务

`game.core.combat` 是第二个核心公共微服务。它不自行读取文件，也不拥有角色资产；初始化时消费已经完成加载的 `JsonDataService`，并负责解释战斗基石以及功法、真意、气机对战斗的影响。

```text
CoreServices.data
  -> load_battle_foundation(data)
  -> BattleEngine / DamageEngine / MechanismRuntime
  -> CombatService
  -> CoreServices.combat
```

战斗定义来自：

- `定义/战斗/属性.json`
- `定义/战斗/资源.json`
- `定义/战斗/事件.json`
- `定义/战斗/原子能力.json`
- `规则/战斗/伤害.json`
- `规则/战斗/行动.json`
- `规则/战斗/时序.json`
- `规则/战斗/状态反应.json`
- `规则/战斗/环境.json`
- `内容/战斗机制/*.json` 经 `core.data` 编号索引后展开
- `内容/战场环境/*.json` 经 `core.data` 编号索引后执行
- `game.core.formation` 提供的阵法节点规则与不可变战斗快照
- `展示/战斗/战报.json`

其他业务只能从 `game.core.combat` 包顶层使用 `CombatRequest`、`CombatantSpec`、`CombatBuildRef`、`CombatGroupSpec`、`CombatResult` 和 `CombatService`。`engine.py`、`models.py`、`mechanics.py` 等均为内部实现。编组是战斗请求级边界，成员仍由参战者快照提交；普通攻击保持合法敌方目标随机，机制目标可使用 `本编组主战者`，不会跨编组寻找辅助对象。

```python
result = await combat.execute(
    CombatRequest(
        left_team=(player,),
        right_team=(enemy,),
        seed=123,
        action_limit=2000,
    )
)
```

`CombatantSpec.build` 只携带功法、真意、气机和器律的稳定编号与实例信息；引用字段固定为 `CombatBuildRef.content_id`，战斗服务自行通过数据服务解析定义。阵法和恢复丹分别使用 `formation_id`、`medicine_id`。`CombatantSpec.gender` 是由角色业务准备的稳定快照值，只供声明两仪分支的功法作条件判定；战斗核心不推导、修改或持久化性别。参战者类别和二次战斗对象类别分别使用 `combatant_type`、`object_type`，事件类型继续使用 `BattleEvent.kind`，三者不能混用。战斗核心只处理行动条、技能冷却、事件、监听、状态、伤害、召唤、构造物、阵法和战报事实，不创建角色资产，也不参与评分和平衡。

构筑效果可以使用本构筑根节点的 `词条` 槽位表。`计量槽位`、`状态槽位`、`规则槽位`、`判定槽位` 由战斗服务在装配副本中绑定；核心执行器只处理计量、状态、规则和判定等操作单元。槽位内部键是逻辑名，玩家可见名称来自当前构筑定义，运行时作用域仍由参战者与构筑实例共同隔离。没有槽位表的旧 JSON 保持兼容，但新内容应优先使用槽位引用。

恢复丹由丹药核心转换成 `CombatMedicineSpec` 后随 `CombatRequest.medicine_definitions` 传入，战斗核心按调用方提交的正式选药策略，在实时资源低于阈值时执行恢复，不读取物品 JSON。实际服丹会产生带丹药编号、恢复资源、恢复比例和实得数值的`使用丹药后`事件。战丹由丹药核心转换成 `CombatStatusSpec` 并放入 `CombatantSpec.prepared_statuses`，战斗核心只执行状态属性和监听机制。共享纳戒扣除由服丹玩法原子提交；探险成功创建时清除首战已使用的待战战丹，创建失败则保留。

阵法通过 `CombatFormationSpec` 以战场级引用传入，不占 `CombatantSpec.build` 装配位。战斗核心把稳定引用交给阵法核心解析，只接收本场不可变的阵基承载、阵眼冲击、节点传导和阶段曲线；阵法正文、五品配置与圣品乘势均不在战斗核心解释。`时序.json` 统一规定四类角色构筑的来源层级、主动技能排序、事件监听快照和阵法轮转点。

## 战场环境执行

- 承载基准只在开战时求和所有正式参战者的 `血气上限`；护盾、召唤物、治疗和复活都不改写它。
- 每次 `受到伤害后.实际数值` 只计一次；来源身份为 `战场环境` 的伤害不会再推进环境。
- 单次大伤害可连续跨越多个阈值，必须按阶段顺序逐一触发入阶能力。
- 常驻监听使用替换制，阶段变化后只编译当前阶段，不叠加旧阶监听。
- 环境压力以恢复、护盾、判定、冷却、行动条和状态反应为主。环境伤害必须由暴击、闪避、破盾或施法等具体事件触发，不使用全场统一伤害倍率。

## 战报事实保证

- `定义/战斗/事件.json` 是事件全集，`展示/战斗/战报.json -> 标准化` 必须逐项声明分类和显示名；初始化时两边少项、多项或残留旧事件名都会直接失败。
- `展示/战斗/战报.json` 是战报名称、分类、颜色、界面文案和默认选项的唯一来源；作者字段使用中文，英文稳定标识只进入后端展示协议，不直接显示给玩家。
- 后端生成完整的 `game.battle_report.presentation` v4 展示对象，负责中文名称、显示数值、时间文本、血条比例和默认选项；`static/battle-report` 只请求数据、建立界面和处理交互。
- 公开战报不提供原始记录入口；内部机器字段和调试记录只允许进入开发者工具或天道后台。
- 伤害、恢复、资源消耗和状态变化只按`展示/战斗/战报.json -> 标准化.结算事件`指定的最终事件统计，不把前置判定、承受方镜像事件或资源总线事件重复计数。
- 阵法冲击以阵法编号作为事件来源，在战报中拥有独立的承载、余承、冲击、节点、轮转和崩解事实，不归到参战队长的个人伤害。
- 展示时间线只重放结构化事件中的前后数值；最后一个事件后的血气、精神和护盾必须与 `CombatResult` 最终快照一致。
- 功法、真意、气机和器律在战报中保留各自来源类别；机制同时保留稳定编号和显示名称。

公共验收命令：

```powershell
.\.venv\Scripts\python.exe "tools/战斗校验/验收战斗核心与战报.py"
```
## 公共编组

`CombatGroupSpec` 是所有战斗模式共用的战斗请求结构，不属于任何玩法专属模型。探险、讨伐、宗门战和未来的直接战斗都可以提交多个编组；每组保存成员与主战者编号，战斗核心只负责边界校验、目标范围和结果归属。地点、讨伐或其他玩法可以生成自己的业务成员，但必须转换为这份公共契约，不得另定义一套编组实体。
