# 启动契约

`game/startup` 只保存跨命令、跨核心服务和全量 JSON 组合后必须成立的启动契约。所有检查在服务装配完成、正式接收请求前执行；任一失败都会终止启动。

检查的具体实现只能放在 `contracts.py`，`__init__.py` 只导出公共入口。`game/app.py` 完成全部服务装配后只调用一次 `validate_startup_contracts()`，不得在各个服务或命令中散落同类启动检查。

## 构筑词条规则

### 词条槽位

构筑可以在根节点声明 `词条` 对象，按 `计量`、`状态`、`规则`、`判定` 分组。组内键是构筑本地槽位，值只保存该构筑的玩家可见名称和效果定义。机制正文通过 `计量槽位`、`状态槽位`、`规则槽位`、`判定槽位` 引用槽位，不直接写入另一构筑的词条名称。

槽位在构筑装配时绑定到当前 `CombatBuildRef` 实例；战斗核心复用操作单元，但不保存词条表，也不跨实例读取槽位。未声明 `词条` 的旧构筑继续按原字段执行，迁移完成后再逐批收口。

- 每个槽位必须有非空的 `名称`；可见名称的特异性在内容整理阶段维护。
- 槽位引用必须命中当前构筑同类别词条；不能回退到公共词条或其他构筑。
- 计量的产生、读取、结算必须使用同一构筑实例；状态、规则和判定修正同理。
- `startup` 只校核结构、归属和引用，不替构筑设计具体数值。

功法、真意、气机和器律属于构筑内容。构筑自身的主动技能、被动技能、状态、计量、裁定和构筑创建的战场规则，均属于构筑词条；伤害标签、事件文案和战斗核心执行器名称不属于构筑词条。

- 主动技能、被动技能和内嵌状态的名称与定义由内容整理阶段维护；启动阶段不重复扫描名称。
- 同一个构筑内部可以多次引用自己已经定义的词条，但只能有一个定义来源。
- 不同构筑不得通过同名状态、同名计量或同名裁定暗中联动。
- 构筑词条的运行时归属由构筑实例确定；同名词条即使出现于不同构筑，也必须使用不同的运行时作用域。
- 新增或修改的技能、被动名称不得与其他构筑重复；旧数据的重复改名在数据迁移阶段处理，不由运行时自动追加前缀。

血气、精神、护盾、攻击、防御、冷却、行动、暴击、格挡等战斗基础属性和事件名称属于公共核心术语，不参与构筑词条去重。

## 机制与构筑边界

战斗核心可以复用监听事件、增加计量、条件判断、阈值结算等通用执行能力，但通用执行能力不拥有具体构筑词条。

构筑之间允许通过真实战斗事件产生机制联动，例如“敌方暴击后触发本构筑被动”；不允许一个构筑读取、修改或结算另一个构筑的状态、计量或裁定。

一个构筑写入的每项计量必须能在同一构筑内找到对应裁定，除非该计量明确标记为只记录、不结算的事实。该闭环规则属于数据校核待接入项目，在接入前不得把它描述为已完成的启动检查。

## 运行时作用域

战斗装配时，每个 `CombatBuildRef` 都会得到唯一的 `实例`。实例是一次装配的作用域，不是内容编号，也不是玩家属性；同一个内容重复装配时必须使用不同实例。

- 技能和被动记录实例归属，事件监听按“参战者 + 实例 + 机制”去重。
- 构筑计量按“参战者 + 实例 + 计量名”存取；同名计量只在同一实例内可读写。
- 状态保留来源实例；叠加、转移、复制和移除不得跨实例匹配，除非节点明确声明允许跨实例。
- 通用执行器只接收并传递实例上下文，不生成或改写构筑名称。
- 事务快照必须完整保存和恢复实例作用域，回滚后不得遗留计量、监听或状态。

战斗核心已有的公共触发次数、行动条、技能冷却等属于战斗公共状态，继续使用各自的公共键，不套用构筑实例作用域。

## 启动校核范围

启动阶段当前只校核会阻断运行的契约：

1. 数据服务先完成全量 JSON 解析和实体索引构建。
2. 构筑词条类别、槽位定义和槽位引用可在当前构筑内解析。
3. 命令编号、数据库状态归属和守卫引用没有冲突。

构筑词条可见名称的特异性已在内容整理阶段完成全量核对；计量产生/读取/裁定闭环由战斗核心装配与运行时路径负责，启动阶段不重复执行内容审查。

错误信息必须包含冲突双方的构筑、编号、文件和字段路径，便于直接修正 JSON。

单个微服务自己的运行数据校验仍归该微服务所有。维护性审查可以调用启动契约的正式检查函数，但不得复制规则；不影响启动正确性的风格、目录和命名审查仍属于维护工具。
