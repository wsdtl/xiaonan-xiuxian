# 通信适配层

`launch/adapter` 定义与平台无关的公共契约，并承载各平台驱动器。业务只从这里注册命令、读取公共上下文、发送回复或主动推送。

## 公开出口

| 能力 | 名称 |
| --- | --- |
| 生命周期与处理器协议 | `BaseAdapter`、`BaseMessageHandler`、`AdapterSpec`、`AdapterHttpMount` |
| 三种注册器 | `MessageHandler`（`fullmatch` / `command` / `regex`） |
| 公共上下文与回复 | `MessageContext`、`ReplyTarget`、`SendOptions`、`SendRequest`、`current_message_context`、`current_reply_target`、`manager` |
| 统一身份端口 | `register_identity_resolver`、`route_fields`、`resolve_user_id`、`resolve_group_id` |
| 命令守卫 | `CommandGuardContext`、`CommandGuardDecision`、`register_command_guard`、`run_command_guards` |

`manager` 是 `AdapterReplyManager` 实例，按当前消息上下文选择真实驱动器回复器。QQ 字段只能通过 `launch.adapter.qq_protocol.depends` 显式声明。

`identity.py` 是框架唯一的身份查询端口：驱动器只调用 `route_fields`，
辅助路由启动时把 QQ 号/QQ 群号解析器注册进来；`launch` 不 import 业务模块。

## 三个驱动器、一份 QQ 协议层、一个通用原语

| 目录 | 驱动器名 | 入站方式 | 职责 |
| --- | --- | --- | --- |
| `local/` | `local` | 进程内直接派发 | 命令索引、匹配、结果捕获式回复；天道后台与托管借它触发正式命令 |
| `qq_wh/` | `qq` | 开放平台 HTTP 回调 | 路由、快速 ACK、Ed25519 验签与回调地址验证 |
| `qq_ws/` | `qq_ws` | 网关 WebSocket | 地址获取、opcode 状态机、心跳、分片、重连退避、关闭码 |
| `qq_protocol/` | 非驱动器 | — | QQ 协议层：命令表、事件解析、去重队列、回复链路 |
| `websocket.py` | 非驱动器 | — | RFC6455 客户端（握手、帧、掩码、Ping/Pong） |

一个驱动器一个文件夹，各带自己的入站知识，互不引用：`local` 不认 HTTP，两个 QQ 驱动器互不 import。启用哪些由 `.env` 的 `QQ_TRANSPORT` 决定：`webhook`（默认）/ `websocket` / `both`，`local` 始终启用。

## 故意保留的平行实现

`local/handler.py` 与两个 QQ 驱动器各自维护命令索引、消息匹配、入站解析和会话状态，这部分**刻意不共享**。入站字段、排队策略与回复通道本就不同，合并会引入一套并不存在的公共会话模型。

## 共享派发骨架

`shared_dispatch.py` 的 `MessageDispatchMixin` 收四段与驱动器会话无关的逻辑：

- `_callback_wrapper`：把注册项绑定到业务回调；
- `_execution_plan`：按 `block` 规则截取本次真正可能执行的回调；
- `_guards_blocked` / `_guard_blocked`：先统一过守卫，再产生任何业务副作用；
- `_call_rule`：把驱动器事件转换成业务函数可接收的参数并调用。

差异通过显式参数提供：`message_context`、`manager`、`raw_message`；共享代码不反向依赖驱动器。

## 一条消息的范围

`request_scope.py` 是消息处理范围的挂载点：组合根启动时用 `register_request_scope(开始钩子)` 登记。处理前依次开启，处理完按相反顺序收尾；守卫拦下、业务抛错、提前返回都会收尾，资源不跨消息存活。

两个入站入口各挂一次：`local/handler.py` 的 `LocalEventHandler.dispatch` 与 `qq_protocol/processor.py` 的 `process_message_event`。核心库的读连接复用就是这么接上的。

## QQ 共用命令表

`MessageHandler._register` 把同一业务回调复制注册到所有启用驱动器，所以业务只写一次 `GameCommand`。两个 QQ 驱动器共用 `qq_protocol/processor.py` 的 `QqCommandRegistry`：

- `processor.py`：共用命令表、事件入口、共用事件队列；
- `runtime.py` 的 `QqDriverRuntime`：单用户串行、并发上限、`event_id` TTL 去重。**单用户串行是硬要求**，同一玩家两条消息不能同时结算事务。
- `QQ_TRANSPORT=both` 时用引用计数：先关的传输不能拆掉另一个还在用的队列；回复统一走 `qq_protocol/manager.py` 的发送队列。

`qq_protocol/__init__.py` 刻意精简，只转发业务需要的名称；否则任何环节出问题都会让所有命令注册失败。

## 修改约定

- 新增驱动器：实现 `BaseAdapter` / `BaseMessageHandler`，在 `registry.py` 登记，复用 `MessageDispatchMixin`。
- 一个驱动器一个文件夹；平台特有概念只允许出现在该目录。
- 同一协议被两个以上驱动器使用时，单独开非驱动器目录，不复制第二份。
- 与平台无关的协议原语放框架级模块（如 `websocket.py`）。
- `launch` 不得静态引用 `game`；业务模块名由 `.env` 的路由配置提供。
- 改驱动器后跑 `tools/全量核对.py` 与相关 `pytest`。
- QQ 统一身份：`MessageContext.user_id` 是 QQ 号，`ReplyTarget.user_id` 是平台 openid；未建立路由时 QQ 命令由 `qq_protocol/processor.py` 拦截并提示重发。
