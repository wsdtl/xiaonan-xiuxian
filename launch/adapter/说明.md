# 通信适配层

`launch/adapter` 定义与具体通信平台无关的公共契约，并承载各自平台的驱动器实现。业务组件只从这里注册命令、读取公共上下文、发送回复或主动推送。

## 公开出口

`__init__.py` 只做名称转发，不放实现逻辑。业务代码从 `launch.adapter` 导入以下四类能力：

| 能力 | 名称 |
| --- | --- |
| 生命周期与处理器协议 | `BaseAdapter`、`BaseMessageHandler`、`AdapterSpec`、`AdapterHttpMount` |
| 三种注册器 | `MessageHandler`（`fullmatch` / `command` / `regex`） |
| 公共上下文与回复 | `MessageContext`、`ReplyTarget`、`SendOptions`、`SendRequest`、`current_message_context`、`current_reply_target`、`manager` |
| 命令守卫 | `CommandGuardContext`、`CommandGuardDecision`、`register_command_guard`、`run_command_guards` |

`manager` 是 `AdapterReplyManager` 实例，按当前消息上下文选择真实驱动器回复器。QQ 字段必须通过 `launch.adapter.qq_protocol.depends` 显式声明，不得扩散到这个出口。

## 三个驱动器、一份 QQ 协议层、一个通用协议原语

驱动器数量与 `available_adapter_specs()` 登记一致。`AdapterSpec.handler` 保存处理器**类对象**，框架以 `spec.handler.run()` 调用，因此处理器的注册与派发方法必须是 `@staticmethod`；改成实例方法会改变调用约定。

| 目录 | 驱动器名 | 入站方式 | 自己的职责 |
| --- | --- | --- | --- |
| `local/` | `local` | 进程内直接派发 | 命令索引、匹配、结果捕获式回复；天道后台与托管借它触发正式命令 |
| `qq_wh/` | `qq` | 开放平台 HTTP 回调 | FastAPI 路由、快速 ACK、Ed25519 验签与回调地址验证 |
| `qq_ws/` | `qq_ws` | 网关 WebSocket 长连接 | 网关地址获取、opcode 状态机、心跳、分片、重连退避、关闭码 |
| `qq_protocol/` | 非驱动器 | — | QQ 协议层：命令表、事件解析、去重队列、回复链路 |
| `websocket.py` | 非驱动器 | — | 与 QQ 无关的 RFC6455 客户端（握手、帧、掩码、Ping/Pong） |

一个驱动器一个文件夹：每个驱动器目录自带它那一侧的完整入站知识，互不引用——`local` 不认 HTTP，两个 QQ 驱动器互不 import。目录名用短名：`qq_wh` = webhook，`qq_ws` = WebSocket，驱动器名与目录名一一对应。

非驱动器只有两个，且都不含任何入站决策：`qq_protocol` 是 QQ 这个协议的公共实现（两个 QQ 驱动器都必须用它，否则业务组件会写出只对一种入站生效的命令），`websocket.py` 是协议原语（换一个平台做长连接可以原样复用）。

启用哪些由 `.env` 的 `QQ_TRANSPORT` 决定：`webhook`（默认）/ `websocket` / `both`，`local` 始终启用。默认保持 webhook 是为了让"新增驱动器"这件事本身不影响线上入站方式；要切网关长连接必须显式配置。

## 故意保留的平行实现

`local/handler.py` 与两个 QQ 驱动器各自维护命令索引、消息匹配、入站解析和会话状态，**这部分刻意不共享**。驱动器的入站字段、排队策略与回复通道本就不同，合并会引入一套并不存在的公共会话模型。

## 共享的派发骨架

`shared_dispatch.py` 的 `MessageDispatchMixin` 收纳与驱动器会话无关的四段逻辑，此前在每个驱动器里各写一份：

- `_callback_wrapper`：把注册项绑定到业务回调；
- `_execution_plan`：按 `block` 规则截取本次消息真正可能执行的回调；
- `_guards_blocked` / `_guard_blocked`：先统一过守卫，再产生任何业务副作用；
- `_call_rule`：把驱动器事件转换成业务函数可接收的参数并调用；
- `_short_text`：压缩日志正文长度。

差异通过显式参数提供，共享代码不反向依赖驱动器：

| 参数 | 含义 |
| --- | --- |
| `message_context` | 驱动器自己的 `MessageContext` 工厂 |
| `manager` | 驱动器自己的回复管理器 |
| `raw_message` | 驱动器事件里的原始正文 |

`_short_text` 的截断符统一为单字符省略号 `…`：此前 QQ 用 `…`、Local 用 `...`，同一功能在两处产生不同输出。

## 一条消息的范围（`request_scope.py`）

驱动器只知道「一条消息处理完了」，不知道业务要在这段范围里挂什么会占用句柄的资源。`request_scope.py` 是这段范围的挂载点：游戏组合根在启动时用 `register_request_scope(开始钩子)` 登记，处理一条消息前依次开启，处理完再按相反顺序收尾。

- 范围覆盖守卫与业务回调两条路径上的每一条出口——守卫拦下、业务抛错、提前返回都会收尾，因此登记来的资源不会跨消息存活；
- 开始钩子返回自己的收尾函数（`Callable[[], None] | None`），钩子自己的异常只记日志，不顶掉这条消息；
- 两个入站入口各挂一次：`local/handler.py` 的 `LocalEventHandler.dispatch` 与 `qq_protocol/processor.py` 的 `process_message_event`。

核心库的读连接复用就是这么接上的（见 `game/core/database/说明.md`）。框架本身不认任何业务资源，也不反向依赖 `game`。

## QQ 两个传输为什么共用一份命令表

`MessageHandler._register` 把同一业务回调复制注册到**所有启用驱动器**，所以业务组件只写一次 `GameCommand`，不能出现"只对某一种入站生效"的命令。两个 QQ 驱动器的三个注册器因此都写进 `qq_protocol/processor.py` 的同一张 `QqCommandRegistry`：

- `processor.py`：共用命令表、事件处理入口 `process_message_event`、共用事件队列；
- 队列是 `qq_protocol/runtime.py` 的 `QqDriverRuntime`：单用户串行、并发上限、`event_id` TTL 去重。**单用户串行是硬要求**，同一玩家的两条消息不能同时结算数据库事务；
- 共用模块级运行时用引用计数：`QQ_TRANSPORT=both` 时先关闭的传输不能拆掉另一个还在用的队列。

**回复链路与入站方式无关**：QQ 平台没有"WS 专用发送接口"，两个驱动器都通过 `qq_protocol/manager.py` 走同一套 OpenAPI 发送队列。

`qq_protocol/__init__.py` 刻意保持精简，只转发业务需要的公共名称。原因见该文件说明：`registry.py` 在**每个命令注册时**都会导入两个 QQ 驱动器，一旦这层顺手把 manager / render / payload 全链拉进来，任何一个环节出问题都会让所有游戏命令注册失败、服务起不来。

## 验证入口

改动驱动器后必须跑这五个脚本，它们都不访问真实平台：

| 脚本 | 覆盖范围 |
| --- | --- |
| `tools/行为验证/验证驱动器派发.py` | 三个驱动器的 `block` 截取、`_short_text` 与注册包装结果必须逐项一致 |
| `tools/行为验证/验证QQ传输开关.py` | `QQ_TRANSPORT` 各取值、默认值、非法值拒绝、两个 QQ 驱动器共用回复管理器 |
| `tools/行为验证/验证QQ双驱动器生命周期.py` | `both` 模式下两种启停顺序，共享运行时都不会被先关的那个提前拆掉 |
| `tools/行为验证/验证QQWebSocket.py` | 回环假网关上的握手、鉴权、心跳、事件派发、回复载荷、Resume 与清理 |
| `tools/行为验证/验证QQWebSocket关闭码.py` | 官方错误码决策矩阵：可 Resume / 必须重新 Identify / 停止重连 |

`验证QQ双驱动器生命周期.py` 单独存在的原因：`.env` 允许两个 QQ 驱动器同时启用，而
`lifespan` 是逆序关停的，先关的那个如果直接释放共享队列，后关的那个会当场失去事件
队列和发送线程池。这个引用计数是共享运行时唯一的存在理由，名字层面的开关测试查不出它。

两个 QQ WebSocket 脚本会自己把本次进程的入站强制设为 `websocket`，不依赖 `.env`：`MessageHandler` 只把回调注册到**当前启用**的驱动器，默认入站是 webhook 时脚本注册的测试命令不会进 WebSocket 的命令表。

`验证QQWebSocket关闭码.py` 的价值在于它按官方错误码表写期望值，而不是按实现写；
关闭码分支一旦改错，会出现"看起来在重连、其实每次都在硬 Resume 已被服务端作废的
会话"，从日志上很难发现。

## 修改约定

- 新增驱动器：实现 `BaseAdapter` / `BaseMessageHandler`，在 `registry.py` 登记 `AdapterSpec` 并加入 `QQ_TRANSPORTS`（或新增自己的开关入口），复用 `MessageDispatchMixin`；
- 一个驱动器一个文件夹。驱动器特有的概念（例如 QQ 的 `openid`）只允许出现在该驱动器目录内；
- 同一协议被两个以上驱动器使用时，为该协议单独开一个非驱动器目录（如 `qq_protocol`），不要复制第二份，也不要塞进其中一个驱动器里；
- 与具体平台无关的协议原语放框架级模块（如 `websocket.py`），不要藏进某个平台的驱动器目录；
- 新增入站传输时先确认它是否需要独立的 `AdapterSpec`：入站字段、排队与回复通道不同就是新驱动器，只是字节到达方式不同则应在同一驱动器内拆分；
- `launch` 不得静态引用 `game`：业务模块名由 `.env` 的路由配置提供，框架不硬编码；
- 三种注册器之外的第四种回调注册方式需要先修改契约，不得在驱动器内私自新增。
